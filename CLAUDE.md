# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A standalone native iOS app bringing Catrobat's embroidery functionality (the Android "Embroidery Designer" flavor) to iOS: users program embroidery designs with Pocket Code-style visual blocks, watch the live stitch preview, and export machine-readable Tajima DST files. Developed as a bachelor-thesis open-source contribution; to be transferred to the Catrobat organization after sign-off. License: AGPL-3.0.

**Read before working**: `docs/ROADMAP.md` (epics, milestones, engineering standards), `docs/DECISIONS.md` (ADR-001…028 — ADR-012 pins the byte-level DST semantics and lists known reference bugs never to port; ADR-013 pins color-change flag placement; ADR-015 pins thread-color emission semantics; ADR-016 pins the M2 ProgramModel/Interpreter target split; ADR-017 pins formula-arithmetic divergences; ADR-018 pins interpreter tick/clock semantics; ADR-019 pins how a golden sitting on a threshold must guard itself; ADR-020 pins the engine's coordinate boundary; ADR-021 pins the M3 preview data path; ADR-022 pins the M3 target layout; ADR-023 pins what runs where — the local commit gate compiles the app, CI runs it; ADR-024 pins the stage renderer; ADR-025 pins the DST header's field widths as a serialization error rather than a trap, and pins field emission order as a contract; ADR-026 pins DST export — the `exportModel.count > 1` gate, the rejecting `DesignName` in front of the mangling header backstop, eager preparation (so a US-211 overflow is a gate reason rather than a failed share), the per-session temp directory, and the exported `.dst` UTType; ADR-027 pins the run lifecycle — two tasks with producer-only cancellation, a terminal that cannot omit the export model, and three budget axes; ADR-028 pins zoom/pan and the stage's VoiceOver summary — one commit per gesture, a fit-aware zoom floor, and a summary only a run-state transition may write), and the current feature's brief in `docs/features/` (ADR-041: work is organised by feature, not by ≤ 5 h story; `docs/user-stories/` is the history of M1–M4).

## Non-negotiable process rules

1. **Test-driven development**: write the failing tests first (the feature brief's test-first outline names them), then implement. No implementation-first code. Red → green happens per slice inside the feature, not once for the whole feature.
2. **Feature-sized units of work** (ADR-041): one feature (e.g. the brick backend, the editor UI, variables) per branch and PR, built out in as many slices as it naturally has. No hour estimates. Commits stay coherent and buildable, but their size follows the work rather than a story budget. **The PR has a size limit even though the feature has no time limit**: when a feature's diff passes roughly 1,500 lines of non-test code, split it into several PRs (e.g. engine, then app). The feature stays the unit of planning; each PR stays a size a reviewer can hold.
3. Where the Catroid and Catty references disagree, **ADR-012 is the arbiter** — never "fix" a red golden test by consulting the other reference.

## Stack & standards

- Swift 6 (strict concurrency), SwiftUI, min iOS 17, universal (iPhone-first). App layer: `@Observable` MVVM on `@MainActor`, no architecture frameworks (ADR-006).
- Engine lives in `Packages/EmbroideryEngine` — platform-independent, synchronous, `Sendable` value types, no I/O; test with `swift test` run inside the package directory (no simulator needed).
- **Swift Testing only** (`@Test`/`#expect`/`#require`), never XCTest. Tests run in parallel: no shared mutable state or fixed file paths; fixtures via `Bundle.module`.
- The `swift-engineering` Claude Code plugin is installed — consult its skills when writing Swift (`swift-testing`, `modern-swift`, `swift-style`, `swiftui-patterns`, `ios-hig`, `localization`, `swift-diagnostics`) and its agents for planning/review. The Sosumi MCP server provides live Apple docs.

## Build & test

- Engine (once `Packages/EmbroideryEngine` exists): `cd Packages/EmbroideryEngine && swift test` — fast, no simulator.
- App: `xcodebuild -project catrobat_embroidery_ios/catrobat_embroidery_ios.xcodeproj -scheme catrobat_embroidery_ios -destination 'platform=iOS Simulator,name=iPhone 17' test` (or `build`).
- Prefer the XcodeBuildMCP tools (`build_sim`, `test_sim`, simulator/screenshot tools) over raw `xcodebuild` — they return structured errors and per-test results.

## Agentic workflow rules

- **Use the swift-engineering plugin agents at their phases** — `swift-architect` during feature planning (before any plan or brief is presented); `swift-search` for code-location queries (keeps grep noise out of the main context); `swift-code-reviewer` after implementation and before handover — once per feature, **plus per slice for every risky slice** (one touching DST bytes, the engine, the interpreter or the program format), together with one Codex round on that slice; `swift-documenter` at feature close (package READMEs for stabilized public API); from M3 on, `swift-ui-design` before building a screen and `swiftui-specialist` for UI implementation. Generic exploration/planning agents complement them but never replace them.
- **Knowledge-graph drift check at the close of a major feature** — run `/graphify . --update` alongside the `swift-documenter` pass when a feature added or changed ADRs, and **not** per slice. It answers one question this toolchain otherwise never asks: *has new work reinvented an invariant an existing ADR already owns?* Read the `semantically_similar_to` edges that cross the `docs/` communities and triage them one by one — **the step is done when those edges have been triaged, not when the tool has been run** — then journal the outcome, including "none, N edges triaged". The AST layer is deterministic and needs no LLM or API key; the semantic layer over `docs/` is what costs (~850k tokens on the first full build; `--update` re-extracts only changed files), which is why this is a feature-boundary tool. **The graph never wins against an ADR** — its `INFERRED`/`AMBIGUOUS` edges are a subagent's single-pass reading of the docs, not a source of truth; where a graph claim and an ADR disagree, the ADR is right and the graph is stale or wrong. Never cite a graph edge to justify changing a golden test (see process rule 3). `graphify-out/` is derived: only `GRAPH_REPORT.md` is tracked (it is the part that diffs meaningfully between milestones); `graph.json`, the HTML viewer and the extraction cache are ignored.
- **Delegation boundary**: delegate *verification and retrieval* liberally; delegate *generation* only against a complete spec. Concretely: feature tests are never delegated — they encode the ADR-012/013 byte semantics and are the least delegable work in the repo (so no `swift-test-creator` for feature tests); `swift-engineer` may implement a slice's green phase against already-red tests ("make these failing tests pass without changing them"). `tca-architect`/`tca-engineer` are out of scope (ADR-006: no TCA), as is `swift-modernizer` (greenfield Swift 6, and Catty code is deliberately not ported wholesale).
- **Cross-vendor review is automated**: marking a PR ready for review (`gh pr ready`), or creating a non-draft PR, triggers a hook reminder to run `/codex-review` (OpenAI Codex, read-only, adversarial-semantics rubric — deliberately different from `swift-code-reviewer`'s). Triage its findings against ADR-012/013 (the ADRs win over the reviewer), record the verdict in the PR description, and journal the delegation outcome. If the triage changed the branch, run the skill's verification round (Codex re-reviews its own fixes). **The loop ends when a round produces no code changes, or when severity has fallen for two consecutive rounds; hard cap 5 rounds** (ADR-041). At the cap the loop stops without escalation: valid findings still open are fixed without a further round or tracked in the PR and journal. Record each round's highest severity, since the stop condition depends on that history. `/finish` verifies this happened; a PR is handed over only with the final round's verdict recorded.
- **Prove red before green**: after writing a slice's tests, run them and show the failures before writing any implementation. A test never seen failing proves nothing.
- **Mutation-check every slice** (ADR-032 invariant 2): before a slice is done, show that a plausible mutation of the code under test turns its tests red. Where the red phase was a compile failure, this is the only proof the assertions discriminate. Record the mutations tried and their result in the PR or journal.
- **Review the brief first when semantics are unclear**: for a feature whose behaviour is not already pinned by ADRs or a reference (e.g. variables), run one Codex round on the brief before writing tests. A feature that only builds on pinned semantics skips this.
- **Never commit red** — except the deliberate TDD red phase: a PreToolUse hook in `.claude/settings.json` runs the engine tests before any `git commit`, plus a signing-free app compile whenever the working tree holds any change under `catrobat_embroidery_ios/`, and blocks if either fails. A failing-tests-first commit is marked with a literal `[red]`, which skips the gate so CI shows the red baseline — on the feature's draft PR, since branches without a PR get no CI (the hook tests for `[red]` anywhere in the command — it is an escape hatch, not a lock). **The local hook is a convenience that catches mistakes, not an enforcement boundary** (ADR-023): it matches command *text*, so unusual command forms and shell expansion can slip past it, and `[red]` is available to anyone who wants it. What actually keeps red out of `main` is the required-status-checks ruleset — engine tests, SwiftLint, the app build and a Release-configuration device compile (`release-build.yml`, the only gate that compiles with `DEBUG` undefined) must pass before a PR can merge.
- **`[red]` commits are optional per slice** (ADR-041): proving red locally (rule above) is mandatory; committing the red state is worth it when the baseline is evidence someone will want later (golden/byte semantics, a bug reproduction), not as a ritual for every slice.
- **Open a draft PR right after a feature branch's first commit** — push it, then `gh pr create --draft`. (Not earlier: a branch with no commits beyond `main` cannot have a PR — `gh` refuses with "no commits between".) `ci.yml` runs `push` on `main` only (ADR-023, 2026-09-28 amendment, which removed the duplicate push/PR run of every PR commit), so a branch **with no PR gets no CI**: without the draft, "push and watch CI after every commit" watches nothing. Opening the PR runs CI on the commits already there, so a `[red]` first commit still shows its red baseline. Mark it ready for review (`gh pr ready`) at handover; the Codex loop runs then, as before. The reminder hook (`.claude/hooks/post_bash_reminders.py`) tells the two apart.
- **Never edit `*.pbxproj`** (permission rule asks first): app sources use synchronized folder groups, so Swift files created on disk under `catrobat_embroidery_ios/catrobat_embroidery_ios/` are picked up automatically. Target/package-dependency changes are done by the human in Xcode.
- Edited Swift files are auto-formatted by a PostToolUse SwiftFormat hook (no-ops if `swiftformat` is missing).
- **UI features**: definition of done includes building, running on the simulator, and capturing a screenshot via XcodeBuildMCP for visual review.
- After notable workflow events (delegation wins/failures, new hooks or rules, tool comparisons, review rounds, defects found by a surprising route), append an entry to `docs/workflow-journal.md` — it is thesis data and stays **exhaustive**. Its granularity follows the circumstance, not the unit of work: one entry per feature is enough for a quiet feature, while a feature with a notable planning decision, review round or delegation outcome gets an entry for each. Every entry should make sense on its own to a reader who was not there. The journal is **append-only**: never edit an existing entry; corrections are new dated entries referencing the old one.
