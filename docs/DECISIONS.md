# Decision log

Lightweight ADRs. Newest at the bottom. Format: context → decision → consequences.

## ADR-001 — App scope: embroidery-focused block app (2026-07-06)
**Context**: On Android, "Embroidery Designer" is the full Pocket Code app (complete Catrobat language + interpreter + stage) shipped as a Gradle flavor. A full port exceeds bachelor-project scope; a blocks-free drawing tool would lose the "learn coding" essence of Catrobat.
**Decision**: Build a visual block-programming app restricted to the brick subset needed for embroidery (motion, control/loops, variables/formulas, the eight embroidery bricks) with stage preview and DST export.
**Consequences**: Interpreter is designed for exactly this subset; brick set parity is defined against the Android embroidery bricks, not all of Pocket Code.

## ADR-002 — Stack: native Swift 6 / SwiftUI, engine as SPM package (2026-07-06)
**Context**: Catty (existing iOS app) is UIKit + SpriteKit with an Obj-C/Swift mix on iOS 13 — dated. Catrobat plans to port its apps to Flutter over the coming months (Paintroid-Flutter is the newest org codebase), which was weighed explicitly.
**Decision**: Stay native: pure Swift 6, SwiftUI UI, minimum iOS 17. The engine (stitch domain, patterns, DST writer, interpreter) lives in a platform-independent Swift Package testable with `swift test`. SpriteKit/Canvas only where stage rendering needs it. Reconfirmed against the Flutter option — the thesis assignment is a modern *native* standalone iOS app.
**Consequences**: Best-in-class iOS experience and TDD-friendly engine without a simulator; diverges from the org's Flutter direction, so eventual maintenance stays a separate native track. Paintroid-Flutter is still mirrored for repo hygiene (CI, lint, conventions), not for code.

## ADR-003 — Project format: native JSON first, .catrobat later (2026-07-06)
**Context**: `.catrobat` files are ZIPs containing a versioned, quirky `code.xml`; full compatibility from day one adds heavy early effort.
**Decision**: Own Codable/JSON project format with a version field. The program model is kept close to Catrobat concepts (scene/object/script/brick/formula) so a `.catrobat` importer/exporter can be added as a later story.
**Consequences**: DST is the only interoperability requirement for core scope; Share-platform interop is a stretch goal.

## ADR-004 — Minimum iOS version: 17.0 (2026-07-06)
**Context**: Trade-off between device coverage and modern SwiftUI APIs.
**Decision**: iOS 17 — covers the vast majority of active devices and unlocks the Observation framework.
**Consequences**: No need for pre-Observation state management workarounds.

## ADR-005 — DST semantics ported from Catroid, verified against Catty fixtures (2026-07-06)
**Context**: Two reference implementations exist: Catroid's `org.catrobat.catroid.embroidery` (canonical, Java/Kotlin) and Catty's `src/Catty/Embroidery/` (Swift). Catty ships a real reference file (`CattyTests/Resources/EmbroideryReference/stitch.dst`).
**Decision**: Treat Catroid as the semantic source of truth (512-byte header, 3-byte records with conversion table, jump bit 0x80, color-change 0xC0, max 121 units/stitch, pixel→unit factor 2.0, terminator 00 00 F3); use Catty's fixtures and tests as golden files for our TDD suite. Port concepts, do not copy code wholesale (all reference code is AGPL-3.0; our project is AGPL-3.0 as well).
**Consequences**: Engine tests are written against known-good bytes before any implementation exists.

## ADR-006 — App-layer architecture: @Observable MVVM, no TCA (2026-07-06)
**Context**: The Composable Architecture was explicitly evaluated (TestStore's TDD fit, block-editor state complexity, effect management) against: solo thesis developer, ≤5h stories, and handover to the Catrobat org, which is not a TCA shop. Most undo-worthy, test-critical complexity already lives in the pure SPM package, which is exactly what TCA would otherwise discipline.
**Decision**: Plain `@Observable` view models on `@MainActor`; zero third-party architecture dependencies. Adopt three TCA-inspired patterns without the framework: (1) editor mutations modeled as a pure `EditAction` enum applied to the value-type program via a single `apply(_:)` funnel — views never mutate the program tree directly; (2) app-layer side effects (file I/O, DST export/share, clock, UUID/date) behind small initializer-injected interfaces with deterministic test doubles; (3) editor tests assert the entire resulting `Program` value, not just the touched field.
**Consequences**: Undo/redo = bounded in-memory snapshot stack (value semantics make it nearly free), coalesced per gesture, bridged to `UndoManager` for shake/Cmd-Z; the undo stack is never persisted. Maintainable by any iOS developer, including Catrobat reviewers and thesis examiners.

## ADR-007 — Stage coordinate space and physical units (2026-07-06)
**Context**: DST units are 0.1 mm, and the engine's pixel→unit factor of 2.0 means 1 stage point = 0.2 mm — stage size determines the *physical* embroidered size, bounded by real hoops (~100×100 mm consumer machines). US-102/US-104 and the M2 virtual needle bake in a coordinate convention long before any UI exists.
**Decision**: Center origin, y-up, fixed virtual stage of 500×500 points (≈ 100×100 mm hoop at 1 pt = 2 DST units = 0.2 mm). The engine applies **no y-flip** when converting to DST units (matching both references); flipping for screen display is purely a rendering concern in M3. Angle convention: degrees, 0° = up (Catroid convention; x via sin, y via cos).
**Consequences**: Engine domain types carry this space explicitly; the M3 canvas, zoom math, and export size validation inherit a deliberate choice instead of an accident.

## ADR-008 — Script representation: flat brick list with paired control bricks (2026-07-06)
**Context**: Catroid scripts are flat ordered brick lists where loops are begin/end brick pairs rendered by indentation; a nested-tree model would force custom nested drag-and-drop in SwiftUI (a multi-week build), whereas a flat list maps directly onto `List` + `.onMove` (free reorder, free VoiceOver reorder actions, free swipe-to-delete).
**Decision**: Scripts are flat ordered brick lists with paired enter/exit control bricks, Catroid-compatible. Nesting is a rendering concern (indentation), not a model structure. Moving a control brick moves its matched pair and enclosed range as one unit — this invariant lives in the model with tests (M2), not in the view (M4).
**Consequences**: M4's editor builds on standard SwiftUI list interactions; the model stays close to `code.xml` semantics for a later `.catrobat` importer.
**Clarification (2026-07-20, US-203 / Codex round 1)**: because a moved pair travels as a *complete balanced block*, reinserting it at any position — including inside another pair — **nests** it and keeps the whole script balanced; it can never *split* a pair. So the move primitive accepts every in-bounds destination (enabling drag-a-loop-into-a-loop and sibling-loop reordering) and rejects only ill-formed moves (bad source, unresolvable pair, out-of-bounds destination). An earlier "reject a move that lands inside another pair as a split" reading was a false premise, corrected before merge.

## ADR-009 — Stage rendering: SwiftUI Canvas with batched paths (2026-07-06)
**Context**: Catty draws one `SKShapeNode` per stitch — a known SpriteKit performance trap that collapses at tens of thousands of stitches. Catroid batch-renders with a single libGDX `ShapeRenderer`.
**Decision**: SwiftUI `Canvas` (Metal-backed) drawing one stroked `Path` for threads and one for stitch points per color run; settled stitches rasterized to a cached image once counts grow, only the live tail redrawn per frame. Zoom/pan is a `CGAffineTransform` applied to the context (unit-testable math). The renderer sits behind a protocol taking `(stitches, transform)` so a Metal escape hatch stays open. Do **not** port Catty's node-per-stitch approach.
**Consequences**: Stack stays pure SwiftUI; M3 exit criterion includes a synthetic 50k-stitch design animating at 60 fps on an A15-class device. `ImageRenderer` over the same renderer gives PNG sharing nearly free (E7).

## ADR-010 — Device family: universal, iPhone-first (2026-07-06)
**Context**: Catrobat's school context makes iPads common; editor-beside-stage is the natural iPad layout. Deciding in M6 would mean rebuilding the navigation skeleton.
**Decision**: Universal app. iPhone-first design priority; the M3 navigation skeleton is size-class adaptive from the start (compact: sequential editor/stage; regular: side-by-side split).
**Consequences**: No navigation rework later; M3 stories include both size-class layouts at skeleton fidelity.

## ADR-011 — Privacy: fully offline, no accounts, no tracking (2026-07-06)
**Context**: The target audience is largely minors (13–18); GDPR-K/COPPA and App Store age-rating implications.
**Decision**: No network access, no accounts, no analytics or tracking of any kind. All data stays on-device; the only data egress is the user-initiated share sheet (DST/image export).
**Consequences**: Simplifies App Store review (age rating, no tracking declaration), removes consent UX entirely, and is a genuine selling point for schools.

## ADR-012 — DST semantics: Catroid is authoritative; known Catty divergences are not ported (2026-07-06)
**Context**: The two references disagree at byte level in places, and the Catty golden fixture is *self-golden* (generated by Catty's own implementation, covering only origin-start, positive-quadrant, single-color-boundary cases). Sharpens ADR-005.
**Decision**: Where the references diverge, Catroid's semantics win. Golden strategy: byte-identical against `stitch.dst` and `color_change.dst`, with the fixture itself verified in an embroidery viewer *before* the golden test is trusted. Specifics pinned now:
- **CO header field counts color blocks, starting at 1** (changes + 1), per both references and both fixtures.
- **Interpolation** follows the references exactly: splitCount = ceil(maxAxisDistance/121); emits duplicate-of-previous-point as jump, intermediates as jumps, target as jump, then target again as a plain stitch; intermediates rounded in stage coordinates *before* unit conversion.
- **Rounding** = `floor(x + 0.5)` (Java `Math.round`; differs from Swift `.rounded()` on negative halves). Relative deltas are computed between individually converted absolute positions (round-then-subtract), never from rounded differences.
- **Extents** are written relative to the first stitch, magnitudes only (per DST spec; equals Catroid's behavior for origin-start designs). A non-origin-start test case covers what the fixtures cannot.
- **Known Catty bugs — do not port**: rejects legal ±121 deltas (fatalError guard uses strict comparison); truncates name to 16 chars instead of 15; writes signed −X/−Y extents; computes extents relative to start point with a sign bug; 4-point sew-up. Catroid's 5-point sew-up (center/ahead/center/behind/center) and 15-char name limit are authoritative.
- **Workspace dedup**: an identical consecutive stitch command from the same actor at the same position emits nothing (Catroid `DSTStitchCommand.act`).
- **Deliberate divergence from Android**: Catroid's Set Thread Color brick only sets a sprite property and never emits a DST color change mid-script (color stops arise only from sprite/layer switches) — in our mostly single-object app that would make the brick a machine-level no-op. We emit a color-change record whenever the newly set color actually differs from the current thread color.
**Consequences**: Every M1 story's acceptance criteria cite these semantics; a future story cannot "fix" a red test by consulting the wrong reference.

## ADR-013 — Color-change flag placement on interpolated moves follows Catroid; the color_change golden is compared through a documented flag transposition (2026-07-09)
**Context**: Discovered during US-105 (journal 2026-07-09): when a color change precedes a long interpolated move, Catty consumed the pending flag on the *first* interpolation jump (the duplicate-of-previous record, at the old position — `color_change.dst` record 9 = `00 00 C3`), while Catroid applies pending flags to the target point before interpolating, so the flag lands on the *final plain stitch* at the new position. ADR-012 didn't pin this case; the sewn output is identical either way (jumps sew nothing — only the machine's pause position differs), but the bytes are not, so US-106's byte-identity criterion against `color_change.dst` cannot hold together with Catroid semantics.
**Decision**: Catroid placement wins (Sebastian, 2026-07-09) — the deciding concern is the Catroweb workflow: a program shared on the Catrobat platform must produce the same DST bytes on iOS as Android's Embroidery Designer. `EmbroideryStream` keeps capturing pending flags before interpolation and emitting them on the final plain stitch. The `color_change.dst` golden test therefore compares against the fixture with a **documented two-byte flag transposition** (the post-color-change move's duplicate-jump record byte 2 `C3→83`, its final plain-stitch record byte 2 `03→C3`), derived and asserted inside the test with a reference to this ADR.
**Consequences**: The transposed expected bytes are no longer the viewer-verified Catty original, so US-106's manual check re-verifies a *freshly generated* color-change file in Ink/Stitch (color stop must pause at the new position). `stitch.dst` is unaffected and stays byte-identical.

## ADR-014 — Pattern-layer arithmetic is Double; sub-resolution divergence from Catroid's float is accepted (2026-07-13)
**Context**: Catroid's stitch patterns compute in Java `float`; the engine's patterns (US-107 `RunningStitchPattern`, US-108 `ZigzagStitchPattern`) compute in `Double` — engine-native and matching Catty's prior art. Codex review of US-107 (journal 2026-07-10) produced a verified repro where the widths diverge by one stage unit after rounding (length 1, (−10,−10)→(−148,81): interpolated stitch 98 lands at (−93,44) in Double vs (−93,45) in float). US-108 makes the gap test-visible for the first time: zigzag offsets go through `sin`/`cos`, whose Double results carry ~1e-16 residue (`sin(180°)` = 1.22e-16, not 0), so Catroid's integer-exact expected coordinates cannot be asserted with `==`.
**Decision**: Pattern-layer geometry stays `Double`. Last-ulp divergences from Android's float output are accepted: they are orders of magnitude below embroidery resolution (1 unit = 0.5 stage points) and are absorbed by the ADR-012 `javaRound` at unit conversion in all but adversarially constructed cases. Pattern tests assert stage-space coordinates within an absolute tolerance (1e-9 — far above transcendental noise, far below resolution) instead of exact equality. Folded in from US-107, with the Catroid behavior stated precisely (corrected per Codex US-108 review): the degenerate-input guards (non-positive length, non-finite positions/width/heading emit nothing and leave state untouched) diverge deliberately from Catroid, where a **zero** length (the formula-error fallback) NaN-poisons the anchor via `distance % 0` and the pattern goes permanently dead, while a **negative** length "works": every update crosses the threshold and emits degenerate duplicate/pair spam at the clamp. The zero/non-finite guards avoid porting an accident Swift would turn into a trap; the negative-length no-op is an intentional product-semantic change, not trap avoidance. Headings are normalized mod 360 (exact) before the radian conversion: Catroid feeds raw degrees to `sin`/`cos` but only ever sees values pre-normalized to (−180, 180] by its sprite layer, so headings outside that domain have no reference semantics — the engine extends them by exact periodicity, which for enormous finite headings deliberately differs from Java's raw huge-argument reduction noise (second Codex US-108 round). Same policy for astronomical stitch counts (US-108 review find): an update whose whole-length count exceeds 1,000,000 emits nothing — Java's `(int)` cast saturates to `Integer.MAX_VALUE` and Android hangs materializing the stitches, Swift's `Int(_:)` would trap; neither accident is ported.
**Consequences**: ADR-012's golden byte-identity tests are unaffected — their inputs sit away from representability boundaries. But bit-exact parity with Android is **not** guaranteed for arbitrary programs (sharpened per Codex US-108 review): float-vs-Double differences can flip a threshold crossing or a `javaRound` boundary and thereby change stitch counts or single units — e.g. a needle at 9.9999998 rounds to 10.0f in float and crosses a length-10 threshold that Double does not; a first stitch at float-exact 31.25 converts to unit 63 where Double's 31.249999999999982 gives 62. Accepted as sub-resolution in effect and vanishingly rare in practice; a story that needs bit parity (e.g. Catroweb round-trip validation) would have to revisit with `Float` pattern arithmetic. Until then, pattern tests cite this ADR for their tolerance helpers.

## ADR-015 — Set Thread Color emission semantics: silent start, invalid-hex no-op, clause-B black, ==121 tie-off (2026-07-15)
**Context**: ADR-012 pins the deliberate divergence that Set Thread Color emits a DST color change when the newly set color differs from the current one, but US-110 planning surfaced edges neither reference decides: what happens before the first stitch, on unparseable input, and at the exact ±121 boundary of `DSTStitchCommand.act`'s layer-switch clauses. Pinned with Sebastian during US-110 planning (2026-07-15).
**Decision**:
- **Silent before the first emitted stitch**: setting a color while nothing has been emitted manager-wide only chooses block 1's starting color — no change record, no empty leading color block. Consistent with Catroid's precedent that color changes only ever enter non-empty streams (clause C requires a non-empty stream; assembly inserts changes only between non-empty layers). A differing set after any emission always arms a change that the actor's next surviving stitch carries; the armed change survives clause-A dedup (which also still updates the actor's last command, as `DSTPatternManager.addStitchCommand` does).
- **Invalid hex is a full no-op**: `ThreadColor(hexString:)` mirrors `SetThreadColorAction` exactly — **UTF-16 code-unit** offsets [1,3)/[3,5)/[5,7) as RR/GG/BB (Java `String.substring` counts UTF-16 units, so `"€FF0000"` parses red on both platforms; corrected per swift-code-reviewer US-110, which caught an initial UTF-8-byte port), offset 0 skipped unvalidated, offsets ≥7 ignored (alpha discarded) — and returns nil for anything malformed, so the current color is kept. This is Android's observable behavior (the parse exception is swallowed; even its null-formula default `"0xff0000"` throws internally and no-ops). Signs are rejected per pair: Java's `Integer.decode("0x+1")` throws where Swift's `UInt8(_:radix:)` would accept. The digit set is Java `Character.digit(char, 16)`'s, not ASCII's (Codex US-110 round 2, verified under Java 17): fullwidth Latin letters and every Unicode decimal digit (Nd) count, digit value must be < 16 — so `"#ＦＦ0000"` is red and `"#ＧＧ0000"` is a no-op on both platforms.
- **Clause-B transition points are black**: on an actor change Catroid emits the workspace's color, which `DSTWorkSpace` never assigns — a reference quirk, ported as `.black` with this provenance note rather than as a nullable color.
- **Exactly ±121 units on a layer switch**: clause C compares strictly `>` (so 121 takes the tie-off branch: previous point with the change, jump, previous point) and clause D strictly `<` (so 121 emits no extra connecting point) — both per the reference's operators, pinned by tests because the boundary is invisible in Catroid's own test suite. The clause distance rounds **previous − target** per axis (Catroid `getMaxDistanceBetweenPoints` argument order) before `abs`, while the stream's interpolation check rounds target − previous (`DSTStream.addInterpolatedPoints`); because `javaRound` is asymmetric at negative halves the two disagree on half-unit gaps — a +60.75-stage layer switch is clause-near yet interpolates, its −60.75 mirror is clause-far yet does not (swift-code-reviewer US-110 find with executed repro; an initial target − previous port classified both backwards).
**Consequences**: A program whose first bricks set a color then stitch produces CO equal to its actual color-stop count (no phantom leading block). Multi-color designs count set-color changes and layer-boundary changes through the same `addColorChange()` funnel, so `CO = changes + 1` (US-104) holds across sources. The manager's stage-space ops replay (US-110) must keep emitting through the stream's dedup-free `append(stitchAt:)` seam; the single-layer equivalence test guards that the lazy replay stays byte-identical to Catroid's eager per-layer interpolation.

## ADR-016 — M2 target layout: ProgramModel and Interpreter as two sibling targets (2026-07-16)
**Context**: The roadmap places M2's program model and interpreter in "a sibling target in the same package (`ProgramModel`/interpreter depending on the engine target, never the reverse)" without deciding whether that is one target or two. M4's editor mutates the program tree and M5's persistence encodes it to JSON; neither needs stitch machinery or DST types. A single combined target would make every model import transitively pull in the engine.
**Decision**: Two sibling targets in `Packages/EmbroideryEngine` (Sebastian, 2026-07-16, M2 planning): **`ProgramModel`** — the pure value graph (Program/Scene/Object/Script/Brick/Formula), Foundation-only, holding no engine types (positions as `Double`s, colors as hex `String`s) — and **`Interpreter`**, depending on `ProgramModel` and `EmbroideryEngine`, the only place model and engine meet (needle → `RunningStitch`/`SewUp` → `EmbroideryPatternManager`). The engine target gains no dependency in any direction.
**Consequences**: M4/M5 import `ProgramModel` without linking embroidery/DST code; the M3 app imports `Interpreter` (plus the engine for `DSTFile`). The dependency DAG stays a straight line inward, and `ProgramModel`'s engine-freedom is enforced at build level (US-201) rather than by convention. Cost: one more target and product in the manifest, and the interpreter owns all model↔engine conversions (stage-point construction, hex parsing via `ThreadColor(hexString:)`).

## ADR-017 — Formula arithmetic is native Double; decimal128 divergence and non-finite-literal semantics pinned (2026-07-19)
**Context**: US-202 ports Catroid's formula evaluator (M2 subset). Catroid computes PLUS/MINUS/MULT/DIVIDE in `BigDecimal`/`MathContext.DECIMAL128` (`FormulaElement.java:820-855`), so e.g. its `0.1 + 0.2` is exactly decimal 0.3 where binary `Double` gives 0.30000000000000004. The story's divergence AC promised an ADR pinning the accepted scope; Codex US-202 round 1 correctly flagged that ADR-014 covers only pattern-layer geometry (`Double` vs Java `float`), not formula evaluation, and surfaced two further edges pinned here.
**Decision**:
- **Native `Double` arithmetic for the four decimal operators.** The finite-operand divergence from decimal128 is accepted and is bounded **per operation** by ~1 ulp of the intermediate operand magnitude — an *absolute* bound that catastrophic cancellation can make arbitrarily large *relative* to the result (Codex US-202 round 2: `100000000.1 − 100000000` is exactly 0.1 in decimal128 but 0.09999999403953552 in `Double` — off by ~6e-9, and no universal absolute tolerance covers all magnitudes). The gap scales with the *result's* ulp and the operation's conditioning, not merely operand magnitude — a division by a tiny divisor blows it up even from stage-space-small operands (Codex US-202 round 3: `0.1 / 3e-9` is 33333333.333333332 via decimal128 but 33333333.333333336 in `Double`, a ~3.7e-9 gap from operands within ±500) — so no fixed absolute tolerance is valid across all in-range inputs; the divergence is accepted without a universal bound. The characterization tests therefore assert **selected cases at pinned magnitudes** within the ADR-014-style 1e-9 absolute tolerance (all current cases are near-unity) — the tolerance is a property of the chosen test inputs, not a promise for every divergent expression; a test at larger magnitude must justify its own tolerance from the ulp bound. `pow` is exact `Math.pow` parity — Catroid, too, computes POW on doubles.
- **Mirrored, not diverged** (each with characterization tests): per-node non-finite normalization (±∞ → ±`Double.MAX_VALUE`, NaN through, NaN-at-root the only throw — `FormulaElement.java:391-394`, `FormulaElementOperations.kt:97-101`); zero-divisor DIVIDE → NaN (including −0.0, which `BigDecimal.equals` treats as 0 there); `interpretInteger` = `Double.intValue()` truncate-toward-zero with Int32 saturation; the POW NaN guard (`atLeastOneIsNaN` precedes `Math.pow`; IEEE `pow(1, NaN)` = 1 would otherwise leak); and POW **zero-sign canonicalization** — Catroid round-trips POW operands through `BigDecimal.valueOf`, which has no signed zero, so `pow(-0.0, -3)` is `Math.pow(+0.0, -3)` = +∞ → +MAX_VALUE where raw IEEE gives −∞: a maximum-magnitude sign flip, reachable without a literal via `pow(-(0), -3)` (Codex US-202 round 1).
- **Pinned divergence — non-finite `Double` literals normalize like computed values.** Catroid NUMBER nodes store *strings*, which skip normalization: a crafted `NUMBER("Infinity")` root survives to `interpretDouble` as +∞, and as a binary operand hits the `BigDecimal.valueOf` catch and coerces to 0 (`Infinity + 1 == 1`) — that coercion branch is live *only* for string literals; computed doubles are normalized before it (which is why US-202's original coerce-to-0 AC, written for `pow(1e308,2)+1`, was wrong). Our `Formula.number` is `Double`-typed; no *editor* surface can produce an ∞/NaN literal (Catroid's own editor writes digit strings), but the public API can — M2's hardcoded programs and M3's bundled samples construct `Formula` values directly, and Catroid's programmatic `new Formula(Double.POSITIVE_INFINITY)` stores NUMBER `"Infinity"` (root → +∞ there) — so this is an accepted **public-API divergence**, not merely a crafted-XML one (sharpened per Codex US-202 round 2): `number(.infinity)` normalizes uniformly at the leaf to `greatestFiniteMagnitude` (`number(.nan)` throws), both at the root and as an operand (`.plus(.number(.infinity), .number(1))` is `greatestFiniteMagnitude` here, 1 in Catroid — characterized in `FormulaTests`). Our own repo never authors non-finite literals in programs. If the stretch-scope `.catrobat` importer ever needs literal-level fidelity, it owns that decision (re-type the case or reject such files) — the evaluator does not carry string semantics on a `Double` payload.
- **Zero-sign residue elsewhere is accepted as unobservable**: signed zeros survive plus/minus/mult/divide in native `Double` where Catroid's `BigDecimal` canonicalizes them (e.g. `-0.0 × 5` is −0.0 here, +0.0 there). Every magnitude-visible composition runs through POW, whose canonicalization covers it; the remaining differences are sign-bit-only and invisible to comparisons, zero-divisor checks, integer truncation, and stitch geometry.
**Consequences**: Formula tests cite this ADR for their tolerance helper and the literal-normalization characterization. US-205's fallback-and-continue can rely on `FormulaError.notANumber` being the sole evaluation error. Bit-exact formula parity with Android is not guaranteed for arbitrary finite arithmetic (same class as ADR-014's boundary caveat); a story needing it would have to adopt decimal128 arithmetic, not tweak tolerances.

## ADR-018 — Interpreter tick & clock semantics: one-action-per-tick round-robin, zero-tick loop bookkeeping, accumulating logical clock (2026-07-23)
**Context**: US-205 builds the headless interpreter. The story required an ADR pinning the tick/clock semantics — how a program advances one step at a time, how concurrent scripts interleave, how loops and `wait` account for ticks, and how bad formulas are handled — verified against Catroid's `ThreadScheduler`/`ScriptSequenceAction`/`RepeatAction`/`WaitAction` and libgdx `SequenceAction`/`TemporalAction`. The model stays the flat paired brick list (ADR-008); everything here is interpreter-internal.
**Decision** (Sebastian, 2026-07-23; several edges sharpened by swift-code-reviewer and Codex):
- **Compilation is internal and one-shot.** Each `whenStarted` script compiles once to a linear `[Instruction]` array with a single-pass backpatch: `repeatLoop` → `repeatBegin(times, endIndex)`, `forever` → `foreverBegin`, `loopEnd` → `loopEnd(beginIndex)`, everything else → `brick`. `endIndex+1` is the forward-skip on exhaustion, `beginIndex` the back-jump (Catty `CBBackend` precedent). An unbalanced script (fails `Script.validate()`) compiles to an inert `[]` — its thread finishes on its first `step()` pass emitting nothing, never a crash or a halt.
- **Tick = one round-robin pass.** One `step()` visits every non-finished thread once, in creation order (scene → object → script). `ActorID` is the global object index. Threads on the same object share one `ObjectRuntime` (needle + variable store), so two scripts on one object interleave brick-by-brick — stitch-visible, and the reason the needle/vars live per-object, never per-thread.
- **One action-producing instruction per thread per tick.** Motion / data / `wait` / embroidery bricks each cost exactly one tick (Catroid `ThreadScheduler` runs each thread's `act` once; libgdx `SequenceAction` advances at most one child). Loop bookkeeping (`repeatBegin`/`foreverBegin`/`loopEnd`) is **zero-tick** and folds into the completing tick: the counter-check and back-jump run in the same tick as the body's last brick, and the *next* iteration's first brick is deferred one tick (`RepeatAction` parity). A thread is marked finished in the same tick its last brick runs (not a tick later). Deferral is gated at the two loop-body entries (`foreverBegin`, `repeatBegin`'s enter-branch) when an action already ran this tick; the `loopEnd` guard additionally consumes the tick for an action-free iteration in isolation. Both guards are needed — either alone either hangs an empty body or spins an action-then-empty-loop (`[move, forever, loopEnd]`, swift-code-reviewer).
- **Action-free loop bodies consume one tick per iteration and never hang.** `forever {}` is bounded only by `run(maxTicks:)`. **Accepted degenerate** (Codex): an empty `repeatLoop(n){}` detects termination one tick *after* its last empty iteration (the empty `loopEnd` yields before the begin can fold exhaustion in). Fixing it would reintroduce a spurious empty tick on the common nested-loop *entry* case, a worse trade; characterized with a test rather than "fixed". **Compounding under nesting** (Codex round 2): nested empty loops add one such late tick at *each* enclosing `loopEnd`, and because same-object scripts share one needle, the extra ticks can shift a concurrent script's bricks across a turn — stitch-visible *in principle*. This is broader than a "harmless" single-level delay, but is unreachable by any real program (nested empty loops emit nothing) and Catroid's own nested-empty accounting is not cleanly pinned; accepted as a pathological divergence and characterized, not matched.
- **`wait` uses an accumulating logical clock — no wall-clock.** On first arrival the duration is resolved via `interpretDouble` (a throwing/zero/negative formula → 0 → 1 tick, Catroid `WaitAction` duration-0 fallback). Each tick `elapsed += clock.tickDelta`; the wait completes when `elapsed >= duration`, checked **after** the add, emitting one `.waited`. Nominally this occupies `ceil(seconds/tickDelta)` ticks, but **accumulation is authoritative** (Catroid `TemporalAction` accumulates `time += delta` likewise): binary-FP means an exact-ratio wait can drift one tick from the nominal `ceil` (Codex: `0.1/0.01` sums to `0.09999999999999999`, completing on tick 11 not 10). Deterministic and characterized, not a bug. `interpretDouble` — not Catroid's Float-API `interpretFloat` — is used so the Double clock stays exact for representable ratios (e.g. `0.1/0.05` → 2 ticks). The duration is **re-resolved each time the wait is entered**: a throwing formula → 0 on *every* entry. This is a deliberate divergence from Catroid (Codex round 2): Catroid reuses one `WaitAction` instance across loop iterations, and its `begin()` only calls `setDuration` on successful interpretation, so a throwing formula on a *reused* wait retains the *previous* iteration's duration (a stale-state artifact of object reuse). We do not replicate that quirk — a wait's duration depends only on its own formula, not on a prior iteration's value. **Precondition**: `tickDelta > 0`; a zero/negative/NaN delta leaves a positive wait runnable forever (caller contract, not runtime-guarded in M2).
- **Variable store.** Project + per-object `[String: Double]` stores; a thread reads object-shadows-project, unknown → 0 (`VariableStoreScope`, matching `ProgramModel.VariableScope`). **First declaration of a duplicate name wins** (Codex — a plain dictionary build would let a later duplicate shadow the first, reversing `VariableScope`'s first-match contract). Writes resolve object-declared → object store, else project-declared → project store, else object-local; an object-scoped write never leaks to the project scope.
- **Repeat count fallback.** `repeatBegin` resolves its count via `interpretInteger` (Int32-saturating, ADR-017); a throwing / negative / zero count → 0 iterations (Catroid `RepeatAction.interpretRepeatCount` catches → 0, and clamps `< 0 → 0`). Nested loops multiply because the counter, keyed by the `repeatBegin`'s index, is cleared on exit so a re-entering outer loop reinitializes it.
- **Never halt.** Every bad-formula path continues with a per-brick fallback: motion via `VirtualNeedle.apply` (catch-and-skip; `placeAt` per-coordinate zero-substitution — US-204/ADR-014); `wait` → 0; `repeatLoop` → 0 iterations; data bricks → substitute 0 (`setVariable` writes 0, `changeVariableBy` adds 0, a no-op) — deliberately distinct from motion catch-and-skip, mirroring Catroid data actions reading through `interpretDouble` (→ 0 on failure). `FormulaError.notANumber` is the sole formula error (ADR-017).
- **Events.** `InterpreterEvent` lands all five cases now; only `needleMoved` and `waited` are produced in US-205. `stitch`/`colorArmed`/`finalizeRequested` are produced from US-206 with provisional payloads chosen to avoid reshaping the enum.
**Consequences**: `run(maxTicks:)` is the concatenation of `step()` batches, so batch and step-by-step consumption agree by construction (M2 exit criterion) — the equivalence test is a structural invariant guard, not a behaviour test, and passed on arrival. A run is snapshot/replayable by copying the `Interpreter` value (all state inside it, no reference types, no globals). Golden-program stories (US-207/208) inherit deterministic tick accounting; any wait in a golden program must accept the accumulation semantics pinned here. US-206 attaches embroidery-event production and engine wiring to the existing dispatch fork (`VirtualNeedle.apply` returning `nil` = non-motion brick).

## ADR-019 — Structure-determining threshold crossings are a distinct class from coordinate tolerance; a golden sitting on one must say so and guard it (2026-07-27)
**Context**: ADR-014 pins pattern-layer arithmetic as `Double` and sets a 1e-9 absolute tolerance for *coordinates*, on the argument that last-ulp divergence is "orders of magnitude below embroidery resolution" and is absorbed by the `javaRound` at unit conversion. Its Consequences paragraph notes in passing that a divergence can flip a threshold crossing, but the ADR's operative rule is about coordinate comparison only. US-208 found the gap is not hypothetical and not small. A stitch pattern decides *how many* stitches an update emits by `floor(distance / length)`; when the exact distance is a whole multiple of `length`, that comparison sits exactly on a rounding boundary and one ulp of `hypot` changes the emission **structure** — the stitch count, the anchor's resting place, and therefore every subsequent point. A 1e-9 tolerance on coordinates cannot express, let alone absorb, a design with a different number of stitches in it.

The concrete case: US-208's five-pointed star walks sides of 20 stage units at stitch length 5. A pentagram's move directions are irrational, so side 4's exact length from the pattern anchor is 19.999999999999998122…, which is 1.878e-15 below 20 — past the half-ulp boundary (1.776e-15) by roughly 1e-16, so the correctly rounded `Double` is 19.999999999999996 and the side yields **three** intervals. Darwin's `hypot` is ~0.53 ulp high here and returns exactly 20.0, yielding **four**. The golden's structure from side 4 onward depends on which — sides 1–3's thirteen records and the five tack records are identical either way, since the tack centres on the needle and the needle is unaffected by the pattern (Codex US-208 corrected an earlier "every literal"). Verified at 60 significant digits, and demonstrated by swapping an fma-compensated correctly-rounded `hypot` into `ZigzagStitchPattern`: all 308 non-star tests stayed green while seven star tests went red (swift-code-reviewer US-208). Neither C nor IEEE-754 requires `hypot` to be correctly rounded, and implementations differ: Python 3.14.6 on the same machine returns 19.999999999999996 for these operands where Darwin returns 20.0. No claim is made here about particular glibc or CPython version thresholds — an earlier draft asserted "glibc ≥ 2.35, Python ≥ 3.8" and neither project promises correct rounding for `hypot` at all (Codex US-208); what is pinned is that the value is implementation-defined and that this golden depends on Darwin's.

**Decision** (Sebastian, 2026-07-27, on the US-208 review):
- **Coordinate tolerance and structural thresholds are separate concerns.** ADR-014's 1e-9 governs "is this point where we expected"; it says nothing about "does this update emit n or n−1 points". The second question has no tolerance — it is a discrete outcome — so it must be handled by *choosing* inputs off the boundary, or by pinning the platform and saying so.
- **The test is not "is the distance on a boundary" but "how far is the *exact* distance from it, in ulps".** Any closed regular polygon walked at an integer side/length ratio is *on* a boundary — US-207's square included, since 20.0 / 5 is exactly 4.0 (Codex US-208 round 2, correcting a first draft that called the square off-boundary). What separates the two goldens is where the exact value sits relative to half an ulp, and that is decided by the **along-motion component** of the floating-point residue: decompose the residue along and perpendicular to the nominal direction, and only the along component moves the distance to first order — the perpendicular one enters quadratically and is negligible at these magnitudes. US-207's square has *no* along component on any side (sides 1–2 carry no residue at all; sides 3–4 a purely perpendicular one), so its exact distances are 20, 20, 20 + 3.16e-31 and 20 + 3.37e-31 — sixteen orders of magnitude inside the 1.776e-15 half-ulp. Stated exactly (Codex US-208 round 4 caught a looser version of this): the representable value *below* 20 is 19.999999999999996, a full ulp away from those exact distances, so no implementation erring by less than one ulp can return it; the admissible results are 20.0 and 20.000000000000004, and `floor(d / 5)` is 4 for both. A correctly rounded `hypot` returns exactly 20.0. Either way the square's structure is safe, which is the claim that matters — not that every implementation returns the same bits. US-208's star side 4 does have one: its residue decomposes into −1.878e-15 along and −1.181e-15 perpendicular, and the along term alone puts the exact distance at 20 − 1.878e-15, just *outside* the half-ulp, so a correctly rounded `hypot` must return the value below 20 and only an implementation erring by ≥ 0.5 ulp rounds it back up. (Codex US-208 round 3 corrected an earlier draft that called the star's residue purely along-motion and claimed the square safe under *every* conforming implementation — nothing here is conformance-guaranteed, since C and IEEE-754 impose no accuracy bound on `hypot`; the square's margin is simply so large that no implementation in practice threatens it.) On-boundary is the screening question; the along component's ulp distance is the deciding one.
- **A golden whose structure depends on a boundary crossing must document the dependence at the value that causes it and guard it with a direct assertion.** Not a comment alone: a test that measures the crossing quantity itself, so a platform or toolchain change names its own cause instead of leaving the golden's diff to be re-derived from scratch. US-208's `theGoldenDependsOnLibmRoundingOfHypot` is the reference implementation of this rule.
- **US-208 keeps its parameters and accepts the pin to Apple platforms' libm.** `Package.swift` declares only `.iOS(.v17)` / `.macOS(.v14)`, CI is macOS-only, and the product is an iOS app; the alternative — a stitch length that does not divide the side — decouples the pattern anchor from the polygon's vertices, making every golden literal irrational and the closed-form hand derivation (the independent half of the golden, and the thing that gives it its value) substantially harder. The trade was taken deliberately, not by omission.
- **No general rule that goldens must avoid boundaries.** For a closed regular polygon there is no integer side/length ratio that escapes: the boundary is wherever the ratio puts it. Demanding boundary-free parameters everywhere would forbid the legible designs these goldens are built from.

**Consequences**: The first Linux SwiftPM job — plausible once the package moves upstream to Catrobat — can be *expected* to turn US-208 red, though this ADR declines to pin any particular libm's behaviour and so cannot promise it (Codex US-208 round 2); the tripwire test is what will explain the failure if it comes. Whoever adds that job owns the choice then: re-derive the star with margin-bearing parameters, or make the golden platform-conditional. This is a *narrower* claim than ADR-014's "bit-exact parity with Android is not guaranteed": here it is Darwin-vs-Linux on identical `Double` source, with no Java in sight. US-209's pattern→stream→bytes differential and US-210's ±121 chokepoint both compare against thresholds and should check whether their inputs sit on one. US-207's square needs no tripwire, but neither of the two reasons drafted first was right. It is **not** free of trig residue — `cos(π/2)` is 6.123e-17 and `sin(π)` is 1.2246e-16 (exactly the dust ADR-014 cites), so its third side ends at x = 20.000000000000004 and its fourth at 3.55e-15, and US-207's `tackCentreIsNotTheLastPathPoint` is built on that. Nor is it off-boundary: 20.0 / 5 is 4.0, the boundary itself. It is safe because its residues are *purely perpendicular* to its motion and so cost the distance only ~3e-31 — a margin no `hypot` with sub-ulp error can round across. That is the ulp-distance test above, and it is the one to apply to any future golden.

## ADR-020 — The engine's coordinate boundary: interpolation decides on the encodable delta, unconvertible coordinates and unsplittable moves are guarded no-ops (2026-07-31)
**Context**: Two coordinate traps were carried in `docs/workflow-journal.md` from 2026-07-09 to M2's last story. **(a)** `EmbroideryStream.addInterpolatedStitches` decides whether to split a move from the stage *difference* rounded to units (Catroid `getMaxDistanceBetweenPoints`), while `DSTFile` encodes each record from *individually rounded positions* subtracted (ADR-012 round-then-subtract). `javaRound` makes the two disagree by one unit at half-unit stage fractions, so at the exact boundary a move the decision measures as 121 encodes as 122 and trips `DSTStitchRecord`'s precondition — a hard crash in a released app. The journal's minimal repro is previous x = 0.125 → target 60.75 (Codex US-110 round 1); the original is −0.3 → 60.3 (swift-code-reviewer US-105). Catroid shares the asymmetry and, having no trap, silently emits a corrupt record (`CONVERSION_TABLE[122]` is the −1 entry), so byte parity here would be parity with corruption. **(b)** `Int(javaRound(value × 2))` traps on NaN, ±∞, and finite values past `Int` range; `EmbroideryStream.addStitch(at: StagePoint(x: .infinity, y: 0))` crashed. ADR-014's guards cover only the pattern path, and Codex's M2-planning rounds established that an interpreter-side guard reaches neither trap: (a) is an engine-internal disagreement, and both leave direct engine callers exposed. The pattern manager compounds (b) — it converts stitch positions in the `assembled()` replay but its clause distance converts a stage *difference* at command time, so there are two reach points, not one.
**Decision** (Sebastian, 2026-07-31, US-210 — delegated to the implementation after the trade-offs were laid out):
- **The encoded delta is a second interpolation *trigger*, never a second split *count*.** A move splits when Catroid's difference-rounded distance exceeds ±121 **or** when the round-then-subtract delta `DSTFile` will actually encode does. The split count stays Catroid's `ceil(difference/121)` whenever the difference triggers, and is **2** when only the encoded delta does — 2 rather than `ceil(121/121)` = 1 because a one-way split emits no intermediates and re-enters the same decision with the same pair, which would not terminate. Within the domain the guards below admit, the result is a strict **superset** of Catroid's interpolation: identical emission on every admitted input whose Catroid output is encodable, extra splits only where Catroid emits a corrupt record. The qualifier is load-bearing and was initially missing (Codex US-210 round 1) — the split cap and the lattice guard *refuse* moves Catroid would have split successfully, e.g. a 121,000,008-unit move, where Catroid attempts ~1,000,001 parts and reaches encodable records. Refusing is a deliberate divergence chosen against a hang, not parity; ADR-012's "the reference wins where it is sound" governs what we emit, not whether we emit at all. Two rejected alternatives, both of which close the trap and both of which are wrong: deciding from the encoded delta *alone* stops splitting in the mirror case (difference 122, encoded 121, e.g. 0.25 → 61.0) where Catroid splits and is correct; and taking the **maximum** of the two as the count changes emissions the reference gets right — at difference 242 / encoded 243 (stage 0.125 → 121.25) it emits six stitches where Catroid emits eight, because Catroid's own recursion already re-splits the over-long first hop. ADR-012 permits divergence only where the reference is unsound, and 242/243 is not such a point. Clamping the delta at the record seam was rejected too — it drops a unit of geometry the needle never recovers. `DSTStitchRecord`'s precondition **stays**: the stream now guarantees the invariant, and the precondition is the programmer-error backstop for anyone constructing a record directly. Both halves of the contract are pinned by name — `differenceTriggerStillWinsWhereTheEncoderIsInRange` for the trigger, `catroidSplitCountSurvivesTheEncodedDeltaBackstop` for the count.
- **The recursion terminates only because the stage lattice is bounded, and that bound is a guard, not an observation.** Each emitted hop re-enters `append` and re-checks its own distance, so a hop that the intermediate's stage-space rounding pushes back over 121 splits again. An S-way split leaves hops of about `distance/S` plus at most ~2 units of snapping slack, so magnitude normally falls by roughly the split factor per level and the depth is small. **That argument is false at large coordinates and the first version of this ADR asserted it unqualified** (Codex US-210 round 1): above ~2^58 stage points the gap between adjacent `Double`s exceeds ±121 units, so at 2^58 → 2^58 + 64 — a 128-unit move both endpoints convert exactly — the only midpoint is exactly halfway between neighbours, ties-to-even snaps it back onto `previous`, the split emits nothing new, and the target re-enters the identical decision. Reproduced as a stack overflow, not a trap or a hang. Interpolation therefore additionally requires the lattice step to stay within ±121 units — **per axis, and only for an axis that actually has to be split**; beyond that no encodable non-zero move exists on that axis and the move is refused whole, like an over-long one. The per-axis scoping is not a detail: a first version tested one maximum across all four components and so let a coordinate merely *sitting* at a coarse magnitude veto a legal move on the other axis (Codex US-210 round 2 — `(2^58, 0) → (2^58, 1)` encodes as a plain `(0, 2)` delta and was being dropped). A coarse axis cannot be short and non-zero, since its hop is a multiple of a step wider than ±121, so "already fits a record" and "does not move" are the same case there. The step to compare is the coarsest one *inside* the interval — `max(|start|, |end|).nextDown.ulp` — and not `.ulp` of either endpoint, which at an exact power of two reports the spacing going **outward**: `2^58 → 2^58 − 64` heads into the finer binade, has a representable midpoint, and subdivides, while `2^58 → 2^58 + 64` has none (Codex US-210 round 3). Taking the *finer* endpoint instead is wrong the other way — `2^58 → 2^58 + 128` subdivides once into a hop that is itself non-progressing, so it has to be refused up front rather than one level down. With that guard the progress argument becomes sound rather than merely typical: every hop is a multiple of the lattice step, so a hop exceeding ±121 spans at least two steps and its subdivision cannot collapse onto an endpoint. The invariant that ultimately matters is that `append` is the only place a `Stitch` is added and always re-evaluates both measures first, so every consecutive appended pair satisfies both `≤ 121` by construction. Pinned by `moveTooCoarseToSubdivideIsANoOp`, its one-binade-lower counterpart `moveAtTheCoarsestSubdividableLatticeStillInterpolates`, `longButSplittableMoveStillInterpolates` (500 of 999 hops re-split), and `deltasStayEncodable`.
- **`EmbroideryPoint.init(converting:)` is failable**, implemented as `Int(exactly: javaRound(value × 2))` — one expression rejecting non-finite and out-of-range with no hand-maintained bound. Failable rather than a predicate a caller must remember, so the trap is unrepresentable at the type level. The *difference* conversions instead **saturate to `Int.max`**: their result is only ever compared against a threshold, so "cannot be converted" and "farther than any threshold" are the same answer, and saturating keeps ADR-015's opposite-argument-order clause distances working unchanged.
- **Rejection is a guarded no-op in the ADR-014 shape, never a clamp.** `EmbroideryStream.append` guards *above* the flag reads, so a dropped stitch leaves armed jump/color-change flags pending for the next surviving stitch (the contract dedup already has) and leaves `lastStagePosition` pointing at a coordinate that was actually stitched. That last part is forced by the encoder, not chosen for symmetry: `DSTFile` builds every record from the last *appended* position, so re-anchoring on a dropped point would measure the next move from one coordinate and encode it from another — reintroducing the unencodable delta at the next stitch. Dropping and re-anchoring are not interchangeable here. Clamping would put the needle somewhere never asked for and keep it there.
- **A move too long to interpolate emits nothing**, bounded at 1,000,000 splits — the same number and the same reason as ADR-014's `maxStitchesPerUpdate` (12.1 metres, three orders of magnitude past the 500-point stage). This trap is *created* by the conversion bound above: once coordinates near the `Int` limit are accepted, a distant second stitch would make `addInterpolatedStitches` append until it exhausted memory, which is no better for a caller than the crash this ADR closes. Running the cap before the interpolation arithmetic is also what keeps that arithmetic inside `Int`.
- **ADR-019 screening, stated rather than measured**: US-210's inputs sit *deliberately on* the ±121 threshold — that is the story's subject, not an accident to be given margin. The boundary cases are pinned by name in `InterpolationTests` and the golden byte tests stay green untouched, which is the evidence that only the broken side of the boundary moved.
**Consequences**: No caller — interpreter, pattern manager, or direct stream user — can crash or hang the engine with any `StagePoint`, and the interpreter inherits that without a guard of its own (it still reports the stitch as an event; the engine decides what is machine-representable). `DSTFile.swift`'s known-trap comment and the README's interpolation caveat, both open since M1, are retired. Callers of `EmbroideryPoint(converting:)` now unwrap; the four in-repo test call sites use `try #require`.

**The pattern manager's replay must ask before arming.** The manager decides flags at command time and the stream converts at replay time, so an emission the stream rejects has already called `addColorChange()` — and the stream-global armed flag then rides the *next* surviving append, which with actors interleaved on one layer is a different actor's stitch. Actor A's colour change landing on actor B's record contradicts ADR-015's "the actor's next surviving stitch" outright, and it is not something the stream can fix from inside, because by then the flag has no owner. `assembled()` therefore asks `canAppend` first and skips a rejected emission whole — no flag, no count. Found by Codex US-210 round 1 and reproduced exactly (`CO` was 3 where 1 is right, and B's stitch carried both A's change and a stray jump); the first version of this ADR claimed rejected emissions preserve pending state, which was true of the stream in isolation and false of the replay.

Two artifacts are accepted rather than fixed. `hasValidPattern` counts *recorded* ops, which the replay may reject, so a manager holding only unconvertible points reports a pattern while assembling an empty stream; nothing promises the two agree, and a future export path gating on it would offer an empty design as exportable — characterized by `rejectedOnlyPatternAssemblesEmpty` and left for whoever wires up export to decide (Codex US-210 round 2). And a colour change armed for an actor whose next stitch is then rejected is *lost*, not deferred, because the manager cleared its own pending bit at command time and cannot know the replay will drop the point. Under-counting is the right failure direction here — the record would otherwise have to attach to a stitch that does not exist — and `CO = changes + 1` keeps matching what was actually emitted. Separately, once an enormous but representable coordinate has been stitched, every later point beyond the 121,000,000-unit reach is dropped, so a single adversarial coordinate can swallow the rest of a design; the alternative is a tighter *product* envelope on accepted coordinates (e.g. the ADR-007 stage bounds), which US-210 explicitly declines by pinning that a coordinate just inside the conversion range still stitches, and which belongs with the serialization-bound work below.

**Not closed, and now the next reachable crash on this path**: `DSTHeader.appendField` preconditions on field width, so extents beyond 9999 units (4-wide `+X`/`−X`/`+Y`/`−Y`, reachable at stage x = 6000) or more than 999,999 stitches (6-wide `ST`) trap when `DSTFile` is built — far more ordinary than anything this ADR guards, and neither created nor worsened by US-210: `addStitch(0,0)` then `addStitch(6000,0)` blows the `+X` field today with no extreme coordinates involved. Left open deliberately, as a *serialization* chokepoint with different semantics — a header field cannot be a no-op, so the choices are clamping the extent and emitting a wrong header, making `DSTFile.init` failable or throwing and rippling that through every golden call site and the M3 export path, or bounding the stage at the app layer per ADR-007. That belongs with the export story, not inside a coordinate-conversion chokepoint. Specified as *US-211 — DST serialization field-width chokepoint* in `docs/user-stories/backlog.md`, unscheduled (M3 candidate, where the export path forces the decision). Two of the fields are confirmed reachable by execution — extents at stage x = 6000 and `CO` at 100 colour blocks — and a third may be coupled to this ADR's own cap: a move of 121,000,000 units emits over a million stitches, which would overflow the 6-wide `ST` field, so the cap may want to be 999,996 rather than a round million. That is US-211's to confirm. Incidental correction while measuring it: ADR-014's parenthetical "DST's stitch-count header field itself caps at seven digits" is off by one — `DSTHeader.swift` writes `ST` at width 6, matching Catroid. The 1,000,000 bound that parenthetical justifies is unaffected.

**Update (2026-08-04, M3 planning)**: US-211 is scheduled as an M3 story and its option is decided — both `DSTFile.init` and `DSTHeader.init` become throwing (ADR-025 pins it at close-out). Three things this paragraph got wrong or missed, corrected rather than edited away: (1) it lists only `DSTFile` as the trapping entry point, but **`DSTHeader.init(stream:name:)` is public too** (`DSTHeader.swift:13`) and traps independently — 33 call sites in total (19 `DSTFile(stream`, 14 `DSTHeader(stream` in checked-in Swift), not the `DSTFile`-only ripple implied here. (2) The `ST` case is no longer "may be coupled" — it is **confirmed by execution**, and the cap move emits **2,500,003** stitches rather than the ~1,000,003 derived here, because intermediates re-split. (3) The suggestion that "the cap may want to be 999,996" is **declined**: once `init` throws, `ST` overflow is a handled error, so the cap need not protect the header, and changing it would alter interpolation emission for moves the engine admits by design. Also newly load-bearing for the decision: the ADR-007 stage bounds this paragraph offers as an alternative **do not exist as code**, and inside that stage the maximum extent is 1000 units — so bounding coordinates would close only the trap already out of reach while leaving `CO` and `ST`, which are reachable inside the stage.

**Closed (2026-08-25, US-211 — see ADR-025)**: the field-width chokepoint this paragraph left open is fixed; both initializers throw, and the paragraph above is now history rather than an open item. Three of its statements are superseded and worth naming, because each was reasoned from something real. Its speculation that "the cap may want to be 999,996" is **declined**, with the opposite pinned: once serialization throws, `ST` overflow is a handled error and interpolation emission must not change to guard it. Its derivation that the cap move emits "over a million stitches" is **2,500,003** — intermediates re-split. And its framing of the three options as "clamping, failable/throwing, or bounding at the app layer" understated the ripple in one direction and overstated the alternative in the other: the ripple was **41 call sites**, not the `DSTFile`-only one implied by listing a single trapping entry point, while bounding at the app layer turns out to close only the trap already out of reach (the asymmetry ADR-025 pins).

## ADR-021 — M3 app-layer preview data path: colour-resolved stitch events into an append-only display list (2026-08-04)
**Context**: M3 must render stitches live as the interpreter produces them. `InterpreterEvent.stitch(actor:position:layer:)` carries no colour — colour arrives out-of-band as `.colorArmed(actor:hex:)` — while `assembledStream()` returns `[Stitch]` with colour already resolved. Three data paths were possible and they are not equivalent. The enum's own doc comment marks the embroidery payloads "provisional — chosen to carry what US-206's producers will need"; M3 is the first real *consumer*.
**Decision**: `InterpreterEvent.stitch` gains `color: ThreadColor`, supplied by a new public read-only `EmbroideryPatternManager.threadColor(for:)`. The app accumulates events into an append-only `StitchDisplayList` with incrementally maintained colour runs, bounds, and a `settledCount` rasterisation watermark; `assembledStream()` is called **once per run**, for the export model only, and is carried on the terminal batch. `.colorArmed` is unchanged and no preview code path consumes it.
**Consequences**: The engine keeps sole ownership of ADR-015's colour semantics — the app performs none of the silent-start, invalid-hex, clause-B-black or `==121` reasoning. The producer change is two lines and order-insensitive, because `addStitch` captures `colorState.current` before mutating and only clears `pendingChange`. ADR-016's DAG is unaffected: `InterpreterEvent` already imports `EmbroideryEngine` and already carries `ActorID`/`StagePoint`/`NeedleUpdate`.

Rejected, with reasons worth keeping because the obvious one is wrong. **Rendering from `assembledStream()` per frame was measured, not assumed: 0.64 ms at 50k stitches in release (0.17 ms at 10k, 0.023 ms at 1k) — i.e. affordable.** *(Corrected 2026-09-01, US-309.* The original sentence continued "roughly 10% of a frame on A15-class hardware". **Both halves of that were wrong.** The numbers are **Mac** numbers, taken in a release build on an M-series machine at planning time, and the sentence did not say so; and 0.64 / 16.67 is **3.8%** of a frame, not 10%, so the figure silently applied an unstated ~2.6× Mac→A15 extrapolation on top of an unstated platform. Re-measured on the same class of machine during US-309: **0.526 / 0.102 / 0.039 ms** — the same shape. **The device counterpart was struck on 2026-09-02 rather than taken, because the device measurement made it unnecessary.** US-309 measured the shipped renderer's mid-gesture path at **69.1 ms per drawn frame** at 50 000 stitches — roughly **100×** the 0.64 ms that rebuilding from `assembledStream()` would have cost. So this ADR's actual point is now made *more* strongly than a device `assembled()` figure could make it: option B was not merely affordable, it is two orders of magnitude cheaper than the design that shipped, in the one case that fails the 60 fps bar. Rejecting it on prefix stability rather than on speed was correct, and "O(n) per frame is too slow" would have been the wrong reason by a factor of a hundred. **This ADR therefore claims a Mac measurement and nothing about an A15, deliberately and finally.** The decision itself is unaffected, because it never rested on the speed — see the structural argument below, which is the actual reason.)* It is rejected on *structure*: `assembled()` iterates `layerOps.keys.sorted()` and emits layer boundaries lazily, so for a **multi-layer** program a new stitch inserts into the middle of the returned array. That forecloses ADR-009's "settled stitches rasterized to a cached image, only the live tail redrawn", which requires an immutable prefix. For a single-layer program the prefix *is* stable — the point is not to make the architecture depend on never having a second object, which the M2 model and M4/M5 both allow. So do not record "O(n) per frame is too slow" as the reason; it isn't, at our scale. Catroid's `DSTPatternManager.getEmbroideryPatternList()` does exactly this and it is that codebase's worst performance bug, but the cost there is a Java object allocated per point per frame on mobile, not the algorithm shape alone. **Tracking colour in the app** was rejected because it duplicates ADR-015 in a second place, which the M2 rule forbids one layer down; Catty demonstrates the concrete failure — its per-batch colour reset mis-colours the batch-boundary seam.

Accepted divergence: the display list is built from *ops*, the export model from the *replay*, so their record lists differ in three places — clause C/D re-emits and interpolation intermediates are duplicates or on-segment points, so those leave the drawn path identical and differ only in record sequence. **Clause B is stronger than that and the first version of this ADR understated it** (Codex round 1): when an actor changes on a layer, `addStitch` emits **two** points at the *previous* actor's workspace position in explicit black (`EmbroideryPatternManager.swift`, clause B — both unconditional; `isFar` decides only whether the second arms a jump). Those two records have **no counterpart in the display list**, so for a multi-actor design whose incoming actor is not itself black, the export model carries black where the preview carries the incoming actor's colour — a difference in **colour**, not merely in record order. (Stated this way deliberately: an earlier wording said black "never appears in the display list", which is false — `ColorState.current` defaults to `.black`, so an actor that never set a colour emits black stitch events. Codex round 2.) Scope of the consequence: M3's bundled samples are single-object, so no M3 user sees it, and the app still implements none of ADR-015 — the preview simply does not show the machine's transition. Corrected here rather than silently, because "the drawn path is identical" would have been re-read later as a guarantee. US-302 owns the multi-actor test that pins the actual difference. Catroid needed `EmbroideryExportIsolationTest` for the same separation.

**Correction (2026-08-09, US-302 / Codex round 2): the divergence list above is incomplete — there is a fourth, and it needs only *one* actor.** This ADR enumerates clause C/D re-emits, interpolation intermediates and clause B. It omits **clause A, workspace dedup**. `Interpreter+Step.emitStitches` emits one `.stitch` event per `addStitch` **call** — documented since M2 ("the event count reflects calls, not surviving stitches") and deliberate, because the event is the trace of what the program asked for and is what US-306's stitch budget counts. But clause A drops an identical consecutive command from the same actor, so the export has no record where the display list has an entry. Reproduced exactly: `setThreadColor(red)` → `stitch (0,0)` → `setThreadColor(green)` → `stitch (0,0)` → `placeAt(1,0)` → `stitch` gives a display list of `[red, green, green]` against an export of `[red, green]`. The drawn *path* is unaffected — the extra entry sits on the position the previous stitch already occupies — but the colour-run boundary moves one entry earlier when a change is armed across the dedup, so the preview shows the new colour one stitch before the machine does.

**Not fixed in the app, and that is the decision rather than an omission.** Filtering deduped events preview-side would put ADR-012's clause A into the app layer, which is precisely what this ADR exists to prevent; suppressing the event in the interpreter instead would require `addStitch` to report whether it emitted, breaking the M2 event contract and the golden event tests, and would cost US-306 the call-count its budget is sized against. The divergence is pinned by `clauseADedupIsAFourthDivergence` in `StagePreviewTests`. It also explains why US-302's square-coil colour-sequence test asserts `displayList.count == stream.count` as a **precondition**: that sample contains no deduped command, and without the precondition the equality would be accidental agreement rather than the invariant it looks like.

**And a fifth (2026-08-09, US-302 / Codex round 3): ADR-020 rejection.** `emitStitches` publishes the `.stitch` event unconditionally, while `assembled()` asks `canAppend` first and skips whole any recorded op the stream would refuse — so a coordinate that is unconvertible or unreachable by interpolation is **drawn but never stitched**. `stitch` at the origin, then `placeAt(1e300, 0)` and `stitch`, gives a display list of two entries against an export of one. This is the largest of the five gaps: the others shift a colour or duplicate a point, this one puts a stitch on screen that the machine will not make. It is also already anticipated on the export side — the M3 design gates export on the post-replay `assembledStream().count > 1` rather than on `hasValidPattern` precisely because ops can be recorded and drawn while every one is rejected at replay — so what was missing was only its statement *here*, as a display/export difference rather than an export-gating one. Pinned by `adr020RejectionIsAFifthDivergence`.

**Two more, and then a decision to stop counting (2026-08-09, US-302 / Codex round 4).** **Six**: the assembler's *inter-layer boundary*. On the first surviving op of a later layer, `assembled()` emits a colour change and a jump, each re-emitting the previous layer's last point — two export-only records with no display counterpart, produced by none of the other five mechanisms. **Seven**: *ordering*. `assembled()` replays `layerOps.keys.sorted()`, so the export is ordered by layer while the display list keeps interpreter execution order; for a program whose upper layer stitches first the two are genuinely reordered, not merely padded. That seventh is the concrete form of the structural argument this ADR already used to reject per-frame `assembled()` — a new stitch landing mid-array is exactly what forecloses ADR-009's immutable prefix — so it was implicit in the decision from the start and simply never written down as a *divergence*. Both are pinned by `layerBoundaryIsASixthDivergence` and `layerOrderingIsASeventhDivergence`.

**The enumeration was wrong three times, so it stops being the authority.** This ADR shipped naming three divergences; review found a fourth, a fifth, then a sixth and seventh. The list kept growing because it was written from the mechanisms its author happened to have in mind, which is not a way to enumerate anything. **The rule below is normative; the list above is illustrative and should be assumed incomplete.**

> **The display list is the trace of what the program asked for. The export model is the trace of what the machine will do.** They coincide only for a single-object, single-layer design with no dedup, no rejection and no interpolation — which is exactly what M3's bundled samples are, and why M3 shows no visible difference. Anywhere else, expect them to differ, and do not write a test that assumes agreement without asserting the preconditions that make it true.

The preview is a preview of the *program*, not of the file. A future story tempted to make the two agree should change this ADR first — and note that making them agree would mean either re-implementing ADR-012's clauses in the app or rendering from the replay, both of which this ADR rejects on the record.

**Confirmed in implementation (US-302, closed out 2026-08-11)**: `InterpreterEvent.stitch` carries `color:`, `EmbroideryPatternManager.threadColor(for:)` is public and read-only, and `StitchDisplayList` maintains colour runs, bounds and `settledCount` incrementally with `append` documented O(N). Three things the eight review rounds decided that this ADR should carry forward, because each is a place a later story could quietly undo it:
- **The divergence list was demoted from authority to illustration *during* review**, after growing 3 → 7. That demotion is the durable part of this ADR; the seven items are not.
- **The display list is deliberately not `Hashable`**, and `liveTail`'s `ArraySlice` must not be stored across an append — holding one makes the buffer non-uniquely referenced and turns the next append into a full copy, silently breaking the O(N) this ADR's per-frame argument rests on. US-305 would have violated it by construction; `withLiveTail(_:)` exists so it cannot.
- **`reserveCapacity` in `append(contentsOf:)` was removed as a pessimization, measured, not argued** — 96 reallocations against 13 without it, plus a full buffer copy on every *empty* batch (routine: a `wait` brick yields one). A later story re-adding it should re-run the measurement first.
The `.colorArmed` case is unchanged and no `StagePreview` code path reads it, so the app performs none of ADR-015's reasoning — asserted by `RunBatch.reducing`'s exhaustive switch with no `default:`, which makes a future event case a compile error rather than a silent drop.

## ADR-022 — M3 target layout: `Samples` and `StagePreview` as app-support targets in the engine package (2026-08-04)
**Context**: M3 needs bundled sample programs and a display-list/transform layer. No sample builder exists in any library target — they live only in test targets, and SwiftPM forbids a test target depending on another test target. The M3 exit criterion "zoom/pan transform math is unit-tested" then decides where that math lives: inside the SPM package it runs under `swift test` and the existing pre-commit gate; inside the app target it needs a simulator.
**Decision**: Two new targets and products in `Packages/EmbroideryEngine`: `Samples` (depends on `ProgramModel` **only**) and `StagePreview` (depends on `Interpreter` + `EmbroideryEngine`, **Foundation-only** — no SwiftUI, no CoreGraphics; transform math is `Double`-based and the app adds a small `CGAffineTransform` adapter). Sample content is Swift builders as the single source of truth, with a checked-in JSON encoding shipped alongside as a resource and guarded by a `decode(resource) == builder()` test.
**Consequences**: The package grows from **three library targets to five** (products likewise three → five; counting test targets, six declared targets become eight or more) and stops being purely "the engine" — accepted, because the alternative moves an exit-criterion test behind a simulator boot. (An earlier wording said "four targets to six", which matched neither the library count nor the declared total; Codex round 1.) The display list, transform math and event reducer stay on the fast gate. M5 inherits the samples as JSON (ADR-003 already pins JSON as the project format) instead of redoing them, and a `formatVersion` bump fails a test rather than silently rotting a resource. `StagePreview.StageGeometry` puts ADR-007's 500×500 stage into code for the first time; its doc comment must state that it does **not** bound engine input, since nothing bounds a `StagePoint` and a design may legitimately leave the stage.

**Confirmed in implementation (US-302, closed out 2026-08-11)**: both targets and products exist, the package is at five libraries and 489 engine tests, and `Sources/StagePreview/` imports Foundation only — pinned by a `StagePreviewTargetIsolationTests` rather than left to review. The Foundation-only rule paid for itself immediately: every acceptance criterion of the milestone's load-bearing story, including the exit-criterion transform math, was verified under `swift test` with no simulator, on a branch whose app target still does not build. **The `CGAffineTransform` adapter this ADR anticipates is still owed by US-305** — `StageTransform` deliberately ships `viewPoint(of:)`/`stagePoint(of:)` over its own `ViewPoint`/`ViewSize` value types instead.

## ADR-023 — What runs where: the local gate protects engine semantics, the app target's protection is CI's (2026-08-11)
**Context**: Until US-303 the app layer was **entirely ungated** — the PreToolUse commit hook and `ci.yml` both ran only `swift test` on the engine package, and the app target was the untouched Xcode template linking none of the five products. US-303 links them and adds the first app code, so both gates have to be told what the app is. The question is not "should the app be tested" but *which gate owns which failure*, because the two have very different costs: the engine's `swift test` is 1.4 s for 489 tests with no simulator, while anything that boots a simulator costs tens of seconds and would fall on every commit in a project whose whole process rests on a small-commit cadence.
**Decision** (Sebastian, 2026-08-11, US-303):
- **The local pre-commit gate compiles; it does not run the app.** It keeps `swift test` engine-only and unconditional, and *adds* a signing-free `xcodebuild build-for-testing -destination 'generic/platform=iOS'` with a persistent `-derivedDataPath` outside the repo, **conditioned on the working tree holding any change under `catrobat_embroidery_ios/`**. `build-for-testing` rather than `build` — a one-word deviation from the story's literal command, worth 0.9 s — because it also compiles the *test* target, which is exactly where red-phase code lives. A simulator boot in a pre-commit hook is **rejected outright**: it would cost the cadence the process depends on, and it buys only what CI already provides.
- **Therefore the local gate cannot catch a runtime failure, and that is a stated limit rather than an oversight.** A test that compiles and *fails* still commits locally; CI is what stops it reaching `main`. The asymmetry is deliberate and follows from what each layer protects: the engine's byte-level DST semantics are pinned by golden tests that must never regress even for a minute, so they run on every commit; the app layer's failure modes are layout, navigation and wiring, which a human sees in the simulator and CI catches before merge.
- **The local gate is a convenience, not an enforcement boundary — CI and branch protection are.** This distinction is load-bearing and took three review rounds to state correctly. A `PreToolUse` hook sees the *command text*, so its classifier is a heuristic over a string, and no regex can survive shell expansion: `g=gi; g+=t; c=com; c+=mit; "$g" "$c" -m normal` runs a real commit while containing neither word. Earlier drafts of this ADR claimed the gate "fails closed, never open"; that is **false as stated**, and the correct claim is narrower — *within the command forms anyone actually types*, it prefers blocking to passing. What genuinely cannot be bypassed is the required-status-checks ruleset on `main`. Anyone wanting to skip the local gate can simply write `[red]`; the gate exists to catch mistakes, not to resist its own user.
- **The gate does not parse the command. It asks the repository.** Whether the app check runs is decided by `git status --porcelain -- catrobat_embroidery_ios/` — *any* change under the app directory, staged or not — and by nothing else. This replaced five rounds of increasingly elaborate flag parsing, and the decision to abandon parsing is the durable part of this ADR.

  **The evidence, because it is the most transferable result of this story.** Five consecutive Codex rounds attacked the classifier and every one found a hole *in the previous round's fix*: `git -C <dir> commit` was unrecognised; bounding the gap with `[^;&|]*` missed `git -c note='a;b' commit`; `[red]` was honoured from a staged path like `catrobat_embroidery_ios/[red].swift`; `git commit -m msg -- <pathspec>` and `--only` bypassed the check entirely; then the quote-stripping written to fix *that* merged an apostrophe in `-m "Don't"` with a later quoted path and swallowed `--only` again, while `-o` and `--interactive` were still unenumerated. Severity ran Medium → Medium → High → High → High: **the loop did not converge, because each fix enlarged the surface it was defending.** A regex over a command string cannot decide what `git commit` will include — the flags are open-ended (`-a`, `-i`, `--include`, `-o`, `--only`, `-p`, `--patch`, `--interactive`, a bare or `--`-introduced pathspec), quoting is ambiguous, and shell expansion can hide the command entirely.

  Asking the working tree has none of those failure modes, because it asks the only question that actually matters: *is there app code here that does not compile?* Every reproducer from all five rounds becomes moot rather than fixed.

- **The cost is real and accepted: an engine-only commit is blocked while the app is broken on disk.** That behaviour was deliberately allowed before (proven by test, and documented here) so engine work could continue mid-refactor. It is given up because the alternative is a check with holes in it, and a gate that is sometimes silently absent is worse than one that is occasionally inconvenient. Escape hatches: finish the change, stash it, or mark the commit `[red]`. The marker is now a plain substring test on the command — no extraction, no `sed` — since with parsing gone there is nothing left to protect it from, and anyone who wants to bypass their own pre-commit hook can already do so. A missing `xcodebuild` **blocks** rather than skipping — the guard exists so the failure is legible, not so the check is optional.
- **Two limits of the working-tree condition, both accepted rather than fixed.** A Swift file hidden by `.git/info/exclude` is invisible to `git status` yet still compiled by the synchronized folder group, so a *locally excluded* broken file skips the check — accepted because such a file is never committed, cannot reach CI, and its author already sees their own build failing. And `git status` failing is now treated as a **block**, not as a clean tree: an unreadable working tree is indistinguishable from an empty one, and the earlier version silently skipped the compile in that case.
- **Every `xcodebuild` invocation names `-project` explicitly.** GitHub Actions starts at the repository root and the project is nested, so a bare `-scheme` finds nothing and fails before reaching a test.
- **The shared scheme is a checked-in build input, and CI asserts its presence before building.** `.gitignore` excludes `xcuserdata/`, where Xcode autocreates schemes, so a fresh checkout has no scheme unless `xcshareddata/xcschemes/` is committed. The explicit guard step exists so that failure reads as one line instead of an obscure xcodebuild error.
- **The "no hardcoded user-facing strings" check is a SwiftLint custom rule, not a test.** Forced, not preferred: app tests run sandboxed in the simulator and cannot read repo sources, so no Swift test can see a literal in a view file. The rule is a *backstop* — the real guarantee is that every string goes through a generated `LocalizedStringResource` symbol, where a typo is a compile error.
**Consequences**: The app layer is gated for the first time, at a measured cost of **2 s incremental / 5 s cold** on top of the engine's 1.4 s — far under the ~30 s threshold US-303 set for dropping the check. (The story's 9.3 s estimate was measured *before* the five products were linked and proved pessimistic, not optimistic.) Behaviours proven by execution rather than assumed: the gate allows a healthy app, blocks a broken one with the compiler's own error line, blocks when `git status` cannot be read, and is skipped entirely by a `[red]` marker. **The third of the original four — "does not fire when only an engine file is staged even with the app broken on disk" — was deliberately given up in the redesign**; it was the behaviour that required parsing the command, and parsing is what would not converge. One scar worth keeping: the first version of the hook nested a `case` inside `$( )`, which does not parse in `sh` and broke **every** Bash call in the session until it was rewritten with a flag variable — a hook is code, and a hook that fails closed takes the whole tool with it.

**The app target's isolation defaults differ from the package's, deliberately.** The app builds with `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` and `SWIFT_APPROACHABLE_CONCURRENCY = YES` — the scaffold's own settings, and already ADR-006's shape — while the package stays nonisolated, synchronous and `Sendable` (ADR-016). The consequence to remember: **a type moved from the package into the app silently becomes main-actor isolated.** That is the right default for view models and the wrong one for anything the engine would call. It has already bitten once: `AppRunClock` needed an explicit `nonisolated`, because without it US-306 gets *"main actor-isolated static property 'preview' can not be referenced from a nonisolated context"* the moment it steps the interpreter off the main actor — which it must, since one `step()` can emit millions of events. **App-layer constants the engine path touches are `nonisolated` by default; view models are not.**

**The setting also reaches the app *tests*, which therefore do not run in parallel.** CLAUDE.md's "tests run in parallel: no shared mutable state or fixed file paths" was written for the package, where it is true. App tests inherit `MainActor` isolation from the project and are effectively serialized. No correctness consequence at this size, and no attempt is made to fight it — recorded so a later author does not read a passing app suite as evidence that it is parallel-safe.

**ADR-010's adaptive layout is a container *swap*, and a size-class change therefore discards navigation state.** `RootView` chooses `NavigationStack` or `NavigationSplitView` on `horizontalSizeClass`, so resizing an iPad window across the boundary (Split View, Slide Over, rotation on a smaller iPad) destroys one container and builds the other empty — the user lands back on the list. Accepted **only** at skeleton fidelity, where the sole destination is a placeholder and nothing is lost but a scroll position. It stops being acceptable at US-304, which introduces a selection worth losing, and the fix belongs there: hoist the selection and the navigation path into an `@Observable` view model owned above `RootView`, so both containers read one state instead of each owning their own. Recorded because the alternative — noticing it later — reads as a bug in ADR-010 rather than as a deliberate staging of it. (Found by the cross-vendor review; the first version of this ADR omitted it.)

**Two traps found during the human Xcode hand-off, recorded because neither is discoverable from the outcome.** (1) Setting `SWIFT_VERSION` at *project* level does nothing while the template's *target*-level `5.0` shadows it — the app would have compiled as Swift 5 while every document claimed 6, which is precisely the ADR-006 violation the step existed to close. (2) `INFOPLIST_FILE` plus a synchronized folder group is a build failure by default (`Multiple commands produce … Info.plist`): the plist is both copied as a resource and processed, and the target-membership checkbox in the save sheet does not stick for synchronized folders — it needs a membership exception set afterwards. Both were caught by reading `project.pbxproj` after each step rather than trusting the UI.

## ADR-024 — The stage renderer: batching hoisted out of the renderer, and the deviations from both references (2026-08-13)
**Context**: US-305 turns ADR-009 into code. Both references get stage rendering wrong in instructive ways — Catty creates **two `SKShapeNode`s per stitch** as direct scene children with no batching and no removal path (`CBSpriteNodeEmbroideryExtension.swift:55-77`; `stitch.isDrawn` only *marks*, nothing is ever removed), while Catroid batches its draw calls well but rebuilds the whole export model every frame. The story also carried an unbuildable test plan and a misdescribed geometry constant, both found in planning.

**Decision**:

- **The batching is a value, not renderer logic.** `StitchDrawPlan` — computed in `StagePreview`, an ordered list of `{style, colour, member segment indices}` — is what the renderer merely strokes. This was forced, not preferred: four of the story's test items asked to be asserted "through the recording renderer double's path list", and a double conforming to `StagePreviewRenderer` records that protocol's *inputs*, so it never has a path list. The alternatives were a `GraphicsContext` spy (which the first criterion forbids, because a context in the protocol defeats the Metal escape hatch) or a double that re-implements the batching (which asserts the double). Consequences beyond testability: the plan holds **indices, never geometry**, so it is transform-free — a pan or zoom cannot invalidate it — and it *cannot* retain an `ArraySlice` across an append, making the violation ADR-021's close-out predicted ("US-305 would have violated it by construction") unrepresentable rather than merely avoided. ~20 assertions on the milestone's load-bearing logic run on the fast gate instead of behind a simulator boot.
- **`.suppressed`, not `.none`.** `Optional.none` shadows a case of that name in every optional context, so `let style: StitchSegmentStyle? = .none` would compile and mean "no style".
- **The bridging segment at the watermark.** The watermark splits *stitches*; a segment joins two, so segment `(k−1, k)` straddles it. The bake draws strictly inside its window and the live pass **starts one segment earlier**. Sound because the display list is append-only *per element*, not merely per prefix: stitch `k−1` can never change, so redrawing its outgoing segment every frame is safe, and the bake picks it up when the watermark passes. The story's item 5 asked for the literal "drawn set is exactly `stitches[k...]`", which is true of the dots and would have rendered a **permanent one-segment gap** in the thread at every advance.
- **One stroking function for both layers.** `Image(size:renderer:)` (`@available(iOS 16.0)`, verified in the SDK interface) and `Canvas` both yield an `inout GraphicsContext`, so settled and live pixels come from identical code. Two implementations would differ at the seam in cap shape, width rounding or alpha, and no unit test would catch it. The bake captures `Array(prefix)`, an explicit copy — ADR-021 measured that as the *cheaper* option, since an escaping closure holding the list's own storage leaves it non-uniquely referenced for the raster's whole lifetime.
- **The raster key excludes the colour scheme.** A real payoff of the dark-mode rule rather than an oversight: nothing inside the canvas changes when appearance does, so the cache survives the switch.
- **The fitted transform is constant for any in-hoop design**, because `fitTarget` always contains the 500 × 500 hoop. So a normal run never refits and the settled raster is never invalidated by a zoom the user did not ask for. Only an out-of-hoop design pays for re-baking.

**Deviations from both references, each deliberate:**
- **Traversals are drawn distinctly** (fixed chrome colour, 1 pt constant width, dash `[3,3]`, α 0.6 → 1.0 under Increase Contrast) where both references draw travel as solid thread indistinguishable from stitching. The colour is chrome and **not the run's colour dimmed**: measured, `#f59e0b` at 45% over the stage field is ~1.2:1, and no single opacity works across every hue. The principle underneath is that **the machine trims travel, so travel is not design data** — which also collapses the contrast question to one provable pair. The dash is load-bearing, not decorative: opacity and width are exactly what Increase Contrast undoes, so a *shape* difference is what keeps travel distinguishable for low-vision users.
- **Every display-list entry is dotted**, including both endpoints of a traversal. Catroid skips dots on jump and colour-change points (`isConnectingPoint`), but those are *synthetic records in the export model*; the display list has no synthetic entries, so there is nothing to exclude. A record-model difference, not an appearance one.
- **Dots on top, after every stroke.** Catroid interleaves circle and line in stitch order (`EmbroideryActor.kt:66-74`), which lets a later colour run paint over an earlier run's penetration points.
- **Colour-run boundaries suppress the segment**, which is *not* Catroid parity: Catroid's latch resets at the next connecting point and draws a black connector across clause B's transition. Our display list has no black transition point to hang one on, so drawing anything would imply continuous thread across a swap the machine stopped for.
- **No needle indicator** — greenfield, and US-306's to design.

**`BrickValues.STITCH_SIZE = 3.15`, corrected. The story's criterion misdescribed both references in three ways and each was checked at the source before being rewritten**: (a) the ratio is **inverted** — both compute *project ÷ device* (`StageListener.java:1015`, `Catty/.../EmbroideryStream.swift:63`); (b) Catty applies a further `sizeConversionFactor = 0.634` **and** keeps a separate dot radius `stitchingCircleRadius = 3.0` (`SpriteKitDefines.swift:49`), so "dot radius and thread width are the same value" is **Catroid's** rule alone; (c) "never recomputes on rotation" is the wrong indictment, since `UIScreen.main.nativeBounds` is orientation-independent — the defect is deriving the size from the *device* at all. On the units: 3.15 is a **device-pixel** constant converted to virtual-stage units by `screenRatio`, and because `DSTFileConstants.java:56` pins Catroid's `STITCH_POINT_UNIT_FACTOR = 2f` — the same factor ADR-007 pins — one Catroid virtual unit *is* one of our stage points, so at ratio ≈ 1 the ported value is 3.15 stage points = **0.63 mm of fabric**. And the consequence, because "the same value" reads as "the same visual width": **a dot's diameter is twice the thread's width** (1.26 mm against 0.63 mm). That beading is Catroid's look and is what makes penetration points read as points — do not "fix" it.

**The dark-mode rule needed narrowing, and the literal criterion is unimplementable.** The story says thread colours must not adapt (they are design data) and "only stage chrome is semantic-coloured". The second half cannot be built: chrome drawn *on top of* a fixed stage field must be fixed too, or a semantic hoop outline over fixed light paper is a light line on a light field in dark mode. The rule that ships:

> **Inside the canvas, everything is fixed. Outside the canvas, everything is semantic.**

"Contrast checked in both appearances" then becomes a *proof of invariance* inside the canvas plus a real two-appearance check only at the canvas/pane seam — confirmed by the screenshots, where the canvas is pixel-identical across appearances and only the pane chrome darkens. A **fixed neutral field is also the only way the thread rule can be honoured at all**: an adapting field would make the *same* design legible in one appearance and invisible in the other. A mid-grey field — the intuitive answer to "keep black and white both visible" — was rejected on measurement: against the shipped square-coil palette it drops `#1d4ed8` to ~2:1 and `#f59e0b` to ~1.6:1, punishing realistic saturated threads to buy two synthetic extremes. Against the light field black (`ColorState`'s default, so the commonest thread) is ~14.6:1. **No grid ships**; nothing asked for one, and it would be confusable with the dashed travel hairline.

**Consequences**: `StagePreview` gains four types and stays Foundation-only, pinned by an extended isolation test that binds the new API to explicit function types so a `CGFloat` on the boundary is a compile error. CoreGraphics enters the app in exactly one file, whose `affine` necessarily re-spells ADR-007's single y-flip as `d: -scale` — pinned differentially against `viewPoint(of:)` rather than trusted, since two spellings of one rule is where a later edit fixes one and forgets the other. `StagePlaceholderView` is deleted. **Two known limitations, both stated rather than left to be found**: the thread-contrast casing is deferred (a fixed field makes contrast invariant, which is what the criterion actually requires; threads within 3:1 of the field are low-contrast until US-307 takes it), and **nothing in US-305 advances `settledCount`** — it is US-306's to call — so the raster path is wired and tested but unreachable at runtime, and US-309 tunes `bakingThreshold` from an untuned starting value. Two additions beyond the criteria, both Sebastian's call and recorded in the story: a temporary tick-capped drain in `AppModel` so the renderer can be seen at all (US-306 deletes it), and a hoop-overflow notice, since US-308 gates export on `assembledStream().count > 1` — hoop-independent — and nothing else in M3 reports leaving the hoop, least of all to a VoiceOver user.

**Review outcome (in-loop `swift-code-reviewer`, 2026-08-13): nine findings, three important, all reproduced. Four were real defects and are fixed; the rest are recorded here rather than fixed.**

- **This ADR asserted a behaviour that no code implemented.** The α 0.6 → 1.0 under Increase Contrast above, and the same claim in `StageChrome`, were written from the design spec while `CanvasStitchRenderer` stroked travel unconditionally at 0.6 — `colorSchemeContrast` was read only for the hoop's line width. Now implemented, so the claim is true rather than retracted. Worth recording as a process point: an ADR is an arbiter document, and a plausible sentence in one is *harder* to catch later than missing code, because the next reader takes it as settled. **Second-order consequence the argument above missed**: once contrast is a drawing input, it must join the raster's cache key — the "the raster survives an appearance switch" reasoning covers `colorScheme` and stops covering `colorSchemeContrast`. `BakeKey` now carries it.
- **One non-finite coordinate silently cropped genuinely out-of-hoop content — the exact failure this story's criterion forbids.** `StitchDisplayList.bounds` absorbed a non-finite position (reachable from a legal program: `changeXBy` accumulates without normalising, so two `greatestFiniteMagnitude` steps reach infinity, and ADR-021 divergence #5 draws it anyway), which made `fitTarget` collapse back to the hoop and fitted a stitch 750 pt outside it **off-screen** — silencing the hoop-overflow notice with it. Fixed at the producer: `expand(toInclude:)` skips a non-finite coordinate per axis and `StageBox(finitelyContaining:)` guards the seed, so **`bounds` covers exactly the finite positions** and `union`'s own skip becomes the belt-and-braces it was described as. The lesson is sharper than the fix: the earlier tests hand-built their poisoned boxes, and `expand` **cannot produce the shape they built** — per axis you always got both edges finite or both poisoned. *The union was proven and the path to it was not, and the defect lived in the path.*
- **A latent stale-raster bug that no test could have caught, because the path is unreachable.** `BakeKey` keyed on `settledCount`, which is sound under append-only — but `reset()` breaks that premise, so a US-306 driver switching designs and re-settling to the same watermark in the same viewport would composite the previous design's raster under the new design's live tail. The fitted transform cannot break the tie, precisely *because* this ADR records as a benefit that it is identical for every in-hoop design. `StitchDisplayList` gained a monotonic `resetCount` and `BakeKey` includes it.
- **The raster is blitted into the `Canvas`'s size while rendered at the viewport.** Equal today because the renderer fills the `GeometryReader` that measured it, but nothing said so; a future caller framing the renderer smaller would stretch the settled layer under an unstretched live tail. Now guarded, falling back to `.entire`.
- **Recorded, not fixed** — `union` can return an inverted box through its public API when two operands are poisoned on *different* edges; unreachable via `fitTarget` (the hoop is finite on every edge) and `fitting` is total for it regardless, so it is a stated precondition. `SampleSelection`'s synthesized `==` compared whole `Program` trees on every update pass, since `RootView` keys `.task(id:)` on it — replaced with `(sample.id, generation)`, keeping the generation that makes re-selection a restart.
- **Two things for US-309, both measured claims rather than guesses.** (1) Passing the display list into the view hierarchy by value leaves `AppModel.display`'s buffer non-uniquely referenced, so **the first append after each render pass pays a full copy** — ~1.2 MB per frame at 50 000 stitches, the same number ADR-021 attributes to a retained `ArraySlice`. It is inherent to the protocol these criteria mandate (`display:` by value, held by a view that must redraw), so it is documented rather than fixed; but ADR-021's text implies that cost is avoidable, and here it is paid by the protocol itself. (2) With the watermark pinned at 0, every frame re-plans `.entire` — re-classifying every segment through `requiresTraversal` and rebuilding every `Path`. Invisible at the samples' 2 976 records; not invisible at 50 000.
- **Open question for US-306's first real settling**: at what scale does `Image(size:renderer:)` rasterise? If 1× rather than the display scale, the settled layer will be visibly softer than the live tail — a seam at the watermark, which is the class of defect the shared stroking function exists to prevent. One screenshot answers it; it cannot be answered now, because nothing advances the watermark.

## ADR-025 — Header field widths are a serialization error, not a trap; and field emission order is a contract (2026-08-25)

**Context**: `DSTHeader.appendField` ended in `precondition(valueBytes.count <= width)`. Every field is fixed-width, so a value that does not fit killed the process — and three fields are reachable from ordinary user input, confirmed by execution: the 4-wide extents (`+X`/`−X`/`+Y`/`−Y`, over 9999 units, `addStitch(0,0)` then `addStitch(6000,0)` → `+X` = 12000), the 2-wide `CO` (99 bare `addColorChange()` calls → `CO` = 100, **with zero stitches**, so `CO` is the only field over width), and the 6-wide `ST` (1 000 001 stitches alternating 1 unit apart inside a 1-unit extent — the story said 2 units; it is 1). US-210 closed the *coordinate* chokepoint and left this one open deliberately (ADR-020, "Not closed"), because a header field cannot be a guarded no-op the way a stitch can.

**The reachability is asymmetric, and that is what decides the fix.** Inside ADR-007's 500×500 stage the maximum per-direction extent is 1000 units — five times under the 4-wide limit — so extent overflow is only reachable *outside* the documented stage, whereas `CO` and `ST` overflow without ever leaving it. Bounding coordinates at the app layer would therefore close only the trap already out of reach and leave the two that are in reach; it is the wrong shape for the problem, and it would first have to introduce engine-space bounds, since ADR-007's stage exists only as prose. Clamping the extent was rejected outright: it is the one field a machine reads to size the design, so a clamp is corruption we *chose*, and undetectable downstream — ADR-012 refuses parity-with-corruption elsewhere.

**Decision** (Sebastian, 2026-08-25, US-211):
- **`DSTHeader.init` and `DSTFile.init` are `throws`**, with a public `DSTSerializationError.fieldOverflow(field:value:limit:)`. Throwing rather than failable because the export path must name *which* limit was hit ("118 colour blocks; DST allows 99") and `Optional` cannot carry that. Both initializers, not just `DSTFile`: `DSTHeader.init` is public and was an independent trapping entry point — a point ADR-020's own text missed. `DSTFile` was not gaining an error surface for the first time; `write(to:)` already throws.
- **The `precondition` is deleted, not kept as a backstop.** ADR-020 kept `DSTStitchRecord`'s explicitly, as "the programmer-error backstop for anyone constructing a record directly" — sound there, because that initializer is `public`. `appendField` is `private` with exactly one caller, so the analogy does not carry and a retained precondition would be dead code sitting one line from the `throw` that supersedes it.
- **The field table becomes `DSTHeader.Field`** — a `CaseIterable` enum in emission order carrying tag, `width`, `limit` and pad byte, replacing three stringly-typed arguments. It removes the possibility of a tag/width mismatch at a call site, gives the error a field identity that is not a `String`, and gives the export layer a compile-time-exhaustive switch for its localised nouns. `Field` and `Field.width`/`limit` are public API from here.
- **Only the first violation, in emission order, is reported.** Deterministic, and it is load-bearing (below). A design busting both `ST` and `+X` is told about `ST`. Collecting all twelve violations buys nothing: the export path renders one message.
- **Field emission order is a contract, not the byte layout's accident.** This is the ADR's least obvious consequence and the one most at risk of being "tidied". Two guarantees depend on it:
  - **`ST` precedes the extents**, which is what keeps `DSTHeader`'s extent arithmetic unreachable at overflow magnitudes. The extents are raw `Int` subtractions over coordinates ADR-020 deliberately admits up to `Int` range (`box.max.x - first.x` can overflow; `abs(min(…, 0))` can hit `abs(Int.min)`). They are safe only by a two-step derivation nobody had written down: a throwing `ST` check bounds `stream.count` at 999 999 before any subtraction runs, and ADR-020's ≤121-unit-per-axis delta then bounds every per-axis span at 999 998 × 121 ≈ 1.21e8 — eight orders inside `Int`. Corroborated by execution: a stream cannot even hold two far-apart coordinates (at 4.6e18 the lattice step is 1024 units, so ADR-020 refuses the second stitch), and a single stitch converting to exactly `Int.min` builds a header with all extents 0. Move an extent field above `ST` and the overflow becomes reachable. The in-loop review found this contract **half-covered**: reordering the two fields inside `init` fails 29 assertions across 8 golden suites, but reversing all twelve `Field` cases passed the entire suite — the *enum's* declaration order, which this ADR and `Field`'s own doc comment both make a contract, was protected by nothing. Now pinned directly by `caseOrderMatchesEmissionOrder`, which reads the emitted tags by walking terminators and compares them against `allCases`, and asserts both order guarantees by name instead of by golden side effect.
  - **The extents precede `AX`/`AY`**, which is what makes `AX` safe. `last` is always inside `boundingBox`, so `−(−X) ≤ AX ≤ +X`; once both extents pass a 4-digit check, `|AX| ≤ 9999`, whose worst rendering is `"-9999"` — **exactly 5 bytes in a 5-wide field, zero margin.** The story called `AX` "implied safe … not an independent case", which is true and is *exactly* true: widening the extent fields, or letting an extent reach five digits, overflows `AX` first. Witnessed at the boundary by `theNegativeExtentBoundaryAlsoFillsTheSignedAxisFields`, which shows `AX` rendering `"-9999"` when the extents sit at 9999 — the *conditional* ("widening the fields overflows `AX` first") is not itself tested, and the in-loop review was right that an earlier wording of this sentence claimed it was.
- **`LA` cannot overflow, and the reason is the order inside `sanitized(_:)`.** It maps over `unicodeScalars` — replacing every non-ASCII scalar with `"_"` — *before* `prefix(15)`, so every surviving `Character` is a single ASCII scalar and 15 characters are 15 bytes. Verified across five adversarial names (21 ASCII letters, 18 emoji, 10 combining-accent graphemes, CR/LF pairs, 30 fullwidth scalars): in every case `LA` emits 15 bytes and the header 512. **That verifies width only, not field validity** — `sanitized(_:)` folds non-ASCII but keeps ASCII *control* characters, so a name like `"a\nb\u{1A}c"` embeds a `0x0A` inside a format whose fields are `\n` + 0x1A *terminated*, and both in-repo header readers mis-parse it. Pre-existing, unchanged by this story, and out of its scope; recorded here because the earlier wording of this sentence read as though CR/LF names had been verified safe rather than verified non-overflowing (in-loop review). **Closed by US-308** (ADR-026): `sanitized(_:)` now folds every scalar outside printable ASCII, so no `String` can put `0x0A`, `0x1A` or `0x00` into `LA`. Worth recording how: US-308's cross-vendor round 2 found it *independently*, without reading this paragraph — a deferred defect that a later story's reviewer rediscovered from the code alone, which is the strongest evidence available that deferring it was a real cost rather than a bookkeeping entry. Moving the `prefix` ahead of the `map` would make it a live trap, because `appendField` counts UTF-8 bytes where `prefix` counts characters. Recorded because the near-miss is real, not because the code is wrong.
- **ADR-020's 1 000 000 split cap stays.** Once serialization throws, an oversize `ST` is a *handled error*, so the cap no longer needs to protect the header. ADR-020 had speculated the cap "may want to be 999,996"; that is **declined** — it would change interpolation *emission* for moves the engine admits by design, in order to guard an error that is now representable, and it would break the rationale ADR-014 and ADR-020 both hang on that number. `ST` overflow is a serialization error, not an interpolation bound. The cap move (0 → 60 500 000 stage points) emits **2 500 003** stitches, not the ~1 000 003 ADR-020 derived, because intermediates re-split; confirmed by execution and deliberately **not** committed as a test, at 1.4 s and 134 MB for a number the tight-extent recipe establishes in 0.5 s.
- **ADR-019 screening**: every input sits *deliberately on* a field-width boundary — 9999/10000, 99/100, 999 999/1 000 000 — because that is the story's subject. ADR-019's screening question is answered yes; its *deciding* question (ulp distance from the boundary) does not apply, because the comparison is a byte count over exact decimal digits, not a floating-point threshold crossing. The one input with floating-point content is the extent recipe (stage 4999.5 → 9999 units), where 4999.5 and its ×2 product are both exactly representable, so `javaRound` has no residue to resolve.
- **Deliberately not decided here**: whether `DSTFile.init` should also refuse a zero-stitch stream. `DSTFileTests.emptyStream` currently pins that a header-only file is legal, US-308's export gate wants `assembledStream().count > 1`, and Catty ships exactly the 515-byte header-plus-EOF file that US-308 calls an anti-goal. That is the export story's decision; the two ADRs will be read together, so this one states that it is not taking it.

**Consequences**: No input, however adversarial, traps either serialization entry point — the guarantee ADR-020 gave for coordinates now extends through the writer, and ADR-020's last open item is closed. The ripple was **41 call sites across 15 files** (25 `DSTFile(stream`, 16 `DSTHeader(stream`), not the 33 the story measured at M3 planning: US-301 and US-302 added sites afterwards. **13 `@Test` functions** also had to gain `throws`, plus one private helper (`InterpolationTests.records(for:)`, which rippled `try` to its two callers). Golden byte identity survived with **no re-blessing**, and every changed line of **executable code** in the pre-existing serialization and golden tests differs only by a `try` or `throws` token — the scope is deliberate and took two cross-vendor rounds to state correctly: the branch also adds a new suite, and it rewrites doc comments *inside* pre-existing serialization tests (`SampleDSTTests`), so both the unscoped version and the first scoping were false — with one forced exception worth naming, since it is the shape any future throwing conversion will hit: `OctagonRosetteGoldenTests`' quarter-turn invariance had to hoist its two calls into locals, because `try` cannot appear to the right of a non-assignment operator. The assertion is unchanged. **662 engine tests**, up from 649 — 660 at the green commit, plus the `Int.min` regression test cross-vendor round 1 asked for and the `Field.allCases` order test the in-loop review's mutation showed was missing.

**Two corrections to the story, both found at planning against the named source.** Its "ordering trap" is **inverted**: `appendField` does write `ST` before `+X`, but that means a huge-move `ST` test traps on `ST`, *the field it targets* — executed, the cap move reports `ST value 2500003` and never `+X`. The tight-extent recipe is still right, for a different reason: it makes `ST` the only violated field, so the test proves the check exists instead of leaning on emission order to shadow a simultaneous `+X` violation. And its `try #require` guidance **does not compile** — `#require` has overloads for optionals, `Bool` and `throws:`, none for a throwing non-optional initializer (`error: call can throw, but it is not marked with 'try'`, alongside a `redundant because … never equals 'nil'` warning). ADR-020's "the four in-repo test call sites use `try #require`" was about the *failable* `EmbroideryPoint(converting:)`, a different shape that the story generalised wrongly.

**Cross-vendor round 1 corrected the boundary itself**, which is the finding worth carrying: the suite pinned `ST` overflow at **1 000 001**, where **1 000 000** is the first value needing a seventh byte — so a regression accepting exactly 1 000 000 and rejecting 1 000 001 passed every test. The story's recipe said 1 000 001 and the criterion said "> 999 999", and neither is wrong; the test simply was not placed on the boundary the field defines. For a story whose whole subject is field widths, that is the one place precision was owed. Also from that round: the ADR's own "every changed test line differs only by a `try` or `throws` token" was literally false as stated (the branch adds a suite and rewrites comments) and is now scoped to what was actually measured, and `Int.min`'s extreme-coordinate claim above gained the regression test it had been asserted without.

**Cross-vendor round 2 closed the loop on the stop condition, and its two findings were both mine to own.** Both Low, both documentation, both about the same sentence: the round-1 fix that *scoped* the "only `try`/`throws`" claim to the pre-existing serialization and golden tests was **still false**, because `SampleDSTTests` is one of those tests and its doc comment was rewritten — the claim needed scoping to *executable code*, which took two rounds to state correctly. And the story file still said "14 test functions", repeating the exact misclassification round 1 had corrected here. Severity history: **Medium → Low**, three findings and two rounds, none rejected; the loop ended on stop condition 1 (a triage that changed no executable code). Worth recording that the round verified rather than agreed — it re-derived the 41 call sites independently, confirmed both `ST` streams hold exactly their stated stitch counts, and checked that `Double(Int.min) / 2` and its ×2 conversion are exact powers of two, so the new conversion-limit test cannot pass from an empty stream. It also stated plainly that it could not run the suite in its read-only sandbox rather than implying it had.

**The mechanism this story contributes to the toolchain**: for a story whose subject is *replacing a trap with a typed error*, the red phase is an exit test asserting **`.success`**, not `.failure`. `#expect(processExitsWith: .failure)` **passes today** — a trap is a failure exit — so it characterises the bug rather than failing on it, and it would have to be deleted at green. Inverted, it fails now (`Expectation failed: .success → .signal(SIGTRAP → 5)`), turns green with the fix, and survives as the "however adversarial" guard. Where a throwing test covers the same recipe, that test subsumes the exit test — a trap would kill the whole run — so the expensive `ST` exit test was retired at green rather than paying 0.5 s twice.


## ADR-026 — DST export: the gate, the two name types, eager preparation, and the exported UTType (2026-08-29)

**Context**: US-308 is the milestone's headline — a design leaves the app as a `.dst` a machine can sew. Two facts set the bar. **Catty's shipping app exports every file with a blank `LA:` field** (only its unit tests ever pass a name), and **neither reference declares a `.dst` type at all** — measured, not assumed: the simulator resolves `.dst` to a system-invented `dyn.ah62d4rv4ge80k65y`, so there is no originator identifier anywhere to reuse. Catroid's `sanitizeFileName` has no empty check and produces a file literally named `.dst`; its `DSTHeader.kt` silently `take(15)`s the name and mangles non-ASCII to `?` under `US_ASCII`. ADR-020 left the gating rule "for whoever wires up export to decide" and ADR-025 explicitly declined to decide whether a zero-stitch stream should be refused. This ADR takes both.

**Decision**:

- **The gate is `exportModel.count > 1` on the post-replay assembled stream** — not `hasValidPattern`, which counts recorded *ops* the replay may reject, and not the display-list count, which is op-derived and carries the same defect. It matches Catroid's `validPatternExists()`, which counts points in the *built* streams. `ExportEligibility` (in `StagePreview`) reports **five** verdicts rather than a `Bool`, because the story's definition of done requires the dimmed control to say *why*, and Catroid's single predicate for both gating and rendering cannot supply one.
- **The export gate and the render empty-state may legitimately disagree, and the app says so.** They diverge exactly in ADR-020's rejected-coordinate case, verified: `placeAt(1e300, 0)` then `stitch` gives a display list of 1 and an assembled stream of **0**, because `emitStitches` appends unconditionally *after* `addStitch` has silently refused the point. An empty stream serialises to **515** bytes and a one-stitch design to **518** — the valid-looking header-plus-EOF file Catty ships. We say "nothing in this design can be embroidered" instead. **What the user is actually looking at is worth stating**: the rejected coordinate is finite, so the display list accepts it and a pure-rejection design draws as a degenerate point at an absurd offset — visually near-empty, not the "you can see your design, it just cannot be sewn" the story's wording implies.
- **"Exportable" is unreachable mid-run**, which no criterion stated. `PreviewRunState.exportModel` is written only from the terminal update, so the share affordance is disabled for the whole duration of every run and can be enabled only by the run ending — naturally, at the cap, or by Stop. So *"export the design you can see, right now"* is not something M3 offers; a later story should read that as a decision, not a defect. It also forces a disabled-hint reason the story never lists: "still stitching". `ExportControl.Readiness` therefore separates `running` from `notRun` even though the engine cannot, since a VoiceOver user mid-run would otherwise be told to press Play while the button beneath them reads "Stop".
- **Two name types, deliberately not one.** `DesignName` (≤ 15 characters, **printable ASCII** — `0x20`–`0x7E` — non-empty, **trimmed on input then validated**) is a *rejecting* layer; `DSTHeader.sanitized` **stays as the *mangling* backstop, with its rule widened to match** (see round 2 below — it folded only non-ASCII, which let the format's own field terminators through), so no caller anywhere — M4/M5, a `.catrobat` importer, a future CLI — can emit a malformed `LA`. The two layers apply the same character rule for opposite reasons: the app so the user sees what they typed, the engine so no caller can corrupt the field structure. This closes an open item ADR-025 had deferred by name. `DSTFile.init` gains **no `DesignName` overload**: measured, requiring one would ripple **56 call sites across 20 files**, and more importantly it would make the backstop unreachable and collapse the two layers into one. The cost, stated so nobody "tidies" it away: the package ships a validator its own serialiser does not require. The whitespace rule was forced by the engine — `DSTHeader` writes `"  pad"` into `LA` verbatim and never trims — and trailing spaces are invisible in a text field, so rejecting them would show an error whose cause cannot be seen.
- **`DSTFileName` is independent of the label, and the independence is real rather than asserted.** Its four rules are the filesystem's, each measured against a real write: `/` becomes a path separator (NSError 4), an empty stem collapses to the directory (512), a 264-character name hits a 255-byte `NAME_MAX` (514), and **NUL truncates the path unpredictably** (4 — the probe's error named a file called "T"). `NAME_MAX` and NUL are both absent from the story's criteria. Measured *legal* and therefore accepted: non-ASCII, `:`, DEL, newline. The independence bites in one place found only by integration: `DesignName` **accepts** `/` and `DSTFileName` rejects it, so `sanitising(_:)` exists as the derivation path — the label keeps the separator, the file name gets an underscore. It takes a `DesignName` rather than a `String` precisely so it can be total.
- **Export is eager: the file is written when the run *ends*, not when the user taps share.** Forced by two independent constraints. A `ShareLink` needs its item at construction time and reports failure to the *system* share UI, so a write inside the `FileRepresentation` closure leaves `ExportState.failed` with no consumer; and `Transferable.exported(as:)` is **iOS 18.2+** against this app's iOS 17 target, so a closure-only write makes the story's own test item 3 unbuildable — a "test that could not fail" arriving through an availability boundary. **Consequently a US-211 overflow is a gate reason, not an export failure**, or its localised message is unreachable behind a generic system alert. The pre-flight is one `DSTFile.init`, which costs nothing extra: ADR-025 records that only the header can fail, so building the file *is* the complete check. One simplification falls out — the file is on disk before a `DSTDesign` exists, so the writer never crosses into nonisolated code and needs no `Sendable` treatment.
- **`ExportState` is three cases, not four.** `preparing` is dropped on measurement: in release, a `DSTFile` from a 52 240-stitch stream takes **2.6–3.0 ms** to build and **0.47 ms** to write, so at the milestone's own exit-criterion size the whole export is under 4 ms — a state no user can perceive and nothing would render. Same call the ROADMAP already made striking `failed` from the *run* enum for having no producer, and ADR-028 made deleting an unreachable hint rather than sending it to ~75 translators.
- **Temp files: one per-session `UUID` directory** under `URL.temporaryDirectory`, holding at most one file, cleared before each write and removed when the design is discarded. `allowAccessingOriginalFile: false` means the system copies the file, so deleting ours cannot break a share in flight. Catty never cleans up at all.
- **The exported UTType is `org.catrobat.embroiderydesigner.dst`**, conforming to `public.data` **and** `public.content` (`public.data` lets Finder and the Files app represent a stored item; `public.content` is what Apple documents as enabling AirDrop, and this story exists to share the file). No `LSHandlerRank` — ADR-011, we open nothing. **Exported rather than imported**, against Apple's own guidance that a proprietary format the system does not declare is an *imported* type: the imported path also says to reuse the originator's identifier, and there is none. The practical difference is Launch Services ranking that ADR-011 does not want. `UTTypeDescription` is localised through **`InfoPlist.xcstrings`**, verified to be picked up from the synchronized folder with no project-file change — which, with `Info.plist` being a plain file edit, is why this story needed **no human Xcode session** at all.

**Consequences**: the milestone's end-to-end thread is complete — pick a design, watch it stitch, name it, and send a machine-readable file out through the share sheet. Verified in the running app rather than only in tests: `LA:SquareCoil` space-padded to 15, `ST:2976`, `CO:2`, 9443 bytes = 512 + 2976 × 3 + 3, in `tmp/dst-export-<UUID>/`. **710 engine tests** (up from 662) and **130 app tests** (up from 65); six screenshots.

**The canary that cannot work, pinned as a regression test.** `UTType(exportedAs:)` builds a type *from* an identifier without consulting the declaration — and the trap is broader than the story's own retraction stated: `.isDeclared` is **`true`** for a completely undeclared identifier, so *any* assertion built on it passes with the plist entry missing entirely; only the conformance check fails. The real canary is the failable lookup `UTType(_:)`, and it was proven capable of failing — with the declaration present all thirteen probe assertions passed, and with `Info.plist` emptied back to `<dict/>` six flipped red on the same simulator, with no stale-LaunchServices false pass. It can **only ever be a hosted app test**: the same probe run as a bare executable, and from inside a hand-built `.app` carrying the declaration, returned `nil` both times, because the declaration resolves only once LaunchServices has *registered* the bundle.

**Two test items were already green, and one was only found so after being written.** Item 5 (byte identity between a stopped run and its completed twin) references no symbol this story adds and passes with every one of US-308's production files moved aside — it already follows from ADR-027 plus `EmbroideryStream: Equatable`. Item 6a is covered four times over by ADR-025's own suite, including the 99-block `.success` control the plan called essential, so only the *app's* rendering of that error was new work. Item 5's corrected form is also not constructible as the story wrote it: `InterpreterDriver.completionReason` orders completion before cancellation, so one program can never stop at the point it would also have finished — the buildable reading is a twin-program pair. The cheap check for this whole class, learned here: **does the new test file reference any symbol the story adds?**

**The in-loop review's headline finding, and why the rule is "printable ASCII" rather than "ASCII".** The first implementation used `Character.isASCII`, which is `asciiValue != nil` — and `asciiValue` **special-cases the `"\r\n"` grapheme cluster to `0x0A`**. So a name of `"a"` plus thirteen CRLFs plus `"b"` validated as **15 characters and 28 bytes**, `DSTHeader.sanitized` truncated it to 15 *scalars*, and the type's headline promise — a name the `LA` field "can carry **verbatim**" — was false in exactly the silent-truncation way this story exists to replace. Two of the admitted control characters, `0x0A` and `0x1A`, are the header's **own field terminators**, so a label containing them would corrupt the structure a reader scans for, and `0x00` truncates any C string the value reaches. Requiring every *scalar* to be printable fixes all of it and restores the invariant `maximumLength` advertises: 15 characters really are 15 bytes. The case is renamed `unsupportedCharacter`, because `nonASCII` would have been a lie about `0x1A`.

**A prepared file is now invalidated by editing the name.** The review found the model able to offer `Alpha.dst` while the field read "Beta" — the name is in the `LA` bytes, so that is the wrong file, not merely a stale label. It was closed only by `StageView` hiding the share row during editing: a **view** condition guarding a **model** invariant, and untested. `ExportViewModel` now records the `DesignName` it prepared from and discards when they diverge, so the property holds without the view's help. A trimming-only edit keeps the file, since it changes nothing that reaches the bytes.

**Three claims in this ADR and the code were overstated and are corrected rather than quietly softened**, which is the finding class this repo counts: the "at most 15 bytes" argument above (false under `Character.isASCII`, true under the new rule); a test comment claiming to assert "over the whole enum" when `Readiness` carries associated values and cannot be `CaseIterable` — proved by adding a tenth case with no hint and watching the suite stay green, now mitigated by a `reasonsOwingAHint` list that lives on the type; and `prepare`'s ordering rationale, which claimed to preserve a usable previous file on failure when what it actually buys is no filesystem side effect from a pre-flight rejection. `RunViewModel.apply`'s "exactly once **by construction**" is likewise reworded: deleting the guard broke no test, because what really makes it once is that every terminal path in the driver is `yield(terminal); return`.

**Three reachable mapping arms had no coverage**, each proved by a mutation that survived the full app suite: `.failed`'s *visible* notice (so a US-211 overflow would have been spoken but not shown — the acceptance criterion says "with the design still on screen"), three of the four extent fields (only `+X` was ever asserted, so a design too far in −X, +Y or −Y would have fallen through to the generic sentence), and the `wasRunning` guard. All three now have tests.

**The cross-vendor round then found the *same* grapheme-versus-scalar mistake in a second place.** `DSTFileName` compared whole `Character`s against a prohibited set, so `"a/\u{0301}b"` — a slash followed by a combining acute, which Swift treats as **one `Character` that is not equal to `Character("/")`** — passed validation with the U+002F path separator still in it, and the write then failed on a directory nobody created. The in-loop review had found this class in `DesignName` and it was fixed there; the sibling type was not checked. Both are now scalar-wise, written the same way so they cannot drift again. **The general lesson is worth more than either fix: a Swift membership or equality test against a `Character` is a grapheme test, and every rule in this project that means "this byte must not appear" has to be spelled on `unicodeScalars`.**

That round also found that **Play Again left the previous export alive** — `state == .ready(oldURL)` with that URL still holding the finished design, while the new run had already cleared the stage. `ExportControl` masked it, so nothing wrong could be shared through the UI; but this ADR says the temp file goes when the design does, and a composed view containing a broken model invariant is not the invariant holding. `AppModel.play()` now discards before starting.

**Cross-vendor round 2 falsified a claim *this ADR* makes, which is the finding it is proudest of.** The paragraph above says the retained backstop stops any direct engine caller emitting a malformed `LA`. That was false: `DSTHeader.sanitized` mapped only *non-ASCII* scalars to `_`, so `DSTFile(stream:name: "A\nB")` emitted an `LA` value beginning `41 0A 42` — and `0x0A`, with `0x1A`, is the header's **own field terminator**, so a scanning reader ends the field early and misparses everything after it. `DesignName` refuses those at the app boundary, but `DSTFile.init(stream:name:)` is deliberately public and takes a `String`: that caller *is* what the backstop exists for. The backstop now maps everything outside printable ASCII, the goldens are byte-identical (no re-blessing), and the claim is finally true. **The two layers now agree on the same character rule for the same reason, arrived at from opposite ends** — the app so the user sees what they typed, the engine so no caller can corrupt the field structure.

That round also pointed out that round 1's own fix left its invariant a **convention**: putting `exporter.discard()` in `AppModel.play()` closed the shipping UI path, but `runner.play(_:)` and `runner.reset()` are both reachable directly — one of this story's own tests calls the former. The discard now hangs off `RunViewModel.onRunDiscarded`, the single chokepoint both paths already pass through, so "the prepared file goes when the design does" holds however the run is discarded rather than because callers remember to.

**Round 3 found the temp directory outliving the window, and two claims the round-2 fix had made stale.** `RunViewModel.discard()` is the chokepoint every *live* abandonment passes through, but closing an iPad window releases its `AppModel` without going through it, and nothing removed the session directory. Firing `onRunDiscarded` from `RunViewModel.deinit` would not have helped — `AppModel` captures itself weakly there, so the closure is a no-op by then. `TemporaryDSTFileWriter` cleans up in its own `deinit` instead: **the object that owns the directory is the one that can always remove it**, and it needs a `nonisolated static` helper because `deinit` is nonisolated under Swift 6 and cannot call the main-actor `removeAll()`. The two stale claims — a doc comment still saying the backstop "maps non-ASCII" and "stays exactly as it is", and a `RootView` comment still crediting `AppModel.play()` with the exporter cleanup that had moved to `onRunDiscarded` — were corrected in place. One of them cited a `sanitisationBackstopIsUnchanged` test that never existed.

**Post-review layout correction, from looking at the running app.** The character counter sat beside the field, which meant it took width *from* the field: the field alone stopped short of the right margin while the canvas, the hoop caption and both pinned action rows ran the full column, so the row read as off-centre because it was narrower than everything around it. The counter now trails the **label**, and the field spans the column. Two consequences worth pinning: **a name can no longer be truncated by the counter at any size** — the AX1 rule now guards a wrapped label rather than a clipped name, so US-308's "the counter moves below the field at AX1" became "below the label", with its *purpose* met by construction instead of at one threshold. And the empty state's copy is now an `.overlay` on the dashed hoop rather than a `ZStack` sibling, because as siblings the label was sized by the slot while the dashes were sized by the aspect-fitted square — so on a pane wider than tall the description ran past the border it appeared to sit inside. `.accessibilityHidden` stays on the shape *before* the overlay; after it, the empty state's entire content would leave the accessibility tree.

**Manual Ink/Stitch verification passed, and turned up the one thing neither review layer could have.** The first file exported through the app's own share sheet reads `LA:SquareCoilexp`, `ST:2976` (2975 stitch records + 1 colour change), `CO:2` with the change at record 1489 of 2976 — a 50.0% split — and extents 53.40 × 52.80 mm, matching the app's accessibility summary to the millimetre. **But the colours differ**: the app shows `#1d4ed8` then `#f59e0b`, and Ink/Stitch drew pink then green. That is the format, not a defect — **DST stores no colour whatsoever**, only coordinates and colour-*change* commands, so every viewer and every machine chooses its own palette per block. Verified rather than assumed, from both ends: this engine's writer emits no RGB anywhere, and Catroid's reference writer likewise tracks only `colorChangeCount`. ADR-015 pins *when* a change is emitted precisely because *what colour* is not a thing the file can say.

**The consequence is a UX gap, and it is filed rather than fixed**: US-308's promise is that what you name is what the machine displays, and a user will reasonably extend that to the colours they picked. They will meet the truth on their own file, with nothing on screen preparing them. **US-312** in the backlog weighs the options (say so in the app, ship a companion colour file, or a format that carries colour); it is out of scope here because M3's promise is DST and the bytes are correct. Also still open: AirDrop, which justifies the `public.content` conformance and which the simulator cannot exercise — its share sheet offers only Copy and Save to Files.

**One limitation carried forward for US-309**: `prepare` is synchronous main-actor I/O inside the run's update fold. The 2.6–3.0 ms measurement above is at 52 240 stitches, and `RunBudget.maxStitchesPerRun` is 200 000 — about 4× that — with an unbounded atomic write on a slow or full disk. It is one dropped frame at exactly the moment a run ends, and `commitName()` does the same on keyboard dismissal.

**Corrections to neighbouring code the move exposed.** `StageView` applied `.fixedSize` to the notice `ScrollView` itself, which inverted its own intent — a `ScrollView` handed a `nil` height proposal reports its content's ideal height, and `fixedSize` then makes it refuse anything smaller, so the region grew and clipped instead of scrolling, defeating the "then the notices scroll" degradation step this story is the first to depend on. And `.swiftlint.yml`'s localized-strings rule is a *name list*, so `ShareLink` and `SharePreview` were invisible to it until added — worth knowing when the next title-taking view arrives.


## ADR-027 — The run lifecycle: two tasks, a terminal that cannot be forgotten, and three budget axes (2026-08-17)

**Context**: US-306 makes the preview a live run. `Interpreter` is a `Sendable` struct with `mutating func step()`, so a driver can own it by value off the main actor; the app then has to get batches across to `@MainActor` without dropping any, stop on command without losing the design, and never re-implement engine semantics. Both references get the stop path wrong in the same direction: Catty's `Stage.stopProject()` calls `removeAllChildren()` **and** `frontend.project?.removeReferences()` — tearing down exactly the object graph its own `shareDST` reads — and Catroid's `StageListener.render():576-600` runs `stage.act()` up to **50×** per frame, *increasing* the count when the pass is fast (`DELTA_ACTIONS_DIVIDER_MAXIMUM = 50f`, `ACTIONS_COMPUTATION_TIME_MAXIMUM = 8` ms), an anti-throttle fighting its own O(n)-per-frame rebuild. Neither is ported. The one sound piece of Catty's pipeline — drain every 2nd frame, `CBPlayerConfig.swift:27` — is the shape ADR-018's fixed tick already generalises.

**Decision**:

- **There are two tasks, and `stop()` cancels only the producer.** This is the load-bearing decision, and the story's own criterion had it wrong in the direction that fails silently. Only the producer can *decide* to stop: it is the thing that observes `Task.isCancelled` and emits the terminal update carrying `assembledStream()`. Cancelling the consumer instead — the natural reading of "the run `Task` is cancellable", and what cancelling a `for await` task or a `.task {}` does — **does** stop the producer, via the stream's `onTermination`; what it loses is the *delivery*. The producer observes the cancellation, builds the `.stoppedByUser` terminal carrying `assembledStream()`, and yields it into a stream nobody is reading, so the app never learns the completion reason and never gets the export model. (**Corrected in round 4, and this is the third wording of this justification.** It first argued from a false claim about `next()` returning `nil`; then from the interpreter being left to run to its natural end, which contradicted the very next sentences of this same paragraph, where `onTermination` is described as cancelling the producer. The decision never moved; its stated reason was wrong twice.) Export-after-stop would fail the way Catty's does while every producer-side unit test still passed. The consumer therefore drains until the stream finishes on its own, one or two elements after the stop, since cancellation is observed between frames. Conversely `AsyncStream.Continuation.onTermination` **cancels the producer** rather than finishing the continuation: `onTermination` fires *because* the continuation terminated, so finishing inside it is a no-op, and what is actually wanted is that a consumer who walks away stops the interpreter instead of leaving it running to the stitch cap.
- **The terminal is unrepresentable-without-an-export-model.** `RunTermination` carries a **non-optional** `exportModel: EmbroideryStream` with no default, and every completion path is funnelled through one private `terminal(_:of:batch:)`. The criterion "the terminal batch always carries `assembledStream()` on all three paths" is then a type, not three code paths that each remembered. That is the direct, by-construction closure of Catty's teardown-before-share hazard. It rides a separate `RunUpdate` wrapper rather than `RunBatch`, for three reasons: `RunBatch` is a pure fold over `InterpreterEvent`s and none of the three completion reasons *is* an event (its own doc comment says so and argues against exactly this); `RunBatch` is `Hashable` and built per frame, so hanging a 200 000-record stream on it is the unconditionally-O(n)-hash trap `StitchDisplayList` declined `Hashable` to avoid; and making the terminal a second stream *element* would put two observable mutations on the final frame, breaking the "one mutation per batch" arithmetic by one for every run.
- **Three budget axes, deliberately not two.** `ticksPerFrame` (1) bounds how many `step()` calls a frame makes; `maxStitchesPerFrame` (2 000) is checked **between** ticks and ends the frame early; `maxStitchesPerRun` (200 000) is the only producer of `.stitchLimitReached`. The two stitch budgets are constantly confused and confusing them yields a design that either stutters or never stops, so: **`maxStitchesPerFrame` never terminates a run, and `maxStitchesPerRun` never throttles a frame.** Neither can bound a *batch*: `step()` accumulates every runnable thread's events into one array (`Interpreter.swift:79`), measured at **24 008 stitches in a single tick** from eight concurrent scripts and 6 001 from one thread in triple stitch, so the first tick of a frame always runs whole however large it is. A corollary worth stating because it makes tests vacuous if missed: **at `ticksPerFrame = 1` the per-frame stitch budget is unreachable by construction.**
- **Pacing is injected, and "immediate" must yield.** `RunPacing` is a one-method `Sendable` protocol (ADR-006 pattern 2). `ImmediateRunPacing.waitForNextFrame()` awaits `Task.yield()` rather than having an empty body: an `async` function that never suspends does not give up the cooperative thread, so a `forever` program would monopolise it and starve the consumer until the stitch cap — a hang that reads like a deadlock. The requirement is **non-throwing** so cancellation has exactly one path (the driver's `Task.isCancelled`) rather than two, because two paths means one of them eventually skips the terminal update. A third implementation is needed in tests and was not anticipated: a **gated** double, since under immediate pacing a mid-run stop races a natural finish and comes back `.programFinished`.
- **The run's state machine is a pure value in the package.** `PreviewRunState` holds the transitions, the append, the export capture, the reset and the settling watermark; `RunViewModel` is `@Observable` with **exactly one observed stored property and one method that mutates it**. ADR-022 keeps `StagePreview` Foundation-only, so the view model cannot move into the package — but nothing about the *logic* needs `Observation`, and hoisting it puts all of it on the fast `swift test` gate. It also makes "exactly one observable mutation per batch" true by construction rather than by discipline. This is the same forced hoist ADR-024 records for `StitchDrawPlan`, one story later.
- **`RunState` has three cases and no `failed`.** ADR-018 guarantees the interpreter never halts, so nothing in the *run* path can fail; `failed` belongs to the export lifecycle, which genuinely can. This corrects ROADMAP.md's four-case enum rather than shipping a case with no producer.
- **The needle is a sibling `Canvas` layer, not a branch inside the stitch layers.** That is what makes ADR-009's cache protection structural: `CanvasStitchLayers` has no `needle` property, so no `BakeKey` field *can* depend on the pose and a per-frame re-bake is unrepresentable rather than merely avoided. The cost is one extra full-viewport compositing layer per frame, for US-309 to measure. Its geometry (`NeedleGlyph`) is fixed **in view points** and uses the transform for position only, so US-307's pinch-zoom cannot grow it into something that reads as a very large stitch; the price, recorded for that story, is that past roughly 3× zoom the needle is comparable to a single thread stroke and stops reading as a marker — the fix if it matters is a floor, not a scale factor.
- **The needle is two inks, because the binding constraint is every thread colour, not the two stage fields.** It is drawn *on top of the design*. `needleCore` `#7f1d1d` alone clears the paper at 6.97:1 and the mat at 5.18:1 but is only 2.10:1 against black — `ColorState`'s default and so the commonest thread. Paired with a white halo the two inks span the whole luminance range and the **worst background anywhere in it** (a mid grey near `#919191`) still clears **3.17:1** against one of them; that is a proved bound over the colour space rather than a spot check, and it is what makes the halo non-optional. It also selects the ink: the bound needs relative luminance ≤ 0.0667, which `#991b1b` misses at 2.88:1 despite passing both fields. Rejected with measurements: `#f59e0b` (1.49:1 paper, 1.11:1 mat — extending ADR-024's rejection to every opacity), `#dc2626` (2.50:1 mat), `#6b21a8` and `#991b1b` (universal bound), and **black, rejected on identity** — best contrast of all, and the one ink guaranteed to be indistinguishable from the design.
- **VoiceOver silence is achieved by having nothing to announce.** A `Canvas` has no child views and the stage is already one element with a *static* label, so "the needle must not be announced continuously" needs no configuration. Recorded because US-307 owns the real summary and is one `accessibilityValue` away from undoing it: a changing value on the focused element *is* a continuous announcement.

**ADR-024's open question is answered.** It asked at what scale `Image(size:renderer:)` rasterises, since 1× would leave the settled layer visibly softer than the live tail. `PreviewRunState.settleChunk = 1000` makes the watermark advance at runtime for the first time (`octagonRosette` three times, settling at 3 000 of 3 194; `squareCoil` twice, at 2 000 of 2 976 — both crossing `bakingThreshold = 2000`), so the question became answerable by screenshot: magnifying a definitely-settled region against a definitely-live one shows **identical edge quality and no seam**. It rasterises at the display scale.

**Found while specifying the UI, and it is the kind of defect a screenshot cannot find**: `StageContentState.resolving` took no run input, so a design whose first bricks are `wait` would show the "press play" empty state while the button beneath it read **Stop** — a screen contradicting itself. Unreachable with the bundled samples, because sample 1 emits 51 stitches on its very first tick, which is exactly why it needed a test. `.running` now resolves to `.drawn`.

**Consequences**: the milestone's end-to-end thread is live — pick a sample, watch it stitch, stop it and still hold an exportable model. US-308 takes `exportModel` from the view model rather than re-assembling. US-309 inherits three tunables named as starting values (`settleChunk`, `bakingThreshold`, `maxStitchesPerFrame`), the extra needle compositing layer to measure, and the by-value display-list copy ADR-024 already flagged. US-307 inherits the Reduce Motion gate (read in exactly one place, on the symbol morph) and the two ways to break VoiceOver silence.

**Correction (2026-08-17, in-loop review round 1) — the premise this ADR first gave for producer-only cancellation is false, and the false premise cost a defect.** The original text argued from "`AsyncStream.Iterator.next()` returns `nil` when the consuming task is cancelled". Measured, that is **wrong while elements are buffered**: a consumer cancelled before it ever ran still received all five buffered elements, and `next()` in a cancelled task with one element buffered returned the element rather than `nil`. Cancellation marks the stream terminal; it does not discard `pending`. The decision is unchanged and the reasons above are the ones that hold.

The cost of believing the false version was a **Critical defect**: it made a discarded run's buffered frames look impossible, so nothing guarded against them. `RunViewModel.discard()` cancelled the consumer and dropped it, and the orphaned consumer then applied the discarded run's buffered frames into the run that replaced it — measured at 5 001 stitches and a `.finished(.stitchLimitReached)` state arriving *after* a `reset()`, and a buffered *terminal* published the discarded design's export model, which is US-308's input. Reachable by picking a new sample while a run is in flight (`AppModel.select(_:)` → `runner.reset()`), which is an ordinary thing to do. It is the same hazard class this ADR claims to close "by construction", arriving through a door the ADR had argued was shut.

Fixed in two places: the consumer checks `Task.isCancelled` before applying, and **`PreviewRunState.apply` refuses updates unless the run is `.running`**. Both were proven load-bearing by reverting each and watching the new tests fail. **This paragraph originally said the second guard made the corruption "unrepresentable"; it does not** — see the round-1 correction below, where Codex refuted that by construction, and where the session identity that *does* close the general case is recorded.

**Also corrected in the same round**, each recorded rather than quietly fixed:
- **`RunBudget` clamps every axis to at least 1, and the axes are `let`.** `ticksPerFrame: 0` ran zero ticks per frame, so `run.isFinished` never became true (no `step()` was made) and `stitchesThisRun` stayed 0 — no budget axis could fire, and the run yielded empty frames forever with **zero** terminals. That was the only path found that breaks the terminal guarantee this ADR makes structural everywhere else. Negative `maxStitchesPerRun` is the mirror case.
- **`onTermination` assigned after termination does not run immediately.** Measured: the handler is stored and invoked with `.cancelled` when the stream *storage* deallocates. No behavioural consequence — if the producer has ended there is nothing to cancel — but the safety argument as first written rested on a mechanism that does not exist.
- **"The stream finishes one element after `stop()`" is one *or two*.** (The *explanation* first given here was superseded by the round-1 fix and corrected in round 3 — see below.)
- **The needle-visibility rule is now `PreviewRunState.visibleNeedle`**, not an expression in `RootView`. The test that claimed to pin it recomputed the same expression in its own body, so it stayed green if the call site dropped the condition entirely.
- **`PreviewRunState.apply`'s "O(batch), never O(display)" holds only within the value.** In the app the display list is also handed into the view tree, so its buffer is not uniquely referenced and copy-on-write makes the frame O(display) regardless — the cost ADR-024 already records and this ADR passes to US-309. The comment should not claim what the package cannot guarantee.
**Correction (2026-08-17, Codex round 1) — three claims narrowed, two orderings fixed.** Six findings (3 Medium, 3 Low), all valid, none rejected.

- **The terminal guarantee is about *production*, not delivery, and the ADR overstated it.** "Exactly one terminal `RunUpdate` carrying `assembledStream()` on every completion path" is true of what the producer *builds*; it is not true of what a consumer *receives*, because a consumer that has stopped consuming terminates the stream, `onTermination` cancels the producer, and the terminal `yield` then returns `.terminated` and is discarded. That is correct behaviour for `discard()` — no terminal is wanted there — but the guarantee must be stated as **delivered to a retained consumer**, which is what `RunViewModel` maintains for `stop()`.
- **Cancellation now beats the stitch cap.** The producer checked `Task.isCancelled` only at the top of the loop, so a `stop()` landing *during* a long frame that also crossed `maxStitchesPerRun` reported `.stitchLimitReached` — telling a user who pressed Stop that the preview had hit a limit. The precedence is now **completion → cancellation → cap**, extracted as a pure `completionReason` so the table is enumerated by a test rather than reachable only by an interleaving. Cancellation deliberately does **not** beat natural completion, which narrows what the finding implied: if the program genuinely finished on that frame the design is *whole*, and `.stoppedByUser` would suggest a partial design the user does not have.
- **"`PreviewRunState.apply`'s `.running` guard makes the corruption unrepresentable" was false**, and Codex refuted it by construction: `begin()` A, `reset()`, `begin()` B leaves B `.running`, so A's late frames are accepted. The guard covers updates arriving while `.idle` or `.finished`; distinguishing *sessions* needs an identity the update does not carry. `RunViewModel.generation` — captured by the consumer closure, bumped by `play()` and by `discard()` — is the guard added for it, though see the round-2 and round-3 corrections below: it is defence in depth rather than the load-bearing check, because every generation change is coupled to a cancellation. Note this is the *second* overclaim on this branch about the same fix: the round that introduced the guard also overstated it.
- **A finite heading did not guarantee finite geometry.** `NeedleGlyph.outline(at:heading:)` guarded that `heading.isFinite`, but `heading * .pi / 180` overflows to infinity near `.greatestFiniteMagnitude` and `sin`/`cos` of infinity are NaN, so the function returned non-finite points while claiming to return `nil` for unusable input. The angle is now reduced modulo 360 before scaling — exact for a periodic quantity, not a degradation. Only the public API was exposed; the interpreter path normalises headings.
- **A tautological assertion**: `run.display.colorRuns == run.display.colorRuns` in the determinism test could not detect a colour-run regression. The first run's value is now captured and compared against.
- **Superseded text removed rather than left standing behind a correction block.** The retracted `AsyncStream` premise still appeared verbatim in `RunViewModel` (twice) and in the test target's `drain` helper, so a reader arriving at any one of them would have been misinformed and would have found the other two "confirming" it. Rewritten in place. The lesson generalises past this branch: **a correction is not complete until every copy of the claim is gone**, because the copies corroborate each other.

**Correction (2026-08-17, Codex round 2) — the guarantee had a hole the package's own test double demonstrated.** Five of six round-1 fixes verified correct and complete; one failed (stale ADR text) and four new findings landed (1 Medium, 3 Low), all valid, none rejected. Severity flat at Medium, so the loop does not stop here.

- **Medium: `stop()` could not terminate a run parked in pacing, and `RunPacing`'s contract permitted it.** The producer observes cancellation *between* frames, so an implementation that stays suspended through a cancellation parks it permanently — no `.stoppedByUser`, no export model, zero terminals. `GatedRunPacing`, this package's own gated double, did exactly that behind a comment calling it "deliberate", and the stop tests hid it by granting a frame *after* stopping. Verified by restoring the cancellation-deaf gate: the contract test times out at 60 s with zero terminals. `RunPacing` now **requires** implementations to return promptly on cancellation — `Task.sleep` satisfies it for free, a hand-rolled gate needs `withTaskCancellationHandler` — and both gates were fixed, the post-stop grants removed (which makes those tests stronger, since they no longer help the producer along), and the requirement pinned by `aRunStoppedWhileParkedInPacingStillTerminates`. The requirement cannot be expressed in the type, so it is documented and tested rather than claimed.
- **Low: the generation guard is defence in depth, not what closes the discarded-run case — and the round-1 correction overclaimed it too.** Codex showed the new test stays green with the guard deleted: `discard()` cancels the old consumer, so its buffered update exits at `Task.isCancelled` before the generation is ever compared. In the code as it stands **the cancellation check is what closes the case**; the generation keeps the property true if a suspension point were ever introduced between that check and `apply`. No current test can distinguish them, and the test now says so instead of implying otherwise. That makes **three successive rounds in which a claim about this one fix was too strong** — worth noting as a pattern, not just a slip: each correction was written in the same breath as the fix, which is exactly when the reasoning is least tested.
- **Low, twice: two stale copies of already-retracted claims survived in this ADR** — "one element after the stop" and the `.running` guard being "unrepresentable" — each contradicting a correction further down the same document. Also `RunSession.stop()` still promised the terminal was "still delivered" without the retained-consumer qualification. Fixed in place. This is the second round in which the *incompleteness of a correction* was itself a finding.

**Correction (2026-08-17, Codex round 3) — three Low findings, all documentation or test coverage; no functional defect.** Every round-2 fix verified correct and complete: the gated pacing actors cannot double-resume, leak or lose a continuation, and no lifecycle, frame-budget, watermark or ADR-007 heading defect was found. Severity fell from Medium to Low.

- **The "one or two elements after `stop()`" *explanation* was made false by round 1's own fix.** It said a stop landing inside `runFrame` yields that frame's ordinary update first and the terminal on the next pass. That was true before cancellation was re-checked after the frame; it is not true now. Today a stop landing during a frame produces **exactly one** element — a terminal *carrying that frame's batch* — which is strictly better, since the frame's stitches are not stranded behind a separate update. The count can still be two, but only for a stop landing in the narrow window between the completion check and the ordinary yield, and that is the case worth naming. A fix invalidating a neighbouring comment is the failure mode this ADR has now seen three times, from three different directions.
- **The generation guard's characterisation needed narrowing a second time.** Two source comments and this ADR still said generation was what prevented stale updates. It is defence in depth: every generation change is coupled to a `discard()` that cancels the old consumer, and there is no suspension between that check and `apply`, so deleting the generation changes no behaviour today. Round 3 additionally confirmed that **no test through the public API can distinguish the two** — it would need a controllable suspension point at that seam — so the code now says exactly that instead of implying a test proves it.
- **"The terminal carries `assembledStream()`" was not discriminatingly tested, and the type claim overstates what the type proves.** A non-optional `exportModel` proves *some* export model reached the terminal, not that it is the interpreter's assembled stream: replacing the driver's call with any fixed non-empty sentinel would have kept every terminal test green, since they only asserted `count > 0`. The type still buys what it was chosen for — no completion path can omit an export model — but the story's criterion asks for the *assembled* stream, and that now has its own assertion: the natural-finish test compares the terminal's export model against an independently stepped interpreter's `assembledStream()` for exact equality, and the cap test asserts two different caps produce *different* export models, which a sentinel cannot satisfy.

**Correction (2026-08-17, Codex round 4) — two Low documentation defects; the loop ends here.** Every round-3 fix verified correct and complete, including that `assembledStream(of:)` is genuinely independent of the driver and that the new assertions discriminate against the sentinel regression. No runtime, concurrency, budget, watermark or heading defect, and no further computed-expectation test blind spot. **Round 4's triage changed no executable code**, which is the `/codex-review` stop condition.

- **The type claim needed narrowing one last time.** "The terminal is unrepresentable-without-an-export-model" is true and useful — no completion path can omit the field — but it does not make the model *the assembled stream*: `RunTermination(reason:exportModel:)` compiles with any `EmbroideryStream`. The stronger property comes from the single `terminal(_:of:batch:)` funnel plus round 3's tests. Corrected here and in `RunUpdate`.
- **The justification for producer-only cancellation was wrong a third time.** It said cancelling the consumer "leaves the interpreter running to its natural end or the stitch cap" — which contradicted this same paragraph two sentences later, where `onTermination` is described as cancelling the producer. What actually happens: cancelling the consumer *does* stop the run, and what is lost is **delivery** — the producer builds the `.stoppedByUser` terminal carrying `assembledStream()` and yields it into a stream nobody is reading, so the app never learns the reason and never gets the export model. Rewritten in all four places it appeared.

**The loop's shape, and what it says about this branch.** Four rounds, **15 findings, none rejected**, severity Medium → Medium → Low → Low, ending on "no code changes" rather than on a clean round. Almost none of it was logic: the driver's arithmetic, the budget, the watermark, the bake key and the ADR-007 heading mapping were confirmed sound in every round. What kept failing was **claims** — five tests that could not fail, and one justification rewritten three times, each rewrite made in the same breath as the fix it accompanied. Two things generalise past US-306. A premise about framework behaviour has to be *executed*, not reasoned about, before it is written down; and **a correction is not finished until every copy of the retracted claim is gone**, because the surviving copies corroborate each other and the next reader cannot tell which is current.

## ADR-028 — Zoom and pan: one commit per gesture, a fit-aware floor, and a summary that only a transition may write (2026-08-18)

**Context**: US-307 adds pinch-zoom, pan and the stage's VoiceOver summary. The roadmap gated zoom/pan on "only if the ADR-009 transform work makes it nearly free", and US-302 does deliver the anchored pinch, the pan and their hardened invariants — so the view composes gestures and calls pure methods. What the story did *not* anticipate is where the remaining difficulty actually sits: SwiftUI's gesture values are cumulative rather than incremental, a `StageTransform` in state is not animatable, `StageTransform.fitting` can legitimately return a scale below the *gesture* floor, and two of the story's own criteria contradict each other for a running design. **Neither reference has any zoom/pan prior art** — Catroid's stage package has none, and Catty's only pinch handling is PocketPaint's crop tool — so this is greenfield on both platforms, like US-306's needle.

**Decision**:

- **The transform is written once per gesture, in `onEnded`, and never during it.** This is the load-bearing decision and it settles three separate things at once. (1) *Correctness*: `MagnifyGesture.Value.magnification` and `DragGesture.Value.translation` are both cumulative from the gesture's start (read off `SwiftUI.swiftinterface:9378-9394`, not assumed), so folding each callback in as a delta compounds them — a pinch whose callbacks read 2, 2, 2 lands at 8× for fingers that asked for 2×. (2) *Simplicity*: because nothing is written mid-gesture, the committed transform **is** the gesture's baseline for its whole duration, so `StageZoom.commit` needs no captured baseline, no rebasing and no per-channel end bookkeeping — a state machine the planning pass had proposed in full and which the single commit deletes entirely. (3) *Criterion 3*: `CanvasStitchLayers.BakeKey` reads the transform, so a transform that cannot change mid-gesture makes "the settled raster is re-baked exactly once, on gesture end" **structural rather than timed**. The live gesture is `.scaleEffect`/`.offset` over the composed canvas — ADR-009's cached raster blitted through the transform as a GPU scale, which is what criterion 3 asks for.
- **The mid-gesture blit is the whole canvas, not the raster rect.** The alternative — freezing the bake transform and blitting the raster's rectangle at a computed delta — was designed in full and rejected: it needs an enum on the `StagePreviewRenderer` protocol plus two new geometry types, and it *uncovers* area the raster never held. Writing the destination of a view-space zoom by `f` about anchor `a` as `[a(1−f), a + f(W−a)]`, a pinch-in about an in-viewport anchor always covers, but **any pan and any pinch-out do not** — so the honest fallback (stroke the whole plan) would carry most frames anyway, and the uncovered strip is *missing design*, not soft design. Scaling the composed canvas moves everything together, so nothing inside it can be uncovered. The price, stated rather than left to be found: everything fixed in view points — the needle, the hoop outline, the travel dash — grows with the blit and snaps back at commit. That follows directly from ADR-027 fixing the needle in view points, and scaling only the stitch layer would be worse, because the needle would visibly detach from the stitch it is sewing.
- **The zoom floor is a rule, not a constant: `minimum = min(fit.scale, StageTransform.minimumScale)`, maximum 50.** `fitting` floors at `minimumRepresentableScale` while `pinched` clamped at `minimumScale` (0.05), so an out-of-hoop design could be *fitted* below the floor a pinch could reach — the first pinch would snap it larger, and double-tap-to-fit followed by pinch-out could never get back. The case is reachable and exports perfectly well; `StageTransform.minimumScale`'s own documentation works it through. **`StageZoomBounds` only ever widens the range**, never narrows it, and that is what lets every one of `pinched`'s seven Codex rounds of hardened invariants keep its meaning: `gestureDefault` *is* the previous behaviour, pinned equal to `clampedScale` by a differential test over the hostile inputs rather than by inspection. `pinched(by:about:)` now delegates to `pinched(by:about:within:)` so there stays exactly **one** anchoring implementation — and the 18 pre-existing pinch tests going red in the red phase is the evidence that the delegation is real rather than a second clamp. The narrower alternative (`minimum = fit.scale`, "never zoom out past the fit") was rejected: it narrows the range for every in-hoop design, makes `minimumScale` dead, and would silently change what `scaleClampsAtBothEnds` means. **The maximum is left at 50 and is practically useless up there** — `StitchDrawMetrics.threadWidth(atScale: 50)` is 157.5 view points, so a single penetration dot is 315 pt across. That is arithmetically correct (0.63 mm of thread magnified 50×) rather than a bug, and it is recorded here instead of being discovered in a screenshot review.
- **The adjustable action steps by 1.5× about the viewport centre, within the same bounds as a gesture.** Multiplicative because the range spans three orders of magnitude, so an additive step usable at 0.05 is imperceptible at 50; 1.5 reaches the maximum from a typical in-hoop fit in about eleven activations and the floor in six. The centre because there is no finger, and because anchoring on the stage origin would walk a panned design off-screen. A narrower assistive range was considered and rejected: the zoom level is now *spoken*, which is what the narrower range was invented to compensate for, and "Fit to Hoop" returns in one step. One bounds concept, not two.
- **`.accessibilityAdjustableAction` alone is a trap, so a named "Fit to Hoop" action ships with it.** Double-tap-to-fit is unreachable with VoiceOver running — a double tap is VoiceOver's own activate gesture — and Switch Control has no double tap at all. Without the named action, the one feature added for users who cannot pinch would let them zoom in and never get back.
- **Numbers appear in the accessibility value only when they are final.** Criteria 5 and 6 contradict each other: a summary of what the stage holds, rebuilt only on run-state transitions, is computed at `idle → running` — when the display list is empty and `display.bounds` is `nil` — and would read "0 stitches" for the whole run while the design visibly stitched. So a running stage says it is stitching and a finished one says what it made. Nothing is lost, because criterion 6 makes mid-run counts unobtainable either way. **The design name is in the label, not the value**, so it is not re-spoken on every value change; the summary a user hears is label plus value. **The zoom level is spoken and comes first** once the user has zoomed, because VoiceOver re-reads the *value* after an adjustable action and a value that could not change would leave that action with no feedback at all — criterion 6's substance is "never per batch", and a zoom step is user-initiated and discrete.
- **`RunPhase` is a separate type because Swift has no intra-type access control.** Two `private(set)` properties on `PreviewRunState` would leave `apply(_:)` free to assign the summary every frame, since `private` there means "within this type". In a separate type it means "within `RunPhase`", so `apply(_:)` **cannot reach the summary at all** — the only way in sets a state alongside it. Stated precisely, because the neighbouring invariant in ADR-027 had the word "unrepresentable" retracted three times: this is a **chokepoint, not an impossibility**. Calling `enter` per batch is still representable, and that is exactly why the counter test is not vacuous. Putting the summary inside `RunState`'s payload *would* make it impossible — and would make the test tautological, since the transition count would then equal the summary-change count by definition. That is the "test that cannot fail" pattern this repo has now hit nine times, declined on purpose. The **append happens before the transition**, or the terminal summary undercounts by a frame; proven load-bearing by reverting it and watching the count come back 1 instead of 3.
- **Two assertions carry the headline criterion, and neither alone is the property.** The *count* is the criterion's letter — 2 transitions against 139 batches for sample 1, two orders of magnitude apart. The *value equality across every batch* is what actually keeps VoiceOver quiet, because the system re-announces on a changed value rather than on a write, so a counter can be satisfied by an implementation that rebuilds an identical value every frame.
- **`colorCount` is distinct colours and must not be reused for the DST header.** Runs, distinct colours and `CO` blocks are three different numbers — red→green→red is 3 runs, 2 colours, 3 blocks — and **neither bundled sample can tell them apart** (1/1/1 and 2/2/2, measured), so the definition is pinned with a synthetic list. US-308 takes `CO` from `EmbroideryStream.colorChangeCount`, per ADR-012.
- **Each length carries its own spelled-out unit.** The story's "98.6 by 98.6 millimetres" composes only in English: unit names inflect with the number and change position, so a catalog entry containing the word can only ever agree with one of the two numbers. Handing `Measurement.FormatStyle` both lengths makes the agreement ICU's problem rather than a translator's, which is what ~75 languages through Crowdin needs. `.wide` rather than the hoop caption's `.abbreviated`, and the rule worth remembering is **abbreviated for the eye, wide for the ear**: VoiceOver's expansion of "mm" is not guaranteed across locales and voices, and "m m" spelled letter by letter is the failure mode. `usage: .asProvided` for the reason the caption already pins it, and an explicit one-decimal precision because the default will otherwise say "98.568 millimetres".
- **Reduce Motion gates the fit transition and nothing else.** `withAnimation` around the reset animates *nothing* — a `StageTransform` in state is not animatable, and `Canvas` re-strokes from whatever it is handed — so the reset runs on the same `.scaleEffect`/`.offset` channel the gesture uses, driven by the new pure `StageTransform.viewDelta(to:in:)`, and swaps the transform at completion. **Direct manipulation is deliberately not gated**: Reduce Motion is about motion the app starts, and suppressing a pinch would break the gesture rather than calm it. ADR-027 asked this story to reuse the transport row's "single gate"; taken literally that is not buildable and would be wrong — `@Environment` is per-view resolution, and passing the flag down as a parameter decouples it from the environment SwiftUI resolves for the child. What is genuinely shareable is the **policy**, so `StageMotion` owns the decision and each view reads the environment where it lives. Being a pure function it is also assertable, where the same decision spelled inline in two bodies could only be checked on a device.
- **The zoom lives in `AppModel`, not in the stage.** ADR-023's container swap is the usual reason, and there is a worse one specific to this value: `RootView` builds the stage at **two** call sites, so `@State` there would be two independent zooms that disagree, and an iPad window resized across the size-class boundary would show the other one. A plain `Sendable` value rather than a second `@Observable` class — a zoom owns no tasks and no lifecycle. It resets in `select(_:)`, beside the run's reset and for the same reason: the view-side spellings re-fire on the ADR-023 rebuild.

**`viewDelta` carries no y-flip, and that is derived rather than omitted.** Both mappings apply `flippingY`, so composing one with the other's inverse cancels it: the delta is a positive uniform scale plus a translation in y-down view space. Guarded on the **results** rather than the intermediate products, which is the lesson `centringOffset` and `pinched` each had to learn twice; refused rather than collapsed to the identity, because an identity delta would draw the old pixels in the wrong place and report success.

**What the criteria could not deliver as written, recorded because the pattern is now the story of this milestone.** Six corrections, each checked against the named source: test items 1 and 2's first half were **already green from US-302** (so re-writing them would produce tests that had never been red); item 2's second half is **vacuous** under `nil`-means-fit (`fit == fit`); item 3's sentence is **not assertable** at all; criterion 4 is **untestable and already true**, since batches are buffered on a separate task and what a gesture can drop is frames, not batches; criteria 5 and 6 **contradict each other**; and criterion 8's spring needed a pure method US-302 never shipped. US-305 had four unbuildable test items and US-306 had two vacuous ones — this is the third consecutive story where the adversarial buildability check at planning paid for itself, and it is now clearly a standing step rather than an occasional one.

**Consequences**: the milestone's stage is inspectable. US-309 inherits three things by name — the mid-gesture path to measure separately from the settled path (ADR-024's own "two things for US-309" now has a third), the useless top of the zoom range if it wants to narrow it on evidence, and ADR-027's needle note going live, since zoom now reaches 50× and the needle stops reading as a marker past roughly 3×. US-308 must not reuse `colorCount` for the `CO` field. **Two limitations ship stated rather than implied**: the pan is **unclamped**, so a design can be panned entirely off-canvas — recovery is one double-tap for touch users and the "Fit to Hoop" action for everyone else, and clamping it needs package math this story did not budget; and in **compact width the canvas's leading edge sits inside `NavigationStack`'s interactive-pop zone**, so a pan begun there pops back to the picker instead of panning, which is not fixable without disabling system navigation.

**Review outcome (in-loop `swift-code-reviewer`, 2026-08-18): four Important findings, all reproduced, all accepted; plus one defect Sebastian found in the running app that no automated check would have caught.**

- **`@GestureState` has already reset by the time `onEnded` runs**, which made the pan's threshold compensation a no-op at exactly the moment it mattered. The live offset subtracted the drag's first translation (so the content did not jump by the recognizer's ~10 pt at pan start), and the commit read the same origin back through `live` — where it was `nil` — and so used the raw translation. Measured: a 101 pt drag whose live offset showed 91 committed 101, i.e. the content jumped *forward* at finger-lift. The comment two lines above the bug asserted the opposite outcome. **The fix removes the subtraction entirely** rather than moving the origin somewhere that survives: live and committed are then the same number by construction instead of two pieces of code agreeing, and the jump moves to pan *start*, where it reads as the drag catching. The obvious way to have both — `DragGesture(minimumDistance: 0)`, no threshold at all — was **built and measured**: it makes the double-tap a byte-for-byte no-op, because a zero-distance drag claims the touch. So the threshold is load-bearing for criterion 2, and the start-jump is its price.
- **A gesture that committed during the fit animation was silently discarded.** `withAnimation`'s completion fires unconditionally and `.gesture` stays live for the whole spring, so a flick-pan finishing inside 350 ms wrote `zoom.settled` and was then overwritten by `fitToContent()`. Reproduced by widening the spring to 6 s. Fixed with a generation token the gesture bumps; the completion no-ops if it is stale. The same fix retires a second, quieter error in the neighbourhood: the two effect channels were **multiplied** and anchored on the gesture's anchor, while `ViewDelta` is defined about the viewport centre — so during any overlap the settling scale was anchored on the wrong point. They are now a disjunction, which makes "never both in flight" true rather than merely claimed.
- **Two of this story's own tests could not fail, and one of them is cited by a source comment.** `onlyTheFinalCumulativeValueIsApplied` re-created its subject inside the loop, so the loop *was* the single commit it compared against and the assertion reduced to `once == once`; it could not be repaired in place, because "applied exactly once" is a fact about how many times the **view** calls `commit`, which no package test can observe — it is replaced by the contract the view relies on (`commit` compounds). `theDeltaCarriesNoYFlip` asserted a property `ViewDelta`'s single scalar makes unrepresentable, and stayed green through a deliberate y-sign error that produced 15 failures elsewhere; deleted, and the citation in `StageTransform.viewDelta` corrected to name the differential test that does pin it. **That is eleven such tests across three stories.** The standing check — *what production code could I delete while this stays green?* — is now the cheapest review question in the repo.
- **The `.idle` accessibility hint was unreachable copy heading for ~75 translators.** The canvas exists only once something is drawn, and the only route to `.idle` clears the display on the way. The entry is deleted and `.idle` shares the stopped hint; the test that asserted three distinct hints was **keeping the dead string alive**, which is worth recording as its own small lesson — a test can preserve dead copy as easily as it can pin live behaviour.
- **Found by Sebastian in the running app, and not findable by anything this story automated**: during a pan the newly exposed strip showed the *pane* background rather than the mat, and only turned into mat when the commit re-rendered the field. `StageFieldView` fills the canvas, but it rides inside the layer the gesture moves, so it slides away from the edge it was covering. Fixed by painting the mat with `.background` **after** the effects, where it is sized to the layout bounds — which geometry effects do not change — so it stays still while the content moves over it. Worth recording for two reasons: the artefact exists only *during* a gesture, so every screenshot in this story's definition of done showed the correct committed state; and my own close-out note had generalised "the mat fills the vacated area" from a committed screenshot to the gesture, which is the same over-generalisation from a still image that ADR-024's review warned about in prose.

**One suggestion is deferred rather than fixed, and named for US-309**: the accessibility *string* is rebuilt on every body evaluation, so a run pays one `String(localized:)` per frame (plus a percent format once zoomed). The *summary* is not recomputed, so the headline criterion is untouched and VoiceOver stays quiet because the string is identical — but it is per-frame allocation on the path ADR-024 otherwise budgets carefully, and it belongs with the other measurements rather than behind a cache added on a guess.

**Correction (2026-08-18, found in the running app) — the mid-gesture decision above is reversed, and the reasoning that produced it was wrong in a way no test on this branch could see.**

This ADR chose to move the *already-rendered* canvas with `.scaleEffect`/`.offset` during a gesture, and rejected `swift-architect`'s in-renderer design on the grounds that a partial blit "uncovers area the raster never held" while "scaling the composed canvas moves everything together, so nothing inside it can be uncovered". **The second half is false.** A `Canvas` rasterises only its own bounds; content panned outside them is never drawn, so sliding the rendered layer back cannot reveal it. Sebastian reported both symptoms from the running app: the newly exposed strip showed the pane background instead of the mat, and — the substantive one — **content dragged back into frame stayed missing until the gesture ended**. The architect's objection was the right objection; I had narrowed it to "the field and the stitches stay aligned with each other", which is a different and much weaker claim.

What ships instead is that design without its blit: `StageRenderTransform` carries **two** transforms, `bake` and `current`. The frame is re-stroked at `current` every frame, so it can draw whatever is now on screen; `CanvasStitchLayers.BakeKey` reads `bake`, which holds still, so the settled raster is **not** rasterised again until the gesture commits. That is what criterion 3 is actually protecting — the expensive half of ADR-009 — and the criterion's literal "blitted through the transform (a GPU scale)" is **not** delivered: the cached raster is skipped entirely while live, because its pixels were baked at a transform the frame is no longer using. Re-stroking the plan is the cheap half; at M3's ≤ 3 194 stitches it is unmeasurable, and it is exactly the mid-gesture path US-309 is already told to measure separately.

Consequences beyond the fix:

- **`StageZoom.previewing` is the same function `commit` calls**, so the frame the user sees mid-gesture and the transform they get on release cannot disagree. This branch had already shipped that disagreement once in the other direction (the threshold subtraction), so it is now a property rather than a discipline.
- **The fit animation had the identical defect and the identical fix.** A reset from a zoomed-in view is a zoom *out*, which by definition brings content into frame; animating `.scaleEffect` over a stale layer played it against blank edges. It now animates a `Double` through `StageTransform.interpolated(to:progress:)` and re-strokes each step, with `bake` frozen for the duration — so the reset also does not re-rasterise per frame.
- **`ViewDelta` is deleted.** It existed only to drive the effect channel; with the animation re-stroking, nothing constructs one, and dead public API in a package is worse than none.
- **The `.background(StageChrome.outsideField)` behind the canvas stays**, and is now the belt to the re-stroke's braces: the field is drawn by the canvas at `current`, and the background guarantees that anything outside the canvas's own bounds is still the stage's own colour rather than the pane's.

**The process lesson is the one this repo keeps relearning, in a new place.** Every screenshot in this story's definition of done showed the *committed* state, and both defects exist only *during* a gesture — so a definition of done built on stills could not have caught either, however many were taken. The mid-drag frame now in `docs/screenshots/us-307/` was captured by sampling the simulator continuously through a scripted drag, which is what it takes to photograph a transient. And the argument that dismissed the architect's objection was mine, written with confidence, and never executed.

**Correction (2026-08-18, after six review rounds) — the interaction layer was replaced rather than patched a seventh time, and the reason is the pattern, not any single defect.**

Everything above about *what* the stage does is unchanged: the zoom bounds rule, the 1.5× step, the freeze-the-bake raster policy, the accessibility summary, the identity-gesture guard. What changed is where that lives.

**The evidence.** The cross-vendor loop ran six rounds at flat Medium severity, 18 findings, none rejected — and three of six rounds found a defect in the *immediately preceding round's fix*. More telling, **four findings were the same conceptual mistake in four different spellings**: `current == committed` (true when a gesture returns to its baseline), `live != LiveGesture()` (false for a pinch back to exactly 1×), `next != fit` (defeated by one ULP on an asymmetric fit), and `overriding(committed)` (faked a baseline and erased "following the fit", so the guard could not fire). Each is a **value standing in for a lifecycle**; each fix was local and correct; each was followed by the next instance one round later. A seventh patch would have been the wrong move — that is a representation problem, and the representation was the thing to change.

**What the representation was.** Five pieces of state in a SwiftUI view — a `@GestureState` of live gesture values, a `@State` fit animation, a `@State` generation token to disarm stale completions, the committed `StageZoom`, and three derived expressions (`isInteracting`, the live transform, the `.settled`/`.live` choice) — with the invariants between them maintained by hand across four methods. **None of it was reachable by a test.** Every one of the 18 findings was found by *reading*, and every fix verified by *reading*, which is the deeper indictment: the area with the highest defect rate on the branch had zero automated cover, and no amount of care substitutes for that.

**What ships.** `StageInteraction` owns both where the stage is (`settled`, `nil` meaning follow the fit) and what is happening to it (`Phase`: `.idle` or `.settling(from:to:progress:)`).

- **One method decides the bake/draw split.** `rendering(gesture:fitting:in:)` returns `.settled` only when nothing is in flight — never inferred from two transforms being equal, which is what let a rasterisation land in the middle of a gesture.
- **The phase enum makes a gesture and an animation mutually exclusive**, where before they could overlap and the composing code had to decide which won. Interrupting is one method (`interrupt`) rather than one rule per caller.
- **~~`finishSettling` is idempotent, and that is what replaces the generation token.~~ Retracted — see the correction below.** The claim was that being inert when nothing is settling removes the need for a token. It does not: idempotence cannot tell *which* animation a completion belongs to, so a completion from an interrupted animation ended whichever animation was running instead. The token was ownership, not bookkeeping, and it is back as an id inside `Phase.settling` — where, unlike the `@State` counter it replaced, a test can reach it.
- **Liveness is an `Optional`.** The view keeps `@GestureState private var gesture: StageGesture?`, whose presence SwiftUI sets and clears — including for a cancelled gesture. An optional cannot be wrong the way a value comparison can.
- **One function reads the gesture**, used by `.updating` and `.onEnded` both, because the live frame and the commit reading the same event two different ways is precisely the class of bug being retired.
- Deleted with it: `StageZoom`, `LiveGesture`, `SettlingFit`, `StageInterpolatedCanvas`, `ViewDelta`, and the generation token.

**And it is now tested.** Twenty tests cover behaviour that previously had none — liveness by presence rather than magnitude, preview/commit agreement across a spread of gestures against both a symmetric and an asymmetric fit, a gesture interrupting the animation, an adjustment surviving a stale completion, and each earlier round's regression named after the round that found it. Verified on the simulator besides: content is re-drawn as it returns into frame, and double-tap restores the fit *byte-identically* to the fitted screenshot.

**The generalisable lesson, and it is the story's most useful output.** When you need to know whether something is happening, **ask the thing, not its output**: a value that usually differs during an event is not a substitute for the event. And when a review loop keeps finding one *kind* of defect at a flat severity, the severity number is the wrong signal to read — the *recursion* is. Three rounds in a row finding a defect in the previous round's fix says the area is mis-modelled, and no further round of patching will say anything different.

**Correction (2026-08-19, Codex rounds 7 and 8) — two claims in the rewrite above were wrong, and the second was a regression the rewrite introduced.**

- **Idempotence is not ownership.** The text above said making `finishSettling` idempotent replaced the generation token it deleted. Idempotence protects a late completion only when *nothing* is settling; it cannot distinguish "my animation" from "a newer one". Begin a reset, interrupt it with a gesture, begin another, and the first completion ended the second a third of the way through. `Phase.settling` now carries a monotonic `id`, `beginSettling` returns it, and `finishSettling(_:)` acts only for a matching id. That is the token again — but *inside the value*, where a test reaches it, rather than as a `@State` counter beside four other pieces of view state. The improvement was consolidation, not the deletion of the concept, and claiming otherwise was over-reach.
- **The rewrite silently turned the fit animation into a snap.** Deleting `StageInterpolatedCanvas` removed the only `Animatable` conformance in the stage. `withAnimation` interpolates animatable *view* data; a `StageTransform` is not animatable and a `Canvas` re-strokes from whatever it is handed, so nothing interpolated and the reset jumped. **No test could see it** — they only ever observed progress 0 and 1, which is exactly the shape of a snap. The shim is restored in the view, where SwiftUI requires it, while the endpoints stay in the model.
- **And the progress split has a consequence worth pinning**: `withAnimation` sets the *model's* progress to 1 immediately, so only the view's shim holds the interpolated value. An interruption therefore has to be told what is on screen — `interrupt(settlingAt:)`, `commit(…settlingAt:)` and `adjust(…settlingAt:)` all take it — or it adopts the destination and the stage snaps from what the user can see to the fit before their gesture applies. At progress 1 the destination *is* correct and the stage returns to following the fit; below 1 the visible transform becomes the user's explicit one, because they took control of something mid-flight. Every earlier test drove `settlingProgressed(to: 0.5)`, which makes the stored and visible values agree and hides the whole class; the tests now reproduce the real path, stored 1 against visible 0.5.

**The lesson these two rounds add to the one above.** Consolidating scattered state was right, and it did retire the recurring bug class — but a rewrite is not self-verifying, and its author is the worst-placed person to notice what it quietly dropped. Both defects here were *deletions*: a concept (ownership) removed because it looked like bookkeeping, and a type (the `Animatable` shim) removed because it looked like scaffolding. **When a rewrite deletes something, the question to answer in writing is what that thing was load-bearing for** — and if the answer is "nothing", a test should be able to show it.

## ADR-029 — The 50 000-stitch measurement: what was proved headlessly, what needs a device, and the fallback ladder (2026-09-01)

**Context**: ADR-009 bet that a SwiftUI `Canvas` drawing one batched `Path` per colour run — with settled stitches rasterised to a cached image and only the live tail redrawn — would hold 60 fps at 50 000 stitches on an A15-class device. That bet was made on *reference analysis* (Catty's node-per-stitch collapse, Catroid's batched renderer) and had never been measured against our own code. US-309 closes its **headless** half; the authoritative device capture is an explicit outstanding hand-off, so the bet is not yet settled. *(Corrected 2026-09-02, Codex round 1: this said "US-309 closes it", which overclaims — the sentence the rest of this ADR spends its length qualifying.)* The story as written assumed the risk was the settled 50k frame; measurement says otherwise, and this ADR records what actually holds the claim up.

**Decision**: the exit criterion is split into a part that is proved on the fast gate and a part that only a device can answer, and each is stated as the thing it actually is.

- **The pass/fail bar is fixed before measuring, and is the criterion's own numbers verbatim**: over a ≥ 10 s capture, **p99 ≤ 16.67 ms and no frame > 33.3 ms**, reported as median / p95 / p99 / worst. `FrameTimeStatistics` is that bar in code. The constants are written as **16.67 and 33.3, deliberately not `1000.0/60` and twice it** — the 3.3 µs difference decides the result, because a display link on a 60 Hz display reports a nominal 16.6667 ms with jitter that is not symmetric about the period. Measured on the simulator rehearsal, before any device was involved: 1 196 frames, every one on time, `p99 16.7 · FAIL`.
- **Per-frame independence is proved headlessly, and the criterion's claim is restated because as written it is false.** AC4 says per-frame work is "independent of total stitch count". It is independent of the **settled** count at a **fixed colour-run count**, and **grows with the colour-run count** — `StitchDrawPlan.planning` walks `colorRuns` twice, so a design changing colour every stitch has `colorRuns == count` and a per-frame cost that grows with n after all. Re-measured with each figure attached to its fixture (50 000 settled, 100-stitch tail): **0.041 ms at one colour run, 0.246 ms at 1 000, 9.791 ms at 50 000**. *(Corrected 2026-09-02: this previously read "linear in colour runs" and quoted "0.0013 ms against 0.3945 ms, a 300× spread" — a figure that named no fixture and which a reviewer then read as applying to the 1 000-run comparison, producing a bound the code fails. The assertions establish **not-quadratic over the measured range**, not linearity: an O(r log r) implementation would pass them, and bounding that out would need a third point and a far more delicate instrument than a wall-clock ratio on a shared runner — this branch has had five such ratios refuted by CI.)*. Both halves are asserted. The discriminating test is *structural*, not timed: at 50 000 settled with a 100-stitch tail the live plan touches exactly 100 dots and ≤ 101 segments.
- **The device cannot discriminate that claim**, which is why it is not asked to. The difference between a 5 000- and a 50 000-stitch settled frame is one copy-on-write of the display list buffer — **measured at 12.7 µs, 0.08 % of a frame** — plus compositing a larger raster. A p99 comparison would come out "the same" whether ADR-009 held or not. The device measures the absolute bar; the fast gate tests the claim.
- **The headless throughput guard is a ratio, not a wall clock.** For a step of k, linear predicts k and quadratic k², so the bound equidistant from both in log space is k^1.5. At a 16× step: bound 64, healthy ~9.9, quadratic mutant **255.08** against a theoretical 256.

**What measurement moved, against what the story expected.** The settled 50k frame is *trivially* cheap — 0.0013 ms of planning. The two real risks are elsewhere and neither is named in the story:

1. **The mid-gesture path.** ADR-028 reversed the blit, so while a gesture is live `canUseRaster` is false and every frame takes `.entire(of:)`: **0.45 ms of planning at 50k** against the settled frame, before a 50 000-segment `Path` and 50 000 ellipses. *(Corrected 2026-09-03, US-310 planning: this said "against 0.0013 ms settled, **350×**", quoting a figure this same ADR corrects two paragraphs above for naming no fixture. The comparable settled number is **0.041 ms** at 50 000 settled with a 100-stitch tail at one colour run, so the planning ratio is ~11×, not 350×. The 350× figure also reached `milestone-3/README.md` and US-309's AC5.)* `StageRenderTransform`'s comment calling this "cheap at the counts M3 reaches" was written against 2 976 stitches; US-309 is what invalidates it. **AC5 asks to tune "the mid-gesture blit from US-307", which does not exist** — ADR-028 deleted it — so the criterion is retargeted to measuring the full re-stroke that was left behind.
2. **The bake schedule is Θ(n²/chunk).** `CanvasStitchLayers` re-bakes whenever `settledCount` changes and a bake re-rasterises the **whole settled prefix**, so a fixed chunk costs Σ chunk·k. At 50 000 that is **fifty** full rasterisations — `settleChunk`'s own comment said "a handful per run", measured against 3 194-stitch samples — and the last one plans the entire design on a single frame near the end of every long run, a dropped frame no capture taken *after* settling could see. In plan work alone: **26.4 ms at chunk 1 000 against 5.4 ms at 5 000**.

**Why the constant did not move, which is a negative result worth keeping.** The proportional chunk the Θ(n²/chunk) finding seems to call for was implemented and measured: at `count / 8` a 50 000-stitch run baked **176** times, not fifty, because a chunk tracking a continuously growing count moves the watermark on nearly every batch. A geometric schedule does bound the count (~10 bakes at ratio 1.5) but only by letting the live tail reach a third of the design — stroking 16 000 segments *per frame* at 50k, the exact cost ADR-009 exists to avoid. **The trade is one-dimensional**: bake work falls as the chunk grows, per-frame tail work rises with it, and the balance point is where one full rasterisation costs what (chunk × frames) of tail stroking costs. *(Corrected 2026-09-02, Codex round 1 finding 7: this sentence said "both sides are GPU-bound", which would send a reader tuning the wrong half. **Each side is part CPU and part GPU**, and the figures quoted here are CPU figures — `StitchDrawPlan.planning` and `CanvasStitchLayers.stroke` run synchronously on the main thread, so 26.4 ms of plan work and 0.45 ms of mid-gesture planning are main-thread milliseconds. The rasterisation those plans drive is the GPU half. What is genuinely true is the next sentence: the *balance point* depends on the GPU half and so cannot be located headlessly.)* Nothing headless locates it. So the fixed chunk stays — it is the tail-optimal end, and the end ADR-009's per-frame claim rests on — and `settleChunk` is the device session's first knob. Raising it flat is separately impossible: at 5 000 neither shipping sample (2 976 and 3 194) would settle at all, undoing US-306. What *did* land is `PreviewRunState.settleWatermark(for:)`: the rule is now a public pure function, assertable rather than only observable. *(2026-09-02: the review found this ADR's "the fixed chunk stays" to be the correct account while `settleChunk`'s own doc comment claimed US-309 had changed it "from a fixed chunk to a proportional one" — stale prose from the abandoned attempt, sitting directly above the line a future reader would edit, and naming a `maximumBakesPerRun` that never existed. The comment now says what this ADR says, and says outright not to restore a proportional chunk without a device measurement that beats the fixed one. The failure it was one edit away from: this negative result quietly undone by its own comment.)*

**The measurement fixture.** `makeUS309SyntheticProgram()` in `Samples` (ProgramModel-only, so ADR-016's arrow is untouched) plus `SyntheticDesign` in `StagePreviewTests`. Every constant sits half a stitch length off a `floor(distance/length)` boundary (ADR-019), which is what makes the count reproducible under trig rounding; the row spacing is deliberately *shorter* than the stitch length so the inter-row move emits nothing and each row is worth exactly 200 stitches. It is reachable in the app through a `#if DEBUG` `SampleID` case appended by `AppModel`, never by `SampleLibrary.all` — five `SamplesTests` suites iterate that array to assert properties of shipping content, and ROADMAP M3 requires bundled samples to be visually appealing designs "not test shapes". `SampleID.shipping` is the new split, and it is the useful part: `allCases` answers "what can this enum be" and `shipping` answers "what is in the library", and two suites asked the first while meaning the second. **One caveat, recorded because "compiled out of Release" is not the whole story** (`swift-code-reviewer`, triaged 2026-09-02): `SampleID` is `Codable` over a `String` raw value this codebase documents as an M5 *persistence token*, so a debug-only case is a live trap the moment M5 stores a selected id — a token written by a debug build is undecodable in Release, i.e. a decode failure on a user's own stored state caused by a case that build cannot see. It is harmless today only because the app target persists nothing at all (grepped: no `AppStorage`, `SceneStorage`, `UserDefaults` or `JSONEncoder`), which is a property of today's app and not an enforced invariant. **M5 must decode this token defensively**, falling back to a shipping sample on an unknown raw value rather than throwing; the constraint is written on `SampleID.us309Synthetic` itself so it is read where it would be broken.

**Five colour bands, not one.** A single-colour 50 000-stitch hatch screenshots as a featureless black rectangle — fifty thousand stitches in a 100 mm hoop *is* a solid fill — and leaves the one dependence ADR-009's claim actually has (colour-run count) entirely unexercised at scale.

**Fallback ladder, in the order it is to be taken if the bar is missed.** ADR-009 kept this escape hatch open precisely for this, and naming the rungs now is what stops the criterion being quietly reworded later.
1. **Tune `settleChunk`** — one constant, and the measurement above says the bake side has 5× in it. Cheapest, and the only rung that needs no new code.
2. **Coarsen the mid-gesture path** — plan a decimated `.entire` while `canUseRaster` is false (draw every k-th segment). A `StitchDrawPlan` change, in the package, on the fast gate. This is the rung the mid-gesture measurement points at. *(Corrected 2026-09-03 by ADR-030, which took this rung: "draw every k-th segment" is **dashing** — it leaves k−1 stitch lengths of blank fabric between drawn segments — and it says nothing about the dots, which are plausibly the larger half of the cost. What shipped joins stitch `a → b` so the thread stays continuous, and strides the dots per colour run. A literal implementation of this line would have looked wrong and saved less.)*
3. **`Path` reuse across frames**, keyed on the plan.
4. **`MetalStitchRenderer` behind `StagePreviewRenderer`** — ADR-009's escape hatch. A milestone of its own, filed as a backlog story rather than taken inside a 4 h story.

**A limitation of the instrument, found by Codex round 1 and load-bearing for how the device numbers may be read.** A `CADisplayLink` callback fires once per display refresh **whether or not the app submitted new content**, and SwiftUI redraws a `Canvas` only when something invalidates it. On a settled 50 000-stitch stage nothing does — no run is advancing, no gesture is live — so captures 1–3 of the hand-off can return a flawless `p99 16.7 · PASS` while the renderer is asked for **zero** frames. Such a capture measures the display's refresh cadence, which was never in question, and says nothing whatever about ADR-009's claim. This is not hypothetical: it is the *expected* behaviour of a static stage, and it would have been mistaken for the criterion being met.

**Confirmed on the simulator, and the numbers are the point.** At 50 000 settled, static: `n=1048 drawn=0 60Hz med 16.7 p95 16.7 p99 16.7 max 16.7@0.1s · 17.5 s · NO DRAWS`. One thousand and forty-eight consecutive frames, every one on time, **zero draws** — a flawless capture of nothing. The same fixture *animating*: `n=2123 drawn=251 60Hz med 16.7 p95 61.9 p99 66.5 max 75.7@23.8s · 37.0 s · FAIL`. So the two captures differ by `PASS` versus `FAIL` and by a **p99 of 16.7 against 66.5 ms**, and the earlier version of this story's screenshot recorded the first one as evidence for ADR-009. (Simulator numbers, non-authoritative for the bar — a host GPU is not an A15 — but the *draw counts* and the shape of the difference are structural and carry over.)

Three consequences, all now in place. (1) `StageDrawCounter` counts `CanvasStitchLayers` draw passes; the recorder tags **each interval** with whether the canvas drew during it, and every capture reports `drawn=` beside `n=` **and takes its quantiles from the drawn frames alone** — a capture with no drawn frame is labelled **`NO DRAWS`** rather than scored. The drawn subset is not a refinement but the whole point: even mid-run the canvas redraws once per batch rather than once per refresh (251 of 2 123 frames), so a whole-capture p95 of 16.7 ms and a drawn-frame p95 of 61.9 ms are the same capture. (2) **Captures 4 (mid-gesture) and 5 (animating) are the authoritative ones for ADR-009**, because only they cause the canvas to redraw at all. *(Corrected 2026-09-02, Codex round 2: this said they "force a redraw every frame", which this ADR's own figures disprove — the animating capture drew **251 times in 2 123 frames**, because a run advances in batches and SwiftUI redraws once per batch, not once per refresh. Only a live gesture plausibly redraws every frame. The consequence is larger than the wording: since even the authoritative captures are mostly idle frames, **a p99 over all frames flatters the renderer by the idle fraction**, so the recorder now tags each interval with whether the canvas drew in it and the bar is evaluated over the drawn frames alone. The readout shows `drawn=` beside `n=`.)* Captures 1–3 are demoted to what they can actually prove: that a settled stage introduces no *background* stutter, and that the display kept up. (3) The Instruments trace is therefore not an optional cross-check on the settled captures; it is the only mechanism that observes the rendering pipeline directly, so it is required for captures 4 and 5. **The 60 fps claim in the thesis must rest on captures 4 and 5, not on 1–3.**

One further lead for the device session, from the animating capture above: the worst frame fell at **23.8 s into a 37.0 s capture** (the figure was 22.4 s of 33.7 s before the instrument was corrected twice over; the phenomenon is the same one). *(Corrected 2026-09-02, Codex round 2 finding 4: an earlier version of this sentence continued "which is after the ~17 s run had finished", and **it cannot know that**. ADR-027's producer and consumer are separate tasks over an unbounded `AsyncStream`, so the producer finishing at ~17 s does not mean the consumer has drained its buffer — the stage can still be visibly animating well past that, and `worstAtMilliseconds` carries no run-state marker to say otherwise. The position is a fact; "after the run" was an inference presented as one.)* The candidates are the last and largest bake of the Θ(n²/chunk) schedule, ADR-026's **eager export preparation** — which serialises all 50 000 stitches on the main thread at terminal delivery — and an ordinary mid-run bake if the consumer was still draining. **Distinguishing them needs a run-state marker in the capture, which the recorder does not have**; that is the cheapest thing to add if the device session wants the answer, and until then the trace of capture 5 is what can settle it. If it turns out to be the export, it is a finding about ADR-026 rather than about ADR-009.

Relatedly, the recorder now reports the display's **nominal refresh rate**, because iOS may drop a display link to 30, 20 or 15 Hz under Low Power Mode, a critical thermal state, or the "Limit Frame Rate" accessibility setting. At 30 Hz every interval is ~33.3 ms and a renderer doing no work fails *both* halves of AC3's bar — an unforced FAIL indistinguishable from a real one, and the hand-off now fixes the device conditions and asks for the rate to be recorded.

The mid-gesture capture is a median of **69.1 ms** — about **14 fps** — which is what ADR-028's removal of the blit implies: while a gesture is live `canUseRaster` is false and every frame re-strokes all 50 000 stitches. **The failure is decisive despite the hardware being wrong for the criterion.** AC2 asks for A15-class; an iPhone 17 Pro is several generations faster. A *pass* there would say nothing about an A15 — but a **fail** cannot be blamed on the device, so the negative result stands without an A15. An A15 is still required later, to confirm a fix.

Backlog US-313 (native two-finger gesture) is sequenced *after* or *with* rung 2, since a more responsive gesture exposes this cost more often rather than less.

**Two findings about the criterion itself, recorded rather than acted on.** (1) **The `p99 ≤ 16.67 ms` half has no discriminating power at 60 Hz.** The animating capture was taken twice: the first read `FAIL`, the second `PASS`, same scenario, decided in the *third decimal* by display-link jitter about a 16.6667 ms period. The half that carries information is "no frame exceeds 33.3 ms", which the animating capture clears by a factor of two. (2) **The settled capture would have read `PASS` under the pre-review instrument** — p99 16.669 is under the bar and its worst frame, 16.725 ms, is *worse than the animating capture's* while the renderer ran **zero** times. That is the false positive this ADR's draw counting exists to prevent, now demonstrated on hardware rather than argued. **The bar is not reworded** (AC8 forbids exactly that); both are open questions for the author.

An incidental corroboration worth keeping: `drawn=251` on the device and `drawn=251` on the simulator, from different machines and different capture lengths — because the draw count is set by the batch count, not by speed. Two independent platforms agreeing on it is evidence the counter measures what it claims.

**Consequences**: the exit criterion's headless half is on the pre-commit gate and defended on every commit; its device half is a stated hand-off with a fixed protocol (`docs/us-309-device-handoff.md`). The measurement build is a **Release** build with `DEBUG` defined on the command line — command-line build settings are global overrides, so one flag reaches the package targets too — which keeps the optimiser on while leaving the fixture and the recorder reachable. ADR-021's `assembled()` figure is corrected in place: it was a Mac number presented with an unstated ~2.6× A15 extrapolation.

## ADR-030 — Coarsening the mid-gesture plan: continuity over dashing, and two constants instead of one (2026-09-03)

**Context**: ADR-029's device measurement answered the M3 exit criterion "half no". Animating to 50 000 stitches passes on an iPhone 17 Pro; **mid-gesture fails at a median of 69.1 ms**, about 14 fps, because ADR-028 deliberately removed the mid-gesture blit — while an interaction is live `StageRenderTransform.canUseRaster` is `false` and every frame takes `StitchDrawPlan.entire(of:)` over the whole design. ADR-029 re-ordered its own fallback ladder on that data and named **rung 2**: "coarsen the mid-gesture path — plan a decimated `.entire` while `canUseRaster` is false (draw every k-th segment). A `StitchDrawPlan` change, in the package, on the fast gate." US-310 is that rung. This ADR pins the semantics; ADR-029 remains the measurement record.

**The premise was checked before the type change, with the decision rule fixed in advance**, because it was a hypothesis and ADR-029 contains evidence against it: the bake schedule strokes the same ~50 000 stitches up to fifty times per run, yet the animating capture's *worst* frame over 251 drawn frames was 16.703 ms — which a 69 ms full re-stroke does not obviously permit, and ADR-029 never reconciles the two. The rule: measure the mid-gesture drawn-frame median at **two** stitch counts on one instrument; a count-independent overhead predicts equal medians, a per-primitive cost predicts growth. Measured on the simulator (iPhone 17, Release with `DEBUG`, 60 Hz, three 4 s scripted drags): **3 194 stitches → median 16.667 ms** (one refresh period, which is the instrument's floor) and **50 001 → 36.129 ms**, with `drawn` 231 against 230 — the same number of drawn frames, because the redraw count is set by the touch-move rate rather than the refresh rate. Growth, so the premise holds; decomposed as `C + p·n` that is `p ≥ 0.416 µs` per stitch, **at least 57 %** of the frame scaling with the count, and `C ≤ 15.4 ms`.

**Decision**:

- **Coarsen, do not dash.** ADR-029's literal wording — every k-th segment — leaves k−1 stitch lengths of blank fabric between drawn segments and saves nothing on the dots. A coarse thread segment instead spans stitch `a → b` with `b − a ≤ stride`, so the thread stays continuous through subsampled vertices. **The rung-2 wording in ADR-029 is corrected by this ADR, not reinterpreted.**
- **The planner stays internal, and that had to be spelled out.** `planning` and
  `lastSegment(before:)` were `private` before this story and needed to be reachable from a second
  file; dropping `private` inside a **`public extension`** makes a member *public*, which review
  caught by compiling a call to it from the test module without `@testable`. A public `planning`
  would be a public constructor for arbitrary plans at a caller-chosen window and stride —
  exactly the chokepoint `Stroke` and `DotRun` give up their memberwise initializers to keep — and
  it made `stride: 0` and `stride: .max` reachable from outside, which in turn made a latent
  overflow in `DotRun.count` reachable. Both are fixed, and both keywords are now explicit so the
  next edit cannot widen them by omission.
- **`Stroke.segmentStarts: [Int]` becomes `segments: [Segment]`, an explicit index pair.** The old contract was "segment `i` spans stitch `i → i + 1`", which is exactly the assumption a stride breaks; a stride is not expressible in one index. In `.entire`, `.settled` and `.live` every segment still satisfies `to == from + 1`, and that is asserted — a stride leaking into a fine window would leave every suite that reads `from` green while the thread rendered in dashes. `Segment` is a sibling of `Stroke`, not nested in it, because SwiftLint's one-level nesting limit is enforced by `--strict` in CI, and it has a public initializer where `Stroke` and `DotRun` deliberately do not: those two exist to make "never empty, never `.suppressed`" unrepresentable and a pair of indices has nothing equivalent to protect.
- **A polyline representation is rejected *now* and is rung 3's natural shape.** It would halve the vertex count even at stride 1, but `segmentPath`'s per-subpath `guard from.isDrawable, to.isDrawable` currently loses exactly **one** segment when a coordinate is non-finite — which ADR-021 divergence #5 deliberately permits — and a polyline would let one bad coordinate delete a whole colour run's thread. Rung 3 must pay for that hardening.
- **The coarse-span rule, verbatim, because it is what keeps ADR-024 true under decimation**: *a thread segment is emitted only if every stitch interval it spans classifies `.thread`, and both endpoints lie in one colour run.* An open span is closed at travel and at a colour boundary rather than drawn through it. **Traversals are never merged**: joining across one draws thread where the machine only travels — the defect ADR-024 records in *both* references — and merging two erases the needle penetration between them.
- **Dots are strided per colour run, anchored at each run's own `lowerBound`.** A global `index % stride == 0` rule drops every dot of a run shorter than the stride, so a thread colour vanishes the instant a finger lands; per-run anchoring makes "every colour run keeps at least one dot" true by construction, including at run length 1. `DotRun` stays a `Range` plus a stride rather than an array of selected indices: an array would allocate up to 50 000 `Int`s per plan in the **un-coarsened** paths — every settled bake — turning a live-path fix into a settled-path regression. A stored `StrideTo<Int>` is not `Equatable` and would break `StitchDrawPlan: Equatable`.
- **Suppressing the dots mid-gesture is rejected.** Dot radius equals thread width, so the dots are the beading that makes penetration points read as points; suppressing them makes the design visibly *thinner* the moment a gesture starts, which is a larger visual delta than sparser beading for one further constant factor.
- **Two constants, not one, and the measurement is what forced it.** A single "budget" had to be simultaneously the floor that keeps the 3 194-stitch rosette untouched (so ≥ 3 194) and the segment count a large design aims for (which the sweep puts near 1 000). No single number satisfies both. So **`liveCoarseningThreshold = 4_000`** decides *whether* to coarsen and **`liveSegmentTarget = 1_000`** decides *how much*, with `coarseningStride(forStitchCount:target:)` as a **public pure function** — US-309's survivor lesson applied on day one, where a test that restated the settle rule instead of observing it passed the mutant.
- **The stride is discontinuous at the threshold**, and that is recorded rather than hidden: a 4 000-stitch design draws every stitch, a 4 001-stitch one strides by 5. It lasts only while a finger is down, and the alternative was a default that provably does not reach one frame period at 50 000 stitches.
- **The window choice is one package function on `canUseRaster == false`**, `forFrame(of:at:compositingRaster:threshold:target:)`, and the liveness guard comes **first** so a caller passing `compositingRaster: true` with a live transform still gets the coarse plan. The renderer's previous branch asked "did we get a usable raster?", which is a *different question*: that branch is also taken when the settled prefix is too short to bake, or the bake key is stale, or the `Canvas` is not the size the raster was rendered at — none of which is an interaction, and none of which should cost fidelity. Putting the choice in the package also puts it on the fast gate (ADR-023) instead of in a `private` SwiftUI view where only a hosted, drawn `Canvas` could observe it.
- **`canUseRaster == false` is a gesture *or* the fit animation.** `StageInteraction.rendering` reports `.live` while a gesture is in flight *or* while the fit spring is settling; both are per-frame full re-strokes, so both get the coarse window. The settle is also the only deterministic way to put the coarse plan on screen for a screenshot. Nothing in this ADR may be described as "gesture-only".
- **There is no spatial seam**, because the coarse plan is selected only when no raster may be composited, so it is always drawn alone and covers the whole list. The seam is **temporal** — a fidelity pop at interaction start and again at commit — and it is the same class of trade ADR-028 already took when it accepted that off-screen content is revealed only as frames re-stroke. `StitchDrawPlan+Planning.swift`'s "one planner parameterised by two windows rather than three implementations" argument survives intact: `coarse` is that planner at a stride above 1, and the identity `coarse(target: .max) == entire` is what keeps it true under refactoring — **that spelling and not `threshold: .max`**, which never enters the stride path at all and so pins only the gate (`swift-code-reviewer`; both cases are now asserted).

**The median mid-gesture frame now fits inside one refresh period** at the shipped **stride of 51**, and stride 201 reads no better. *(Corrected 2026-09-03, `swift-code-reviewer`: an earlier version said "the knob has a knee: stride 50 achieves it" — two errors in one clause. The stride at a target of 1 000 over 50 001 stitches is **51**, which the table above already prints; and limitation (1) below makes a *knee* unlocatable by this instrument, since strides 51 and 201 both read the refresh floor and the transition lies anywhere in (13, 51]. The preference for 1 000 over 250 rests on fidelity, not on a knee.)* **The tail does not respond to the stride at any of the four values** — p99 moves 46.7 / 52.9 / 49.2 with no ordering — so it is *not* the coarse plan. The candidates are the gesture-end commit and the full re-bake it triggers (three drags, three commits, and p99 of 231 drawn frames is the second or third worst frame), which is rung 1's and ADR-029's Θ(n²/chunk) territory rather than this rung's. **This ADR therefore claims the median and explicitly does not claim the tail.**

**Two limitations on what these numbers can mean.** (1) A display-link interval can only report **multiples of the refresh period**: 16.667, 33.333, 50.0. A frame costing 18 ms and one costing 33 ms both read 33.333, which is why the target-4 000 row is "still two periods" rather than a measurement of its cost. (2) These are **simulator** numbers and non-authoritative for ADR-029's bar — the device read 69.1 ms where the simulator reads 36.1, so the device is roughly 1.9× slower on this path and the shipped target may not be small enough there. What carries is the structure: same instrument, same draw count, cost responds to the stride. **The device capture and a budget sweep of at least two values remain a stated hand-off**, and the A15 confirmation stays a milestone-level item.

**An interval the machine cannot reach is not planned at all, and "reach" is the test — not "is finite".** ADR-021 divergence #5 lets a coordinate the *stream* rejects into the display list, and `EmbroideryStream.requiresTraversal` answers `false` for one it cannot convert — it has no distance to compare — so `classifying` calls both intervals touching such a stitch `.thread`. The fine plan emits them and `segmentPath` then skips each subpath on `isDrawable`, so **nothing is drawn there in either plan**; a coarse span joining *over* the bad vertex, however, has two finite endpoints and would be drawn as one solid line across ground the machine only travels. Spans therefore break at such a vertex, and **while coarsening** the interval itself is dropped rather than emitted — *only* while coarsening: at stride 1 nothing merges, so nothing may be dropped, or `.entire`/`.settled`/`.live` would stop showing stitches ADR-021 requires the display list to show.

**Two cases hide under "rejected coordinate", and they must not be conflated** (`/codex-review` round 5 caught this paragraph doing exactly that, one clause after correcting it):

- **Non-finite** (`NaN`, `±∞`). The mapped view point is non-finite too, so `segmentPath` skips it in *every* plan. Dropping such an interval while coarsening costs **no pixels at all** — nothing was ever drawn there.
- **Finite but unconvertible** (magnitude past `Int64.max / 2`). `EmbroideryPoint(converting:)` rejects it, so the replay never goes there and no span may cross it — but at a small scale it still maps to a finite view point, so the *fine* plan genuinely draws it. Dropping it while coarsening therefore **does** cost a segment: one that sits some 10^17 view points off-screen, which is a fidelity trade a live frame is already making, and which the fine windows keep.

So **conversion rejection is not the same as view-space undrawability**, and a joinability rule that decided *emission* rather than *merging* silently changed the fine windows (`/codex-review` round 4, against round 3's own fix). The predicate is **`EmbroideryPoint(converting:)`, exactly what `requiresTraversal` consults** — ADR-020's range guard — and *not* plain finiteness: `1e307` is a finite `Double` that the machine cannot reach and that maps to a non-finite view point at `StageTransform.maximumScale`, so a finiteness test permits a span straight across it while the fine plan draws neither adjacent interval. Reachability also keeps the plan **transform-free**, which `StitchDrawPlan`'s type doc requires: joinability cannot depend on the transform even though the defect was found through one. *(Three corrections in one, all from `/codex-review`: round 1 found the defect — coarsening could draw thread across travel where the fine plan drew nothing — and round 2 found that the first fix, which emitted those intervals individually to keep the coarse plan's *interval* coverage identical, gives a 50 000-stitch list of rejected coordinates 49 999 segments and defeats the bound below on exactly the input coarsening exists to survive. Dropping them costs no pixels. What the coarse plan matches is the fine plan's **drawn** coverage, not its emitted coverage. Round 3 then found that stage-space finiteness is the wrong predicate — a finite-but-unreachable coordinate reintroduces the same ADR-024 violation through the *transform* — and that the bound below still needed one more term.)*

**What the bound actually is**, stated because "≤ target" would be a false claim: **every break costs a partial span**, so thread segments are `≤ ceil(count/stride) + colorRuns + traversals + unreachableIntervals` and dots `≤ ceil(count/stride) + colorRuns`. *(The last term was added in round 3, after Codex constructed the case that refutes the shorter bound: a list alternating reachable and unreachable stitches breaks the span at every third interval, so it emits one short segment per drawable island — about 1 666 of them at 4 998 stitches — however large the stride is. Dropping the unreachable intervals had fixed the all-rejected extreme and left this one. A bound over a span-based scheme has to carry one term per thing that forces a break; that is now what it says, and it is asserted on a fixture built to maximise the new term.)* **A design that changes colour every stitch is not helped by this rung at all** — ADR-029 identifies the colour-run count as the one axis that genuinely grows, and it is out of reach here. Rungs 3 and 4 are where that case goes.

**US-313 inherits an invariant from this, and it is why the dependency is written down.** If US-313 satisfies "live two-finger centroid" by committing the transform *continuously*, `canUseRaster` becomes `true` mid-gesture: every frame then takes `.entire` **uncoarsened** *and* `BakeKey.transform` changes per frame, re-rasterising the settled prefix on every frame — **worse than today, on both counts**. ADR-028's one-commit-per-gesture rule is what makes this rung effective, and US-313 must preserve it or re-derive both consequences.

**Consequences**: ADR-009's batching claim is untouched — at most two strokes plus one dot path per colour run, asserted in the coarse plan too — and ADR-021 and ADR-024 are preserved by construction (no retained slice; no thread across travel). ADR-029's rung 2 wording is corrected here. A renderer-only alternative is recorded rather than taken: replacing `addEllipse` with `addRect` while live turns four cubics per dot into four lines with no plan change at all, untestable headlessly, and a legitimate device-session knob if the Instruments trace says the ellipses dominate. Rung 3 (`Path` reuse keyed on the plan) must key on the stride as well, and will see roughly fifty invalidations across a 50 000-stitch run.
