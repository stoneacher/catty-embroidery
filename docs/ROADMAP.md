# Roadmap — Embroidery Designer for iOS

Standalone native iOS app bringing Catrobat's embroidery functionality (Android "Embroidery Designer" flavor) to iOS: users program embroidery designs with visual blocks, watch the stitch preview on a stage, and export machine-readable Tajima DST files.

**Stack**: Swift 6, SwiftUI, min iOS 17. The engine (stitch domain, patterns, DST export, interpreter) lives in a platform-independent Swift Package (`EmbroideryEngine`) developed strictly test-first with `swift test`. License: AGPL-3.0 (Catrobat standard).

**Process**: TDD (failing tests first), user stories ≤ ~5 h, many small commits, one story per PR-sized unit of work. Stories for the *next* milestone are refined in detail; later milestones stay coarse until we get there.

**Engineering standards** (per the `swift-engineering` plugin skills — consult them while coding):
- **Swift Testing, not XCTest**: `@Test` / `#expect` / `#require`, parameterized tests via `@Test(arguments: zip(...))`. Tests run in parallel by default — they must not share mutable state or fixed file paths; serialize (`.serialized`) only as a last resort.
- **Swift 6 strict concurrency** enabled in the package from day one. Engine domain types are `Sendable` value types; the engine core stays synchronous and isolation-agnostic — actor/`@MainActor` decisions belong to the app layer (M3+), not the engine.
- Test fixtures load via `Bundle.module` (SPM resources); file-emitting tests write to unique temp URLs or assert on in-memory `Data`.
- App-layer side effects (file I/O, DST export/share, clock/sleep, UUID/date) sit behind small initializer-injected interfaces with deterministic test doubles (hand-rolled, no DI library — ADR-006). The engine takes no dependencies and performs no I/O.
- **Definition of done for every UI story (M3+)**: no hardcoded user-facing strings (String Catalog + translator comments; layout uses leading/trailing — Catrobat ships ~75 languages incl. RTL); loading/empty/error states shipped with the feature; animations respect Reduce Motion; basic VoiceOver pass (the stage canvas gets a summarizing label: stitch count, colors, size in mm); touch targets ≥ 44 pt; Dynamic Type to AX1 without truncation.

**Backlog**: fully analysed stories with no milestone yet live in [`user-stories/backlog.md`](user-stories/backlog.md); milestone planning assigns them a place. Written up at discovery time rather than left as journal carry-forwards, because the one carry-forward that was (the ±121 coordinate trap, 2026-07-09 → US-210) was mis-scoped twice by review before it became a correct story.

## Milestones

### M1 — Engine core (E1 + E2)
**Status**: Done — 2026-07-16. All ten stories (US-101–US-110) merged; exit criterion met (US-106 golden-file tests green in CI; generated DST verified in Ink/Stitch, see workflow journal 2026-07-09).

A pure Swift package that turns a programmatic sequence of needle movements into a **valid DST file**, byte-verified against the reference fixture from Catty (`CattyTests/Resources/EmbroideryReference/stitch.dst`) and the semantics of Catroid's `org.catrobat.catroid.embroidery`. No UI. CI runs `swift test` on every push.

**Exit criterion**: a DST file generated by our engine loads correctly in an embroidery viewer and matches golden-file expectations (header, stitch records, jumps, color changes, terminator).

### M2 — Interpreter MVP (E3)
**Status**: Done — 2026-07-31. All ten stories (US-201–US-210) merged; exit criterion met 2026-07-25 (see below). US-210 closed the last M1 carry-forward: the engine's coordinate boundary is a chokepoint no caller can crash or hang (ADR-020).

Program model (project → scene → object → scripts → bricks) plus a minimal interpreter executing headlessly: when-started script, move/turn/goto, repeat/wait, the eight embroidery bricks, and a formula subset (literals, arithmetic, variables). Executing a program yields an `EmbroideryStream`. Scripts are flat brick lists with paired control bricks; the move-a-pair-as-a-unit invariant is model logic with tests (ADR-008). The virtual needle operates in the ADR-007 stage space. The program model and interpreter ship as **two sibling targets in the same package** (ADR-016): `ProgramModel` (pure value graph, no engine dependency) and `Interpreter` (depends on `ProgramModel` + the engine target, never the reverse) so M4's editor and M5's persistence can import the program model without dragging the engine or DST I/O along.

Detailed stories: [`user-stories/milestone-2/`](user-stories/milestone-2/)

**Exit criterion**: a hardcoded "stitch a square/star" program produces the expected stitch stream in unit tests — still no UI — and the interpreter is **incrementally consumable**: execution advances step-by-step, emits ordered needle/stitch/color events, is deterministic (golden stitch-stream tests), and takes an injected clock for time-based bricks. Unit test: consuming events one at a time yields the same stream as batch execution.

**Exit criterion met** — 2026-07-25, US-207: the hardcoded square program (`setThreadColor` → `runningStitch` → compiled `repeatLoop(4)[moveNSteps, turnRight]` → `sewUp` → `writeEmbroideryToFile`) is pinned by a hand-derived 22-record golden stream *and* a differential replay through the engine's own pattern types. Step-by-tick consumption is asserted two ways — `step()` batches concatenate to `run()` (the ADR-018 structural invariant), and a consumer rebuilding the stream from the emitted events *alone* gets the identical stream — alongside the 12-tick profile and re-run determinism. US-208 demonstrated the same on 2026-07-27 with a second pattern type and a mid-program colour change: the star (`zigZagStitch`, five 20-unit sides at 144°, `setThreadColor` between two compiled loops) is pinned by a hand-derived 26-record golden and the same differential replay, with `colorChangeCount == 1` carrying through to `CO = 2` in the DST header. Its parameters sit on a `floor(distance / length)` boundary that only Darwin's `hypot` rounding resolves the way the golden expects — kept deliberately, guarded by a tripwire test, and pinned as ADR-019.

### M3 — Walking skeleton app (E4 + E7, thin E6)
**Status**: In progress — planned 2026-08-04. Ten stories (US-301…US-309 plus US-211 carried in from the backlog), ~40 h. **US-301 done 2026-08-09** (implemented 2026-08-07, Ink/Stitch verified 2026-08-09): `Samples` is the package's fourth library product, holding Catroid's `DefaultExampleProject` transcribed verbatim and a two-colour square coil in triple stitch, both guarded by JSON round-trip resources and an ADR-019 threshold screen. **US-302 done 2026-08-11** (implemented and reviewed 2026-08-09, merged as PR #32; eight Codex rounds, 21 findings all valid, final round clean): `StagePreview` is the fifth product — append-only display list, ADR-007's stage in code, `Double`-based zoom/pan math and a pure event reducer — and `InterpreterEvent.stitch` now carries the engine-resolved thread colour (ADR-021). The milestone's "zoom/pan transform math is unit-tested" exit criterion is **met**, under `swift test` with no simulator. 489 engine tests, up from 403. **US-303 is next and is gated on the human Xcode hand-off** listed in the milestone README — all nine items were still open on 2026-08-11, so the app target is still the Xcode template and links none of the five products. **US-303 done 2026-08-11**: the app target stops being the Xcode template — it links all five package products, builds as Swift 6 / iOS 17.0, ships a size-class adaptive `RootView` (ADR-010) with every string the *app* owns in its String Catalog (sample names and summaries stay in the `Samples` package's own bundle, per US-301), and is gated for the first time by an `app-build-and-test` CI job and a signing-free pre-commit compile check (ADR-023), both proven to fail before being trusted. 6 app tests. **US-304 done 2026-08-12** (PR #35): the sample picker, plus the ADR-023 selection hoist it inherited. **US-305 done 2026-08-13** (PR #36): ADR-009 in code — `StitchDrawPlan` batches the display list into at most two strokes plus one dot path per colour run, `StageView` fits `union(hoop, contentBounds)` so a design leaving the hoop stays visible, and the settled/live split is wired (though `settledCount` is US-306's to advance, so the raster path is unreachable at runtime and `bakingThreshold` awaits US-309's measurement). ADR-024 pins the renderer's deviations from both references. **546 engine tests**, up from 489.  **US-306 done 2026-08-17** (PR #37): the preview is a live run — `InterpreterDriver` steps the interpreter off the main actor into an unbounded `AsyncStream`, `PreviewRunState` folds one update per frame in a single observable mutation, and the settling watermark now advances, which makes US-305's cached-raster path reachable and answers ADR-024's open question (no seam; `Image(size:renderer:)` rasterises at the display scale). ADR-027 pins it.  The story's own cancellation criterion was wrong in the direction that fails silently: it says "the run `Task`" where there are necessarily two, and cancelling the consumer — what `.task {}` does — produces the terminal update carrying `assembledStream()` and never delivers it, reproducing Catty's teardown-before-share hazard while every producer-side test passes. `stop()` cancels the producer only. The batching had to be hoisted out of the renderer because four of the story's nine test items were unbuildable as written — a recording double records the protocol's inputs and never sees a path list — which three prior Codex rounds had not caught; and US-305's own Codex loop then found that `StageTransform.fitting` inherited the *gesture* zoom bound from `init`, cropping designs that export perfectly well. **US-307 done 2026-08-18** (PR pending): the stage is inspectable — pinch and pan composed simultaneously but committed **once** in `onEnded` (SwiftUI's gesture values are cumulative, so per-callback folding compounds them), which also makes ADR-009's "re-rasterise on gesture end" structural rather than timed, since the bake key reads a transform that cannot change mid-gesture. The canvas is one accessibility element whose value is rebuilt on run-state transitions only — 2 rebuilds against 139 batches — enforced by a separate `RunPhase` type, because `private(set)` inside `PreviewRunState` would still let `apply(_:)` write it. **Done 2026-08-19** (PR #39), manual VoiceOver / pinch / Reduce Motion pass confirmed the same day. **649 engine tests**, up from 581, plus 65 app tests and seven screenshots. ADR-028 pins it, and carries three corrections: the mid-gesture design was reversed after Sebastian found two defects in the running app that exist only *during* a gesture, and the interaction layer was then rewritten rather than patched, after six review rounds found the same conceptual mistake in four spellings. **Six of the story's own criteria and test items could not be built as written**: two were already green from US-302, one is vacuous, one is unassertable, one is untestable-and-already-true, and criteria 5 and 6 contradict each other for a running design — a summary rebuilt only on transitions would read "0 stitches" for the whole run. Third consecutive story where the planning-time buildability check paid for itself. **US-211 done 2026-08-25**: the header's field widths stop being a `precondition` on ordinary input — `DSTHeader.init` and `DSTFile.init` throw `DSTSerializationError.fieldOverflow(field:value:limit:)`, so the export path US-308 builds can say *which* limit was hit instead of the process dying. ADR-025 pins it, and pins two things the story had not seen: **field emission order is a contract** (a throwing `ST` check is what keeps the header's unguarded `Int` extent subtractions unreachable, and the extents being checked first is what keeps `AX` safe — at `"-9999"`, exactly filling its 5-wide field), and ADR-020's 1 000 000 split cap **stays**, against ADR-020's own speculation that it might want to be 999 996. The ripple was **41 call sites across 15 files**, not the 33 measured at planning. ADR-020's last open item is closed. **660 engine tests**, up from 649; goldens byte-identical with no re-blessing. The story's red mechanism is reusable: for a story that replaces a trap with a typed error, the exit test asserts **`.success`**, since `.failure` passes while the bug is present.

Minimal SwiftUI app wired end-to-end: pick a bundled sample program → run it with live stage preview (needle + stitches) → export the DST via share sheet. Proves the full thread through all layers. App-layer state uses iOS 17 `@Observable` view models on `@MainActor` (ADR-006); interpreter output reaches the preview via `AsyncStream` from the cancellable run `Task`, **batched before mutating observable state** (never one UI update per stitch); the run lifecycle is a small state enum.

**Correction (2026-08-04, M3 planning; implemented 2026-08-17 in US-306, ADR-027)**: this paragraph originally specified that enum as `idle/running/finished/failed`. **`failed` has no producer** — ADR-018 guarantees the interpreter never halts (every bad-formula path continues with a per-brick Catroid fallback, and `FormulaError.notANumber` is caught, not propagated), so nothing in the *run* path can fail. The run enum is `idle | running | finished(programFinished | stoppedByUser | stitchLimitReached)`; `failed` belongs to the *export* lifecycle, which genuinely can fail (disk, and after US-211 field overflow). Corrected rather than shipping a case with no producer.

How stitches reach the preview is pinned as **ADR-021** (colour-resolved events into an append-only display list — *not* per-frame re-assembly, for a structural reason rather than a speed one), and the target layout as **ADR-022**.

**In scope**: fit-to-screen stage (Canvas renderer per ADR-009), play/stop, needle indicator, run states, share-sheet export with an **exported UTType for `.dst`** (Info.plist declaration + `Transferable`/`FileRepresentation` — no system type exists) and design-name validation (≤15 ASCII chars, shown as a live counter, not a post-hoc error); String Catalog from the first UI commit; size-class-adaptive navigation skeleton (ADR-010); ≥2 bundled samples that are visually appealing designs exercising zigzag/triple/color-change — not test shapes. **Out**: scrubbing, speed control, editing (pinch-zoom/pan only if the ADR-009 transform work makes it nearly free).

**Exit criteria**: end-to-end sample→preview→DST works; a synthetic 50k-stitch design animates at 60 fps on an A15-class device; zoom/pan transform math is unit-tested. The transform-math criterion is met under `swift test` with no simulator, because `StagePreview` is a Foundation-only package target (ADR-022).

### M4 — Block editor (E5)
Create and edit programs in the app: brick palette as a bottom sheet with detents (tap-to-add, matching Catroid's flow — no free-form drag-from-palette), reorder via `List` + `.onMove` (flat list per ADR-008; custom accessibility actions as fallback; each brick is a single VoiceOver element with parameter values in its label; brick layout reflows under Dynamic Type). Parameter editing is **type-specific** (number pad, color picker / curated thread palette, variable menu, minimal arithmetic entry) — a full Catroid-style formula-editor keyboard is explicitly deferred (M6/stretch; don't build editor surface for functions the M2 interpreter doesn't have).

Editor mutations are a pure `EditAction` set applied to the value-type program in the SPM package (UI-free, developed test-first with full-`Program` equality assertions — ADR-006); the first M4 story is this headless EditorCore including the **undo/redo snapshot stack** (bounded, coalesced per gesture, `UndoManager` bridging for shake/Cmd-Z). All editor mutations are undoable from day one. One thin persistence slice lands here too: **implicit autosave** of the single working program to Documents as JSON (no project list or versioning UI — that stays M5), so the editor is usable across restarts and testable with real users.

**Checkpoint after M4**: informal usability session with 3–5 target-age users via TestFlight; findings triaged into the M5/M6 backlogs.

### M5 — Project management (E6)
Project list (create/rename/duplicate/delete — rename validates the 15-char DST name rule inline), JSON (Codable) on-disk format with versioning (autosave itself lands in M4), bundled sample designs.

### M6 — Brick parity & polish (E8)
Full parity with the Android flavor's embroidery brick set and behaviors — the concrete parity target is the 8 embroidery bricks plus Catroid's embroidery-category motion bricks (PlaceAt, SetX/SetY, MoveNSteps, TurnLeft/TurnRight, PointInDirection, Arc, GoThrough) and the control/data subset; list it as a checklist early so M6 isn't discovering scope. Polish is an **audit**, not a build-out (the M3+ definition of done keeps states/accessibility/strings continuous): pseudo-localization + RTL pass, sparse haptic map (success on export/run-complete, selection tick on brick add/reorder-drop, error on export failure — nothing else), app icon, App Store prep (age rating, no-tracking declaration per ADR-011) — ready for sign-off and transfer to the Catrobat org.
