# Project management

**Status**: In progress — PR 1 (slices 0–6, PR #78) merged after the Codex loop (5 rounds, cap); US-329 (persistence into the `Projects` package target, PR #79) merged; PR 2 (slices 7–10) in progress since 2026-10-27 | **Epic**: E6 (M5) | **Branch**: `feature/project-management` (PR 1), `feature/project-list` (PR 2)

**Goal**: a user keeps several designs. They see their designs in a list, newest first, and can create, open, rename, duplicate and delete them. Each design autosaves to its own file, and relaunching reopens the last design, even after a force-quit. A design has one name: it is the list's name and the export's DST `LA` name, and the exported file is named after it (ADR-026's sanitised form, so `A/B` exports as `A_B.dst`). Renaming checks the 15-character DST rule as the user types. Bundled samples become templates: opening one starts a new design from it.

**In scope**
- One file per project, per-project autosave, the project list (sidebar on regular, root of the push chain on compact), create, rename, duplicate, delete with confirmation, samples as templates, migration of M4's single `WorkingProgram.json`, the stage's name field becoming the project name, an empty state.
- US-320 (a new window opens on a name error the user did not cause): fixed by design, since every project always has a valid name.
- US-327 (CI hang guards): the one-minute `.timeLimit` guards are raised to three minutes as this feature's first commit (decided 2026-10-25, Sebastian).

**Out of scope**
- Thumbnails; iCloud, Files-app visibility and project import/export or sharing; `.catrobat` (Language-test runner); folders, search and sort options; a trash or undo for delete; a recovery UI for refused files.
- The format's multi-version admission machinery: no build has been distributed (Sebastian, 2026-10-25), so ADR-037's freeze has not started (D10).
- US-316 (stage 60 fps tail): **its own feature, right after this one** (decided 2026-10-25). It shares no code with project management; the backlog asked for a reason before a third deferral, and this is it.
- The US-312 thread-colour sidecar: an export concern, not storage; out (decided 2026-10-25).
- Variable rename/delete: an editor verb (ADR-045), not file management; out.
- US-324 (unknown key dropped): app-written files never carry unknown keys and project files are not exposed for hand edits; deferred.

## Decisions (D1–D12, accepted by Sebastian 2026-10-25 as planned by `swift-architect`)

- **D1 Storage**: one flat file per project, `Documents/Projects/<UUID>.json`, format v1 unchanged (the name is already `program.name`). The modification date comes from file attributes. No manifest: a second source of truth would drift.
- **D2 Identity**: a `ProjectID` wrapping a UUID, generator injected (ADR-006 pattern 2). Renaming touches no paths; duplicate names are harmless.
- **D3 Drafts**: a sample tap or "+" opens a **draft**, a fresh `ProjectID` with no file yet. The first change writes it through the normal pipeline; a design opened and left alone leaves nothing behind. Opening, running, exporting, navigating, backgrounding and closing are not changes and write nothing; the first changing edit (a valid rename, an undo or a redo included) writes exactly that ID (Codex brief review, 7). Duplicate is deliberate and writes at once. A sample project persists the encoded builder value; `SampleID` is never persisted, so the three doc comments that promise otherwise are corrected (ADR-032 invariant 3). Amends ADR-045 step 4: a draft goes through `load` but mints no revision until its first change.
- **D4 One name**: project name = `program.name` = DST `LA`; the export file stem is `DSTFileName` sanitised from it, as ADR-026 already separates the two (Codex brief review, 1); `ExportViewModel` stops owning the name (ADR-026 amendment). Sample projects take `program.name` ("Square Coil"), not `resourceName` ("SquareCoil"), so an exported sample's `LA` gains a space (one Ink/Stitch check). A blank design is named "Design" from the catalog, with an ASCII fallback if a translation fails `DesignName`. **Generated names are made unique, user renames are not checked**: `"<base> N"`, N from 2, compared case-insensitively ("Octagon Rosette" → "Octagon Roset 2"). Domain and rules (Codex brief review, 8–9): the input is a validated `DesignName`; a localized default that fails validation falls back to ASCII "Design" *before* suffixing; an existing suffix is a terminal ASCII space plus decimal integer and is stripped first; case folding is ASCII-only; the base is truncated by the final suffix's length and all trailing spaces removed (a base cut to nothing would need a 14-digit number, so it cannot occur). Uniqueness is against persisted project names **and the names of live drafts in the window registry**; names read only from refused files are compared too.
- **D5 Migration**: the legacy `WorkingProgram.json` becomes a project with a fixed, well-known UUID. Order: write the project **only if no file with that ID exists**, then set last opened, then delete the legacy file. An existing fixed-ID project is never overwritten — it may have been edited since a migration whose delete failed — so a replay only finishes the remaining steps (Codex brief review, 2). An empty or invalid name gets the default. A refused legacy file stays where it is and is alerted once per process; `WorkingProgram-refused-*.json` files are left alone.
- **D6 Launch**: each window keeps its project ID in `@SceneStorage`. Algorithm (Codex brief review, 3): (1) the scene ID, used only if it names an existing, openable project; (2) else `lastOpenedProjectID` (UserDefaults, decoded defensively), on the same condition; (3) else a draft with a **freshly minted ID**. **An unresolved stored ID is never reused** for a draft, so a deleted project cannot be resurrected and a refused file cannot be overwritten. A stale scene ID is replaced, and a last-opened ID that names a missing project is cleared. A refused candidate is alerted for, under its own ID. Tests inject a unique UserDefaults suite.
- **D7 Several windows**: ADR-037's last-writer-wins rule per project. Revisions stay global, but `highestAccepted` and failures are per `ProjectID`; a success for B never clears A's failure. A registry records which window holds which project (and each draft's name): registration, switching and closing are **explicit, observable transitions**, with weak references only as a retention safeguard, and a late unregister from an old window token never removes its successor (Codex brief review, 11). Renaming or deleting a project another window holds is disabled with a reason. A delete leaves an in-memory tombstone, so a late save cannot resurrect the file. Two windows on one project keep today's semantics.
- **D8 Rename**: renaming the open project is an edit (`.renameProgram`): undoable, through the pipeline. Renaming a closed project is a catalog write (load, rename, save, fresh revision). The list's Rename opens a sheet reusing `DesignNameField` (counter, error line, Save disabled while invalid). The stage's field commits on submit or focus loss. **A change that differs only in the name re-prepares the export and does not void the run**, and so does its undo or redo (ADR-038/045 amendment). The rule is decided by the **actual before and after values** reaching the change chokepoint, not by the initiating action: `onProgramChanged` reports both programs (Codex brief review, 5). A run that a content change already voided is never brought back by undoing to a rename-only difference. **Transient name buffer** (Codex brief review, 6): the stage field and the rename sheet hold raw text; an invalid value never reaches the program, the list, undo history or the export. On submit it keeps focus and shows the error; on focus loss the field returns to the committed name.
- **D9 Delete**: a confirmation dialog naming the design. The file is removed **first**; only on success are the tombstone installed, the summary removed, stored IDs that name it cleared, and the window moved to a blank draft (compact pops to the list). A failed removal changes nothing and reports the failure (Codex brief review, 12).
- **D10 Format freeze**: not triggered by this feature (no distributed build). The freeze becomes a release-checklist step, with a frozen-v1 vocabulary census test added at that step.
- **D11 Refused files**: stay where they are. A refusal installs a **process-wide write block for that `ProjectID`**: no window may save to, rename or overwrite it until it is re-probed as openable or deleted, which replaces ADR-037's single process-wide block with one per project (Codex brief review, 4). Set-aside is retired for project files (ADR-037 amendment). They are listed with their name if a probe can read it, a badge ("Needs a newer app" / "Damaged") and only Delete. Opening one says the current design stays open (new copy; the existing six promise "a new, empty design").
- **D12 Thumbnails**: not now. Rows show the name and a relative modification date.

## Acceptance criteria

- [ ] Every project is one file, `Documents/Projects/<UUID>.json`, a v1 program document; a save never writes a file the window did not create or open, and a failed save leaves the previous bytes.
- [ ] A draft writes no file until its first change, then exactly one; duplicate writes at once with a new ID and a uniqued name.
- [ ] Every generated name passes `DesignName` validation and is unique, case-insensitively, among persisted names, live drafts' names and refused files' names (a property over generated bases, including 15-character bases and 9→10, 99→100 suffixes).
- [ ] A save to one project never supersedes another's; a save after a delete leaves the file deleted; failures show only in windows holding that project.
- [ ] One name: the export's `LA` equals `program.name` and its file name is ADR-026's sanitised form of it; an invalid typed name never reaches the program; a rename-only change, and its undo and redo, keep a live run and re-prepare the export; every other change voids the run and saves.
- [ ] Launch opens the window's project, else the last opened, else a draft with a fresh ID; an unresolved stored ID is never reused; after a force-quit the last design reopens (M4 exit criterion 3, re-pointed).
- [ ] The legacy working file migrates exactly once, also when replayed after a crash or a failed delete at each step; an existing migrated project is never overwritten.
- [ ] Refused files are listed, badged and deletable, never opened or overwritten by any window; a failed delete changes nothing.
- [ ] The list, create, rename, duplicate and delete work on compact and regular, with String Catalog entries for all new copy; screenshots of both.
- [ ] An exported sample with a space in its `LA` name opens correctly in Ink/Stitch (manual check).
