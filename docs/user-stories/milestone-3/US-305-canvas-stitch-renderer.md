# US-305 — Canvas stitch renderer, fit-to-screen, empty state

**Epic**: E4 Stage & preview | **Estimate**: ~5 h | **Depends on**: US-302, US-303

**Status**: Done — 2026-08-13. 546 engine tests green (up from 489) and the app suite green on the simulator; SwiftLint `--strict` clean; screenshots reviewed at four combinations (iPhone/iPad × light/dark) with a design drawn. Planned with `swift-architect` and `swift-ui-design`; **the planning pass corrected seven things in the criteria below** (marked **planning correction** inline, each verified against the named source rather than taken on report), and Sebastian took two scope decisions, recorded under "Scope decisions". Reviewed twice: an in-loop `swift-code-reviewer` pass (nine findings, three important, all reproduced — four were defects and are fixed) and a Codex loop that ran **four rounds, severity High → High → none → none**, ending on stop condition 1. Codex's round 2 is the one worth remembering: it **refuted my own triage of round 1's High**, which had deferred a real cropping defect on an argument that confused a design's span with its per-direction DST extent. Two limitations ship stated rather than implied — nothing here advances `settledCount`, so the cached-raster path is wired and unit-tested but unreachable at runtime (US-306 owns it), and the press-play empty state is therefore not screenshot-reachable while the temporary drain runs.

**Story**: As a user, I want to see the design drawn on a stage that fits the screen, so the preview is legible before I ever press play.

This is where ADR-009 becomes code. Both references get the rendering wrong in instructive ways: Catty creates **two** `SKShapeNode`s per stitch as direct scene children with no batching and no removal path, and Catroid batches its draw calls well but rebuilds the entire export model every frame. We take Catroid's per-primitive geometry, Catty's nothing, and ADR-009's cached-raster strategy — which Catroid itself already validates for pen drawing in `PenActor`'s `FrameBuffer`.

## Acceptance criteria
- [x] `StagePreviewRenderer` protocol with `associatedtype Body: View`, taking `(display, transform, needle, viewport)`; `StageView` is generic over it. **No `GraphicsContext` in the protocol signature** — a context there *is* the Canvas leaking into the abstraction and would defeat ADR-009's Metal escape hatch. `CanvasStitchRenderer` returns a `Canvas`; a future `MetalStitchRenderer` returns something else.
- [x] `CanvasStitchRenderer` batches into **one stroked `Path` per (colour run × segment style)** for threads, plus one `Path` per colour run for penetration dots. Never one shape per stitch — that is the Catty anti-goal ADR-009 exists to forbid. **Per-run alone is not a valid batching unit**: a single colour run can contain short → long → short segments, and one stroked path cannot render the middle one hairline/dimmed while the others stay normal (Codex round 3 — an earlier draft said "one path per colour run" and contradicted the styling rule below). Since there are exactly three styles and one is not drawn, the real bound is **two thread paths per colour run**, so the batching claim ADR-009 cares about is unaffected. Stated exactly, the per-run bound is **≤ 2 stroked thread/traversal paths + 1 dot path**.

  **Emission order is a deviation from Catroid and has to be chosen deliberately.** Per colour run: traversal stroke, then thread stroke (travel hints sit *under* thread); then every dot path, after all strokes, so **dots always sit on top**. Catroid interleaves line and dot in stitch order (`EmbroideryActor.kt:66-74`), which lets a later colour run paint over an earlier run's penetration dots. Ours cannot. Record in ADR-024.
- [x] Dot radius and thread width use the same value, ported from Catroid's `BrickValues.STITCH_SIZE = 3.15` (`BrickValues.java:187`), scaled by the transform. **Not** by device diagonal.

  **Planning correction — this criterion misdescribed both references in three ways, and all three were checked at the source before being rewritten.** (a) The ratio is **inverted**: both references compute *project ÷ device*, not device ÷ project — `StageListener.java:1015` returns `creatorDiagonalPixel / deviceDiagonalPixel` and `Catty/src/Catty/Embroidery/EmbroideryStream.swift:63` does the same. (b) Catty is not a single-factor case: it applies `sizeConversionFactor = 0.634` (`EmbroideryDefines.swift:59`) *and* uses a **separate** dot radius constant `stitchingCircleRadius = 3.0` (`SpriteKitDefines.swift:49`), feeding `size` in as the circle's *stroke* width — so "dot radius and thread width use the same value" is **Catroid's** rule, not something both references share. (c) "never recomputes it on rotation" is the wrong indictment: `UIScreen.main.nativeBounds` is orientation-independent, so rotation was never the trigger. The real defect is that the size is derived from the **device** and the project's virtual size rather than from the view and the transform — which is what makes it unable to respond to zoom at all.

  **And 3.15's units, since the criterion says "ported" without saying ported into what.** It is a **device-pixel** constant on the Catroid side, converted into virtual-stage units by `screenRatio` (`EmbroideryActor.kt:39`), then drawn under the batch's projection matrix as a `circle` **radius** and a `rectLine` **width** (`EmbroideryActor.kt:83, 88-94`). Because `DSTFileConstants.java:56` pins Catroid's `STITCH_POINT_UNIT_FACTOR = 2f` — the same factor ADR-007 pins for our stage — one Catroid virtual unit *is* one of our stage points, so at the ordinary `screenRatio ≈ 1` this is **3.15 stage points = 0.63 mm of fabric**. Reading 3.15 as stage points and multiplying by `transform.scale` reproduces that physical size exactly and drops the device dependence entirely.

  **Say the consequence out loud, because "the same value" reads as "the same visual width":** with radius = width = 3.15, the dot's **diameter is twice** the thread's width (1.26 mm against 0.63 mm). That beading is Catroid's look and is what makes penetration points read as points. It must be in ADR-024 or someone will "fix" it.
- [x] **The dot rule is stated in display-list terms, because Catroid's cannot be evaluated here.** Catroid skips dots on jump and colour-change points (`isConnectingPoint == !jumpPoint && !colorChangePoint`), but those are *synthetic records in the export model* — `isJump`/`isColorChange` live on assembled `Stitch` values, and the display list is reduced from `InterpreterEvent.stitch`, which carries actor/position/layer/colour and no flags (US-302 also forbids consuming `.colorArmed`). So **every display-list entry is a stitch the program requested, and every one gets a dot**; there are no synthetic entries to exclude. Deliberately "requested" and not "a real needle penetration": under ADR-020 an op can be recorded — and therefore drawn — while the replay rejects it, so it never becomes a record and the machine never goes there. That is the same display-vs-export divergence US-308's gating handles, and the preview showing the requested design is the intended behaviour. This is a record-model difference, not an appearance difference, and it must be written down rather than left as an unreachable criterion. (Codex round 2: the first draft demanded flags the planned data path never carries, so a renderer that dotted everything would have passed anyway.)
- [x] **Segment styling carries what the flags used to**, all of it derivable from what the display list actually holds. **The cases are evaluated in this order and the precedence is load-bearing**, because a colour-run boundary and a traversal can coincide:
  1. `.suppressed` across a **colour-run boundary** — no segment drawn, and it **wins over** `.traversal`. (**Planning correction — the case is named `.suppressed`, not `.none`, as every earlier line of this story called it.** `Optional.none` shadows a case of that name in every optional context, so `let style: StitchSegmentStyle? = .none` would compile and silently mean "no style at all" rather than "the suppressed style". A footgun for free.) **This is a deliberate divergence, not Catroid parity** — an earlier draft claimed parity and was wrong (Codex round 3). Catroid's `colorChange` latch suppresses lines only until the next *connecting* point resets it (`EmbroideryActor.kt:64-73`), and clause B's second black point at P is connecting, so Catroid resets the latch there and then **draws a black P→Q connector**. Our display list has no black transition point to hang that connector on — it goes red P → green Q directly — so drawing anything there would imply continuous thread across a thread swap the machine stopped for. Suppressing is the honest rendering of the data we hold; claiming Catroid does the same is not.
  2. `.traversal` when `EmbroideryStream.requiresTraversal` says the move would be interpolated as machine travel — drawn distinctly (hairline/dimmed), a deliberate deviation from *both* references, which draw travel as solid thread indistinguishable from stitching.
  3. `.thread` otherwise.
- [x] Documented fallback if `requiresTraversal` runs hot or proves unreliable: draw every non-boundary segment as thread, matching both references, recorded as a known limitation. **As prose, not as a flag** — a config boolean nobody ever flips is worse than a sentence, because it reads as a supported mode.

  **Planning correction — `PreviewStitch.Segment` does not exist.** This criterion ended "`PreviewStitch.Segment` already has all three cases", which is false: `PreviewStitch` (`PreviewStitch.swift:18-26`) has `position` and `color` and nothing else, and `grep -rn "Segment" Packages/EmbroideryEngine/Sources/` hits only an unrelated comment in `TripleStitchPattern.swift:55`. **This story creates the type**, which also means test item 6 below has nothing to compile against on day one — as it should, that being the red phase.

  It must **not** hang off `PreviewStitch`. A `PreviewStitch` is a per-stitch value stored up to 50 000 times; a segment style is a *relation between two consecutive entries*, always derived and never stored. Nesting it there invites exactly the stored property that would put a derived classification into the append-only list — a second source of truth, and 50 k bytes to hold it — against a type whose own doc comment already argues at length for staying minimal ("deliberately carries neither `layer` nor `actor`"). It ships as a top-level `StitchSegmentStyle`.
- [x] The 500×500 stage is drawn as a **hoop outline and is not clipped to**; the fit target is `union(stageRect, contentBounds)`, so a design that leaves the hoop is visible rather than silently cropped. Nothing bounds a `StagePoint` (US-302's `StageGeometry` doc comment says so), and showing the overflow is how the user learns before export tells them.
- [x] The settled/live split is wired from the start: stitches below `settledCount` render from a cached raster, the live tail per frame. The baking threshold is a named constant with a comment; US-309 tunes it by measurement.
- [x] **The bridging segment at the watermark, which this story discovered and no criterion covered.** The watermark splits *stitches*, but a segment joins **two** of them, so segment `(k−1, k)` straddles it: a bake that draws segments `0..<k−1` and a live pass that draws `k..<n−1` never draw it, and the thread shows a permanent one-segment gap at every watermark advance. The rule: **the bake draws strictly inside its window; the live pass starts one index earlier.** Dots partition cleanly (`0..<k` settled, `k..<n` live); segment starts are `0..<max(0, k−1)` settled and `max(0, k−1)..<max(0, n−1)` live. Sound because the display list is append-only **per element**, not merely per prefix — stitch `k` never changes once appended, so the live pass may read it, and when the watermark passes it the bake picks the segment up. Disjoint, so a traversal's alpha is never double-composited. Note the live pass therefore needs stitch `k−1`, which is *outside* `liveTail`: index into `stitches` rather than reaching for the slice, which ADR-021's close-out forbids storing anyway.
- [x] **Nothing in this story advances the watermark.** `markSettled(upTo:)` belongs to US-306, which owns the run; US-305 only *respects* `settledCount`. "Wired from the start" means the split is honoured, not that a settling policy is invented here.
- [x] **Empty state**: with no stitches, a localised "press play" state rather than a blank canvas. The loading state is unreachable and stated as such.
- [x] **Thread colours must not adapt to dark mode** — they are design data. Only stage chrome (hoop, background, grid) is semantic-coloured; contrast checked in both appearances.
- [x] **Story-specific definition of done**: screenshots at compact and regular, light and dark, with a sample loaded; the canvas's accessibility summary is deferred to US-307 and the canvas is not left as an unlabelled element in the meantime.
- [x] Close-out pins **ADR-024**: the renderer's deviations from both references (distinct jumps, greenfield needle, dot/thread geometry, dark-mode rule) — **plus the six this story's planning added**: the corrected 3.15 provenance and its reinterpretation as stage points; dot diameter = 2 × thread width; dots-on-top rather than Catroid's interleaved order; the bridging-segment rule at the watermark; the narrowing of "only chrome is semantic" to *inside the canvas is fixed, outside is semantic* (a semantic outline over a fixed light field is a light line on a light field in dark mode — the literal rule is unimplementable); and travel-as-chrome, i.e. that a traversal is drawn in a fixed chrome colour rather than a dimmed thread colour, because the machine trims travel and so travel is not design data.

## Test-first plan

**Planning correction, and it is structural: items 2, 3, 6 and 7 were unbuildable as written.** They each asked to be asserted "through the recording renderer double's path list" — but a double conforming to `StagePreviewRenderer` records that protocol's *inputs*, which are `(display, transform, needle, viewport)`. Paths are produced **inside** a renderer, so a double, being an *alternative* renderer, never has a path list to inspect. There were only three ways out: a `GraphicsContext` spy, which the first acceptance criterion forbids outright; the double re-implementing the batching, which makes the test assert the double; or the batching becoming a **value** that both the double and the real renderer can be checked against.

Hence `StitchDrawPlan` — a pure, **index-based** plan (`{style, colour, member indices}`) computed in `StagePreview` and merely *stroked* by `CanvasStitchRenderer`. This is not a test-speed optimisation; it is the only construction under which those four items assert anything at all. Two consequences fall out for free: the batching logic runs under `swift test` in ~1.4 s instead of behind a simulator boot (ADR-023's cost argument, applied to the milestone's load-bearing logic), and a plan of `Int`s **cannot** violate ADR-021's rule against storing an `ArraySlice` across an append — the violation ADR-021's close-out warns "US-305 would have committed by construction" becomes unrepresentable rather than merely avoided.

The split is a partition, not a duplication: the double proves **wiring** (items 1, 8), the plan proves **logic** (items 2–7). Nothing is asserted twice.

1. Renderer *inputs*, not rendering: a recording renderer double asserts it is handed the expected display list and transform for a given viewport. **App target** — `StageView` computes its inputs inside a `GeometryReader`, whose closure does not run when `body` is merely read, so the test hosts the view in a `UIWindow` at an explicit frame and calls `layoutIfNeeded()`. That frame *is* the expected viewport.
2. Colour-run grouping: a two-colour sample with only ordinary short moves yields exactly two thread paths; the same sample with one long gap inside the first run yields **three** (that run splits into a thread path and a traversal path). Asserted on `StitchDrawPlan`, so no `Canvas` and no simulator is needed.
3. **The renderer actually consumes the classification.** Every stroke in the plan carries its style *and* its member indices — not just that classification is computed. Without this, an implementation that classifies correctly and then strokes everything as ordinary thread passes every other item here (Codex round 3).
4. Fit-to-screen: a design exceeding the stage produces a transform whose fitted content bounds include the out-of-stage extreme (i.e. it is not clipped away). **An engine test**, since `StageBox.union`, `StageGeometry.fitTarget(including:)` and `StageTransform.fitting` are all package code. Includes the non-finite case: ADR-021 divergence #5 lets a rejected coordinate be *drawn*, so `bounds` can carry NaN, and `Swift.min(a, .nan)` returns `a` — a naive union would silently discard a real extent or the hoop itself.
5. Settled/live split. **Planning correction — the item as written is off by one and an implementation satisfying it literally would render a visible gap.** "After `markSettled(upTo: k)`, the per-frame drawn set is exactly `stitches[k...]`" is true of the **dots** and false of the **segments**, for the bridging-segment reason above. The honest and stronger form is a partition invariant: `settled ∪ live == entire`, disjointly, plus the explicit assertion that the live plan *includes* the segment entering the watermark.
6. Segment classification, all three cases **plus the precedence case**: a > 121-unit op gap classifies `.traversal`; a colour-run boundary classifies `.suppressed`; an ordinary short move classifies `.thread`; and a boundary that *is also* a long gap classifies `.suppressed`, not `.traversal`. Assert the drawn count: N stitches give N − 1 segments, so one `.suppressed` boundary leaves exactly **N − 2** drawn — a renderer that ignored `.suppressed` would otherwise pass, and one that got the precedence backwards would draw N − 1.

   Two cases to add, both discovered while checking the trigger at its source. **Exactly 121 units is still `.thread`**: `interpolationSplitCount` compares with a strict `>` against `DSTStitchRecord.maxDelta = 121`, which is itself an *inclusive* bound, so 121 is encodable in one record and needs no traversal. That is a golden sitting on a threshold and **ADR-019 requires it to guard itself** — the test must state the strict comparison it depends on, so tightening the trigger fails here loudly rather than silently reclassifying every 121-unit move. And **an ADR-020-*rejected* move classifies `.thread`, not `.traversal`**: `requiresTraversal` returns `false` when `canAppend` refuses, so the preview draws ordinary thread across a move the machine will not make at all. That is divergence #5 surfacing in the renderer, and it is worth pinning rather than leaving for someone to find and "fix".
7. Dot count equals display-list count: every entry is dotted, including both endpoints of a traversal. Pins the deviation from Catroid's record-model rule so it cannot be "fixed" later by someone reading `isConnectingPoint`.
8. Empty display list produces the empty state, not a zero-stitch canvas — **and the renderer is never invoked**, which is the half of the claim a screenshot cannot make.
9. Screenshot review across the four appearance/size-class combinations.

## Scope decisions (Sebastian, 2026-08-13)

**1. A temporary synchronous drain ships in this story, and US-306 deletes it.** Found while planning: **US-305 has no stitch producer.** `Interpreter(` and `.step()` appear nowhere in the app target except `SampleLinkageTests.swift` — US-306 owns the run driver and *depends on* this story, so as specified the renderer could only ever display the press-play state and item 9's "screenshots … with a sample loaded" would evidence an empty hoop four times over. Since visual review is most of this story's value, `AppModel` gets a tick-capped drain on appear (~10 lines, doc-commented as US-306's to delete). Rejected: swapping the two stories, because US-306 needs the surface it renders into; and shipping the renderer proven only by unit tests, because ADR-009's entire rendering strategy would then reach `main` never having drawn a pixel on a device.

**2. The hoop-overflow notice ships, though no acceptance criterion asks for it.** The criteria make the overflow *visible* (unclipped, fitted through `union(stageRect, contentBounds)`), and the design pass established that the cues are sight-only — a fill change and a zoom. Checked, and the gap is real for the whole milestone: **US-308 gates export on `assembledStream().count > 1`, which is hoop-independent**, and `StageGeometry`'s doc comment says it bounds nothing, so no other M3 story ever tells a user their design left the hoop. A VoiceOver user would get nothing at all. One String Catalog entry plus a `Label` shown when `bounds` is not contained in `StageGeometry.box`. Not an error state — export is not blocked by it.

**Deferred, deliberately: the thread-contrast casing.** The design pass proposed a dark casing stroke under any colour run whose thread luminance falls within 3:1 of the stage field, and it is a real problem — the shipped square-coil sample's amber `#f59e0b` sits at ~1.5:1. But the criterion below asks only that contrast be *checked* in both appearances, and a fixed (non-semantic) stage field makes it **invariant by construction**, so the criterion is met without casing. Deferred as a stated known limitation, in the same idiom as this story's own `requiresTraversal` fallback; US-307 owns accessibility and can take it.
