# US-307 — Pinch-zoom / pan and the stage VoiceOver summary

**Epic**: E4 Stage & preview | **Estimate**: ~3 h | **Depends on**: US-302, US-305, **US-306**

**Status**: Implemented 2026-08-18 — 632 engine tests (up from 581) and 64 app tests (up from 48), SwiftLint `--strict` clean, six screenshots. Planned with `swift-architect` and `swift-ui-design`; **the planning pass corrected six things in the criteria below**, marked **planning correction** inline, and Sebastian took four scope decisions recorded under "Scope decisions". Review and close-out below.

**Story**: As a user, I want to pinch and drag the stage to inspect stitches closely; and as a VoiceOver user, I want one spoken summary of what the stage holds rather than tens of thousands of elements.

The roadmap gates zoom/pan on "only if the ADR-009 transform work makes it nearly free". US-302 delivers the math and its tests, so it is — the view only composes gestures and calls pure methods. The accessibility summary lands here rather than in US-305 because its content (stitch count, colours, size in mm) is only meaningful once a run can produce it.

## Acceptance criteria
- [x] `MagnifyGesture` and `DragGesture` composed simultaneously, writing `StageTransform` through the US-302 pure methods. **No transform math in the view.** — **planning correction**: the gestures are composed simultaneously but the transform is written **once, in `onEnded`**, never per callback. Both `magnification` and `translation` are cumulative from the gesture's start (verified in the SDK interface, `SwiftUI.swiftinterface:9378-9394`), so folding each callback in as a delta compounds them — a pinch reading 2, 2, 2 lands at 8× for fingers that asked for 2×. The live gesture is a `.scaleEffect`/`.offset` over the rendered canvas instead, which is also what delivers criterion 3. "No transform math in the view" is **not fully testable**, only reviewable: what *is* checked is that every arithmetic operation the view needs exists as a package function, pinned at compile time by `StagePreviewTargetIsolationTests.theZoomBoundaryIsPackageTypes`.
- [x] Pinch is anchored: the stage point under the user's fingers stays fixed. Zoom clamped to documented min/max; double-tap resets to fit. — **planning correction**: "documented min/max" is no longer two numbers. `StageTransform.fitting` can legitimately return a scale **below** `minimumScale` (0.05) for an out-of-hoop design that exports perfectly well, so an absolute floor would snap it *larger* on the user's first pinch and double-tap-to-fit followed by a pinch-out could never get back. `StageZoomBounds` floors at `min(fit.scale, minimumScale)` — a **rule**, and one that only ever *widens* the range, which is what lets `pinched`'s seven rounds of hardened invariants keep their meaning unchanged.
- [x] During a gesture the settled raster is blitted *through* the transform (a GPU scale) and re-rasterised on gesture end. The mid-gesture crispness loss is an accepted, **stated** trade-off rather than a surprise. — **the substance ships and the literal wording does not, and the difference was found the hard way.** `StageRenderTransform` carries two transforms: the frame is re-stroked at `current`, and `CanvasStitchLayers.BakeKey` reads `bake`, which holds still — so the settled raster is rasterised **once per gesture, on commit**, which is the expensive half ADR-009 protects. The cached raster is *not* blitted while live: its pixels were baked at a transform the frame is no longer using, so compositing them would misplace them. The first version did blit — it moved the rendered layer with `.scaleEffect` — and that is precisely why content panned off-canvas stayed missing when dragged back, since a `Canvas` never drew it. There is consequently **no mid-gesture crispness loss to state**; the trade-off that replaces it is a per-frame re-stroke, which is unmeasurable at M3's counts and is US-309's to measure at 50 000.
- [x] Gestures work during a run without dropping batches. — **planning correction**: untestable as worded, and already true. Batches are buffered in the `AsyncStream` and consumed on a separate task (ADR-027), so a gesture cannot drop one. What a gesture *can* drop is *frames*, by invalidating the bake key — which is criterion 3, and is closed by construction. The frame-rate reading belongs to US-309.
- [x] **The canvas is a single accessibility element** with a summary value: design name, stitch count, colour count, and size in millimetres (embroidery units × 0.1 from the export model when present, else display bounds × 0.2 per ADR-007's 1 pt = 0.2 mm). The hint describes the run state and the available adjust actions. — **planning correction, two parts.** (a) The design **name is in the label**, not the value: the summary a user hears is label *plus* value, and a name in the value is re-spoken on every value change — after every zoom step and at both ends of every run — while it is already the navigation title. (b) The **counts come from the display list and only the size from the export model**, which is what the criterion's own parenthesis specifies for the size alone; `stage.run.limit.notice` already argues that "the count is what is on screen", and using two sources for "how many" on one screen would be worse than either. Measured, both bundled samples agree exactly anyway (3194/3194 and 2976/2976), so nothing observable rests on it this milestone. Verified on the simulator: one element, label `Embroidery stage, Octagon Rosette`, value `3.194 stitches, 1 colour, 98,6 millimetres by 98,6 millimetres`.
- [x] **The summary updates on run-state transitions only, never per batch.** A value changing 60×/s makes VoiceOver unusable. This is the story's headline definition-of-done item and it is asserted by call count, not by inspection. — **planning correction: this criterion and the one above contradict each other, and the contradiction had to be resolved before either could be built.** A summary of "what the stage holds", rebuilt only on transitions, is computed at `idle → running` — when the display list is empty and `display.bounds` is `nil` — and would therefore read "0 stitches" for the entire run while the design visibly stitched. **Numbers appear only when they are final**: a running stage says it is stitching, a finished one says what it made. Nothing is lost, because this criterion makes mid-run counts unobtainable either way. Asserted by count (`summaryRevision == 2` against `revision == 139` for sample 1) **and** by value equality across every batch — the count is the criterion's letter, but the system re-announces on a changed *value*, so a counter alone would pass for an implementation that rebuilt an identical value every frame.
- [x] Zoom is reachable **without gestures**: `.accessibilityAdjustableAction` (increment/decrement) on the canvas element, so VoiceOver and Switch Control users can zoom at all. — **planning correction, two additions the criterion needs to be whole.** (a) A **named "Fit to Hoop" action** ships alongside it, because double-tap-to-fit is unreachable with VoiceOver running (a double tap is VoiceOver's own activate gesture) and absent under Switch Control entirely — without it, the criterion hands its users a zoom with no way back. (b) The **zoom level is spoken**, as a percentage relative to the fit, placed first in the value. VoiceOver re-reads an element's *value* after an adjustable action; a value that could not change would leave the action with no feedback at all. That is compatible with criterion 6, whose substance is "never per batch" — a zoom step is user-initiated and discrete, and the summary-rebuild count it asserts is untouched by zoom.
- [x] Reduce Motion: the double-tap-to-fit transition is instant (the transform spring is decoration; the stitch animation from US-306 is not). — **planning correction**: `withAnimation` around the reset animates *nothing*, because a `StageTransform` in state is not animatable — `Canvas` simply re-strokes from whatever it is handed. The reset therefore runs on the same `.scaleEffect`/`.offset` channel the gesture uses, driven by a new pure `StageTransform.viewDelta(to:in:)`, and swaps the transform at completion. Reduce Motion passes `nil`, which is a legal `Animation?` meaning "instantly", so one call site serves both branches. **Direct manipulation is deliberately not gated** — Reduce Motion is about motion the app starts, and suppressing a pinch would break the gesture rather than calm it. ADR-027 asked this story to reuse the transport row's single gate; what is actually shareable is the *policy* (`StageMotion`), not the environment read, which is per-view by design.
- [ ] **Story-specific definition of done**: a real VoiceOver pass on simulator or device, plus screenshots at two zoom levels; the mm figure verified against a known sample (sample 1 is ~98.6 × 98.6 mm). — **partly outstanding, and precisely stated.** The **mm figure is verified** on screen against sample 1 (`98,6 millimetres by 98,6 millimetres` in the live accessibility tree). The **VoiceOver pass and the two zoom levels are not automatable in this environment**: the available UI automation is single-finger only, so a pinch cannot be synthesised, and `xcrun simctl ui` exposes only `appearance`, `content_size` and `increase_contrast` — no VoiceOver and no Reduce Motion. Six screenshots ship (fit, panned, mid-run with the needle, dark, AX5, iPad regular); a zoomed one requires a real pinch. See "Outstanding manual verification".
- [x] Close-out records the zoom min/max, the adjustable-action step, and the mid-gesture raster policy. — ADR-028.

## Scope decisions

Four decisions Sebastian took before the tests were written, each because it changes what the tests assert:

1. ~~**Mid-gesture blit via `.scaleEffect` on the composed canvas**, rather than an in-renderer partial blit of the raster rect.~~ **Reversed 2026-08-18 after Sebastian found both of its symptoms in the running app** — see ADR-028's correction. The rejection of `swift-architect`'s design rested on "scaling the whole canvas moves everything together, so nothing is uncovered inside it", which is false: a `Canvas` rasterises only its own bounds, so content panned outside them is never drawn and sliding the layer back cannot reveal it. What ships is that design minus its blit — `StageRenderTransform` carries `bake` and `current`, the frame re-strokes at `current`, and the bake key holds still so the settled raster is rasterised once per gesture rather than per frame. Criterion 3's *substance* (do not re-rasterise per frame) is delivered; its literal "blitted through the transform (a GPU scale)" is **not**, because the cached raster is skipped entirely while live.
2. **Numbers appear only when final** (criterion 6, above).
3. **The zoom level is spoken, first, in the value** (criterion 7, above).
4. **The fit animation is built rather than dropped.** Criterion 8 would otherwise ship vacuous — nothing to gate — and a criterion that gates nothing is worse than one that costs half an hour.

## Outstanding manual verification

Not blockers for review, but the story is not closed until they are run. Nothing in this environment can do them:

- **A real two-finger pinch**: anchoring under the fingers and the clamps at both ends. The `onEnded`-fires-with-one-channel risk is discharged **by measurement, not by argument** — a drag with no pinch was driven on the simulator and committed. (An earlier wording here reasoned that it "takes the same `value.first == nil` path", which is a claim about what happens *inside* `onEnded` and says nothing about whether `onEnded` is called; the conclusion was right and the argument was not.) Nothing about the needle, hoop or dash "snapping back" needs checking any more — with the canvas re-stroked at the live transform, view-point chrome keeps its size throughout.
- **Screenshots at two zoom levels** (fit and ~3×, the point ADR-027 records the needle stops reading as a marker).
- **A real VoiceOver pass**: the adjustable action's spoken feedback, the "Fit to Hoop" action, and that the value is *not* re-announced during a run. **This is now load-bearing rather than confirmatory.** An automated test that hosted the canvas and walked its accessibility tree was written, proven falsifiable, and then removed: it passed locally and failed on CI, and the failure could not be reproduced here even after restarting the simulator — a hosted view publishes its accessibility hierarchy only once the accessibility server is engaged, which a machine running UI-automation tooling all session satisfies and a clean runner does not. So deleting `.accessibilityValue`, the adjustable action or the named fit action from `StageCanvas` still leaves every automated test green, and only this pass would catch it.
- **Reduce Motion**: that double-tap-to-fit becomes instant.

## Test-first plan

**Two of these six items were already green before the story started, and a third is not assertable as written.** Found by checking each against the named source rather than assuming, and recorded here because a test that has never been red proves nothing — which is the whole point of the repo's red-phase rule.

1. ~~Anchor invariance: pinching by 2× about a given view point leaves that point's stage coordinate unchanged~~ — **already green since US-302**: `StageTransformTests.pinchKeepsTheAnchorFixed` (`StageTransformTests.swift:170-182`) pinches about a view point over four factors including 2.0 and asserts exactly this; the story's own prose concedes it ("US-302 delivers the math and its tests"). Replaced by the invariance that *is* new — the anchor surviving a **cumulative** gesture value folded against an unmoved baseline, which is where the real defect lives (`StageZoomTests.committingAPinchKeepsTheAnchorFixed`, `.onlyTheFinalCumulativeValueIsApplied`, `.aPinchIsAppliedBeforeThePan`).
2. Clamping holds at both ends — **first half already green** (`StageTransformTests.scaleClampsAtBothEnds`). The new content is the **fit-aware floor** (`StageZoomBoundsTests`). Second half — "double-tap-to-fit reproduces `StageTransform.fitting(...)` exactly" — is **vacuous** under the shipped design: `nil` means "follow the fit", so `resolved(fitting: fit)` returns the fit it was handed and the assertion is `fit == fit`. Replaced by the property that has content: after a double-tap a changed viewport changes the resolved transform, and after a pinch it does not (`StageZoomTests.fittingToContentReturnsToTheFit`, `.anExplicitTransformDoesNotRefit`).
3. Summary builder: for sample 1 it reads "3194 stitches, 1 colour, 98.6 by 98.6 millimetres" — **the sentence is not assertable and the numbers are.** `%lld` renders 3194 with the reader's grouping separator, and `AppStringsTests` refuses on principle to assert English wording. Split: the numbers in `StageSummaryTests.sampleOneSummarises` (3194 / 1 / 98.6 ± 0.05), the catalog's plural forms and argument substitution in `AppStringsTests`, and the composition in `StageAccessibilityTests`. Also **the unit is stated on each length rather than once** — "98.6 by 98.6 millimetres" only composes in English, because unit names inflect with the number and move position; handing `Measurement.FormatStyle` both lengths makes that ICU's problem rather than a translator's. `.wide` rather than the hoop caption's `.abbreviated`, because this string exists only to be spoken and VoiceOver's expansion of "mm" is not guaranteed: **abbreviated for the eye, wide for the ear.**
4. The summary builder's call count across a multi-batch run equals the number of state transitions, not the number of batches — `RunPhaseTests.theSummaryIsRebuiltOncePerTransition` (2 against 139), plus `.theSummaryIsIdenticalAcrossEveryBatch`, which is the assertion that actually protects VoiceOver.
5. The adjustable action changes scale by the documented step and respects the clamps — `StageZoomAdjustmentTests`, **without recomputing the step formula**: the viewport centre stays fixed, the two directions round-trip, and both ends stop *exactly* at the bound. One literal pins 1.5 as documentation.
6. Size-in-mm uses the export model when present and display bounds otherwise, and both agree for a sample with no rejected coordinates — **"agree" is a tolerance, not an equality**, and the bound is derived: each edge rounds to a whole embroidery unit through `javaRound`, so a span's error is strictly within ±1 unit = **±0.1 mm**. Measured on sample 1: 98.5676 mm from the display bounds against 98.6 mm from the export model, a gap of 0.032 mm. Additionally, **"colour count" is ambiguous and neither bundled sample can disambiguate it** — distinct colours, colour runs and DST `CO` blocks are 1/1/1 for the rosette and 2/2/2 for the coil — so it is pinned with a synthetic red→green→red list (3 runs, 2 colours) and must not be reused for the header field.
