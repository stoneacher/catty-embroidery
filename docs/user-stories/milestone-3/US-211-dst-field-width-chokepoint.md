# US-211 — DST serialization field-width chokepoint

**Epic**: E2 Embroidery engine (semantics shared with E7 Export) | **Estimate**: ~3 h | **Depends on**: US-210 (ADR-020)

**Status**: **Done** — implemented 2026-08-25. Specified 2026-07-31 at discovery time (in `backlog.md`); scheduled into M3 on 2026-08-04. **ID preserved** so the ADR-020 and journal references that already cite it keep resolving. **660 engine tests** (up from 649), SwiftLint `--strict` clean, CI green on all three checks. ADR-025 pins it. Planned with `swift-architect`, and **the planning pass corrected six things in the criteria below** (marked **planning correction** inline, each verified against the named source by execution rather than taken on report); Sebastian took two scope decisions, recorded under "Scope decisions". No Ink/Stitch verification needed — the goldens are byte-identical with no re-blessing, which is this story's own acceptance criterion. No app-layer change, so no screenshot and no manual a11y item.

**Story**: As the DST writer, I want the header's fixed-width fields to stop being a `precondition` on ordinary input, so that a design larger than the Tajima header can express fails in a way a caller can handle instead of killing the process.

`DSTHeader.appendField` ends with `precondition(valueBytes.count <= width, …)`. Every field is fixed-width, so a value that does not fit is a crash — and several are reachable from coordinates and colour counts a real design can produce. US-210 closed the *coordinate* chokepoint (ADR-020) and deliberately left this one open: a header field cannot be a guarded no-op the way a stitch can, so the fix is a different decision, not a wider version of the same one.

**It is scheduled here because the export path is the caller that forces the decision** — and now that US-308's design exists, it does.

## The reachable fields

Verified by execution unless marked otherwise. Widths confirmed directly against `DSTHeader.swift:19-30`.

| Field | Width | Overflows at | Reachable how |
|---|---|---|---|
| `+X` / `−X` / `+Y` / `−Y` | 4 | extent > 9999 units | **Confirmed crash**: `addStitch(0,0)` then `addStitch(6000,0)` → `+X` = 12000. But see the asymmetry below — stage x = 6000 is 12× the ADR-007 stage. |
| `CO` | 2 | > 99 colour blocks | **Confirmed crash**: 99 `addColorChange()` calls → `CO` = 100 (width 3). Reachable by a design that never leaves the stage. |
| `ST` | 6 | > 999 999 stitches | **Confirmed by execution (2026-08-04)** — the backlog's "derived, not executed" caveat is retired. Two recipes: the ADR-020 cap move (0 → 60 500 000 stage points) yields **2 500 003** stitches, not the ~1 000 003 originally derived, because intermediates re-split; and `ST` can be isolated from `+X` with 1 000 001 stitches inside a 2-unit extent (alternate two points 1 unit apart to dodge dedup). Both run in well under 0.1 s. |
| `AX` / `AY` | 5, signed | \|value\| > 9999 (negative) | Implied safe once extents are bounded, since \|AX\| ≤ max extent. Not an independent case. |
| `LA` | 15 | — | Already handled: `sanitized()` truncates (ADR-012). |

**The reachability is asymmetric, and the ADR must say so.** Inside ADR-007's 500×500 stage the maximum extent is 1000 embroidery units — comfortably inside the 4-wide fields. So extent overflow is only reachable *outside* the documented stage, whereas `CO` and `ST` are reachable by designs that never leave it. The traps are not equally ordinary, and that asymmetry is what rules out bounding coordinates as a fix.

**The backlog's field list was incomplete**: `DSTHeader.init(stream:name:)` is **public** (`DSTHeader.swift:13`), so it is a second trapping entry point independent of `DSTFile`.

> **Planning correction (2026-08-25) — the field list is still incomplete, in a way widths cannot show.** Two field *expressions* are unguarded signed `Int` subtractions over coordinates ADR-020 deliberately admits up to `Int` range: `box.max.x - first.x` can overflow, and `abs(min(…, 0))` can hit `abs(Int.min)`. They are unreachable, but only via a derivation nobody had written down, and it makes **emission order load-bearing** — `ST` is emitted before the extents, so a throwing `ST` check bounds `stream.count` at 999 999 before any subtraction runs. ADR-025 pins it. Two more fields are unreachable-by-construction for reasons worth stating rather than assuming: `AX`/`AY` because the extents are checked *first* (and then only exactly — `"-9999"` fills the 5-wide field with zero margin), and `LA` because `sanitized(_:)` folds to ASCII over `unicodeScalars` *before* `prefix(15)`, so 15 characters are 15 bytes. Verified across five adversarial names (21 ASCII letters, 18 emoji, 10 combining-accent graphemes, CR/LF pairs, 30 fullwidth scalars). Moving that `prefix` ahead of the `map` would make `LA` a live trap.

## The decision

**`DSTFile.init` and `DSTHeader.init` become `throws`.** Decided at M3 planning (2026-08-04), to be pinned as **ADR-025** at close-out. The three options were not equivalent:

- **Clamp the extent** and emit a header that misdescribes the design — rejected. ADR-012 refuses parity-with-corruption elsewhere; this would be corruption we *chose*, in the one field a machine reads to size the design, and it is undetectable downstream.
- **Bound the design at the app layer** per ADR-007 — rejected, and it fails on its own terms. ADR-007's stage bounds **do not exist as code** (`grep -rn "500" Sources/` returns two comments and no constant), so this option must first introduce engine-space bounds, moving its cost toward the throwing option rather than away. Worse, the asymmetry above means bounding coordinates would close only the trap already out of reach and leave the two that are in reach. Wrong shape for the problem.
- **Throwing, not merely failable** — chosen. It is the only option that lets a caller respond, and US-308 has a caller that must: the export path needs to tell the user *which* limit was hit ("118 colour blocks; DST allows 99"). `Optional` cannot carry that. And `DSTFile` is not gaining an error surface for the first time — `write(to:)` already throws.

**Measured cost**: **33 call sites** gain `try` — 19 × `DSTFile(stream`, 14 × `DSTHeader(stream` in checked-in Swift. In tests these become `try #require` or `throws` test functions.

> **Planning correction (2026-08-25)** — both halves of that sentence are wrong now.
>
> **The count is 41, across 15 files** (25 × `DSTFile(stream`, 16 × `DSTHeader(stream`, the latter including the internal `DSTFile` → `DSTHeader` call), all inside the engine package; US-301 and US-302 added sites after the M3-planning count was taken. **13 pre-existing `@Test` functions** also had to gain `throws`, plus the private helper `InterpolationTests.records(for:)` — 14 functions in total, but the classification matters, and an earlier version of this line said "14 test functions" (Codex round 2 caught the wording repeating a misclassification round 1 had already corrected in ADR-025). The estimate mentioned none of it. There are no app-target call sites yet — US-308 adds the first.
>
> **`try #require` does not compile here.** `#require` has overloads for optionals, `Bool` and `throws:`, none for a throwing non-optional initializer: `error: call can throw, but it is not marked with 'try' and the error is not handled`, plus a `redundant because … never equals 'nil'` warning. ADR-020's "the four in-repo test call sites use `try #require`" was about the *failable* `EmbroideryPoint(converting:)` — a different shape, generalised wrongly. The correct forms are plain `try` inside a `throws` test, or `try #require(throws: DSTSerializationError.self) { … }` where the *error* is the subject.

(Provenance of that number, since it was got wrong once: a planning-session count of 39 came from a `grep` without `--include='*.swift'`, which swept `README.md`, `Tests/InterpreterTests/Resources/GoldenPrograms/PROVENANCE.md` and two `.build/` artifact copies. Codex round 1 caught it. Count Swift only.)

**On the ADR-020 cap (the backlog's AC 3): do not lower it.** Once `init` throws, `ST` overflow is a *handled error*, so the cap no longer needs to protect the header. Lowering 1 000 000 → 999 996 would change interpolation *emission* for moves the engine admits by design, in order to guard an error that is now representable, and would break the shared rationale ADR-014 and ADR-020 both hang on that number. Pin the opposite: `ST` overflow is a serialization error, not an interpolation bound.

## Acceptance criteria
- [x] No `StagePoint` input, however adversarial, makes `DSTFile(stream:name:)` **or `DSTHeader(stream:name:)`** trap. `appendField`'s `precondition` becomes unreachable-by-construction, or the width check moves into the throwing path. **Resolved as: the check moved into the throwing path and the `precondition` was deleted.** *Planning correction*: the ADR-020 analogy that would have kept it does not carry — ADR-020 kept `DSTStitchRecord`'s precondition because that initializer is `public` and reachable directly, whereas `appendField` is `private` with exactly one caller, so a retained precondition would guard nothing.
- [x] Both initializers are `throws`, with a public `DSTSerializationError: Error, Equatable, Sendable` a caller can switch on to name the field, the offending value, and the limit. One case, `fieldOverflow(field:value:limit:)`, carrying a `DSTHeader.Field` rather than a `String` (scope decision 2).
- [x] The `ST` case is confirmed by execution (both recipes above), and the ADR records that ADR-020's 1 000 000 cap **stays**, with the reasoning above. The cap move's 2 500 003 stitches are recorded in ADR-025 and deliberately **not** committed as a test (1.4 s, 134 MB, for a number the tight-extent recipe establishes in 0.5 s).
- [x] Just-inside cases stay working: extent exactly 9999, `CO` exactly 99, `ST` exactly 999 999. All three committed; the `ST` one costs ~0.5 s and ~50 MB and is header-only (scope decision 1). *Planning correction*: the criterion misses that the **negative** extent boundary puts `AX`/`AY` on their own boundary simultaneously, at `"-9999"` — five bytes in a five-wide field. That is the test which makes this story's "`AX` is not an independent case" claim checked rather than asserted.
- [x] Existing golden byte-identity is untouched — the two US-106 fixtures and US-209's `square.dst` stay green with **no re-blessing**. If a golden needs re-blessing, the change is wrong. *Planning correction*: this **undercounts the golden surface** — US-301's byte pins in `OctagonRosetteGoldenTests`, `SquareCoilTests` and `SampleDSTTests` have no fixture file but are equally no-re-blessing surfaces, and they are the ones whose enclosing functions had to gain `throws`. Verified in its concrete form: every changed line of *executable* code in those tests differs only by a `try` or `throws` token — doc comments inside them were rewritten too, which is why the claim needs the scope — with **one forced exception** — `OctagonRosetteGoldenTests`' quarter-turn invariance hoists its two calls into locals, because `try` cannot appear to the right of a non-assignment operator. The assertion is unchanged.
- [x] Sweep the incidental defect ADR-020 recorded but never fixed in code: `StitchPattern.swift:22-23` still says "DST's stitch-count header field itself caps at seven digits". It is width **6** (`DSTHeader.swift:20`). The 1 000 000 bound that parenthetical justifies is unaffected. *Planning correction*: the wrong claim lives **only** in that code comment — ADR-014 does not contain it, and ADR-020 plus the journal already record the correction. So the sweep is one comment, not an ADR edit.
- [x] **ADR-025 states the reachability asymmetry explicitly** — extent overflow unreachable inside ADR-007's stage, `CO` and `ST` reachable inside it — so a later reader does not "simplify" the fix back to bounding coordinates.
- [x] ADR-019 screening: state that these inputs sit deliberately *on* field-width boundaries. That is the subject of the tests, not an accident of them. Stated in the suite doc comment and ADR-025, with the addition the criterion does not make: ADR-019's *deciding* question (ulp distance from the boundary) **does not apply here**, because the comparison is a byte count over exact decimal digits rather than a floating-point threshold crossing. Saying only "they sit on boundaries" would invite a later reader to look for an ulp analysis that does not exist.

## Test-first plan

> **Planning correction (2026-08-25) — `#expect(processExitsWith: .failure)` cannot be this story's red.** Those tests **pass today**: a trap *is* a failure exit, so they characterise the bug rather than fail on it, and they would have to be deleted at green. **Inverting the expectation to `.success`** is strictly better and is what was built: it compiles against today's API with no new types, fails now with `Expectation failed: .success → .signal(SIGTRAP → 5)`, turns green with the fix, and survives afterwards as criterion 1's guard. Where a throwing test covers the same recipe it subsumes the exit test — a trap would kill the whole run — so the expensive `ST` exit test was retired at green rather than paying 0.5 s twice.
>
> **The "ordering trap" below is real as a fact and inverted as an inference.** `appendField` does write `ST` before `+X`, but that means a huge-move `ST` test traps on `ST`, *the field it targets* — executed, the cap move reports `ST value 2500003` and never `+X`. The tight-extent recipe is still right, for a different reason: it makes `ST` the only violated field, so the test proves the check exists instead of leaning on emission order to shadow a simultaneous `+X` violation. (The genuinely load-bearing consequences of emission order are the `Int`-overflow and `AX` derivations, both now in ADR-025.) Two further measured details: the tight extent is **1** unit, not 2, and the `CO` recipe needs no stitches at all — 99 bare `addColorChange()` calls make `CO` = 100 with `ST` and every extent reading 0, so `CO` is the only field over width.
>
> **The `ST` overflow value is 1 000 000, not 1 000 001** (Codex round 1). 1 000 000 is the first value needing a seventh byte, so `999 999`/`1 000 000` is the pair the field actually defines; the story's recipe of 1 000 001 left a regression that accepted exactly 1 000 000 passing every test. For a story about field widths this was the one place precision was owed, and the suite now sits on the real boundary.
>
> **Item 5 is vacuous as a test item** — it adds no test. It is a regression requirement on the existing goldens, and it is kept as criterion 5 in its concrete form ("the diff contains only `try`/`throws` tokens").

1. **Exit tests** pinning today's traps first — `#expect(processExitsWith:)`, the mechanism US-210 already used for ADR-020 — then converted to the chosen semantics. `+X`: `addStitch(0,0)` then `addStitch(6000,0)`. `CO`: 99 `addColorChange()`. `ST`: 1 000 001 stitches inside a 2-unit extent. **These must be exit tests, not ordinary ones**: `precondition` traps, and a trap terminates the test process rather than throwing, so an in-process "characterisation test" would kill the suite instead of passing. (An earlier draft of this plan said "characterisation tests… they pass", dropping the word "exit" that the backlog specification had and losing the mechanism with it — Codex round 1.) **Note the ordering trap too**: `appendField` writes `ST` *before* `+X`, so an `ST` test built from a huge move would trap on the wrong field — isolate it with the tight-extent recipe.
2. The ADR-020 cap move confirms `ST` reaching width 7, and that cap and field are decoupled once `init` throws.
3. Just-inside boundaries stay green (9999 / 99 / 999 999).
4. All 33 call sites updated with `try` / `try #require`; one test proves a caller can distinguish "too large" — and *which* field — from any other failure.
5. The two US-106 goldens and `square.dst` re-run byte-identical.

## Inherited from US-305 (2026-08-13): the fit clamp crops the same designs this story rejects

**Codex round 1 on US-305, High, valid and deliberately not fixed there.** `StageTransform.fitting` clamps its result to `StageTransform.minimumScale = 0.05`, so a fit target wider than `available / 0.05` cannot be shown whole and out-of-hoop content maps outside the viewport — despite US-305's criterion that the hoop ∪ content union keeps such content *visible rather than silently cropped*. Reproducer: `fitTarget(including: StageBox(minX: 7000, minY: 0, maxX: 7000, maxY: 0))` into a 320 × 320 viewport needs scale ≈ 0.0397, gets 0.05, and maps x = 7000 to view x = 341.25 on a 320-point canvas.

**Why it landed here rather than being fixed in US-305.** The threshold is ~5760 stage points of *extent* on a 320-point viewport (~1.15 m of fabric; ~6560 at iPhone width). **Every design that reaches it is already unexportable by this story's own subject**: the 4-wide `+X`/`−X`/`+Y`/`−Y` header fields overflow above 9999 units = **5000 stage points**, which ADR-020 records as reachable and which traps in `DSTHeader.appendField`. So the crop's entire domain sits inside the domain US-211 must already handle, and the two decisions want to be taken together — a preview that shows a design the writer will refuse is its own kind of wrong.

It is also **not silent**: `bounds != StageGeometry.box`, so US-305's hoop-overflow notice still fires and a VoiceOver user is still told part of the design lies outside the hoop. They just cannot see it.

**Deliberately not blessed with a test.** No characterisation test pins the current behaviour, because that is how a defect becomes a specification — the failure mode ADR-024's review notes record from US-302's round 6.

**What this story has to decide**, since the fix is a small change to a chokepoint with seven rounds of review history: `minimumScale`'s own doc comment says "**how far the user may zoom**", i.e. the bound is about *gestures*, and `fitting` is not a gesture. So the aligned fix is to move the gesture bound into `pinched(by:about:)` and leave `init`'s clamp with only an absolute representable floor — after which `fitting` may go as low as the content needs. That changes what US-302's `StageTransformTests` assert (they pin the implementation — `init` clamping — rather than the stated intent), which is exactly why it is not a close-out edit. Note ADR-024 also records that the fitted transform is *constant for every in-hoop design*, so nothing in M3's samples is affected either way.

### Correction (2026-08-13, Codex round 2): the argument above is wrong, and US-305 fixed the crop itself

**The overlap claim is false.** It reasoned that every design the fit clamp cropped was already unexportable because the 4-wide extent fields overflow above 5000 stage points. That confused a design's **span** with its **per-direction extent**: ADR-012 (line 67) writes extents *relative to the first stitch, magnitudes only*, so a design centred on its first stitch can span far more than 5000 points while each direction stays inside the field. Codex's counterexample: `(0,0) → (−3201,0) → (3201,0)` spans 6402 stage points and reports `+X = −X = 6402` units, both well inside 9999. **It exports today and it was cropped in the preview.** The interpolation split (~106 stitches for the long move) is nowhere near any cap either.

**So it was fixed in US-305 rather than inherited here.** `minimumScale` now means what its doc comment always claimed — "how far the *user* may zoom" — and is applied in `pinched(by:about:)`; `init` clamps to a new `minimumRepresentableScale`, so `fitting` may go as low as the content needs. Pinned by `StageFitBeyondGestureLimitTests`, which uses Codex's design as its reproducer.

**This section is corrected rather than deleted, because the wrong argument is the useful part.** It was quantitatively precise, cited the right ADR, and was still wrong — on a distinction (span versus per-direction extent) that the ADR states plainly one line away from where it was read. A deferral rationale that arrives with arithmetic attached is exactly the kind that gets accepted without being re-derived.

**What remains US-211's**: nothing from this finding. The field-width chokepoint is unchanged and still unstarted.


## Scope decisions (Sebastian, 2026-08-25)

1. **Pay for the `ST = 999 999` just-inside test.** It costs ~0.5 s and ~50 MB against a suite that otherwise runs in 0.2 s, roughly tripling the local pre-commit gate's engine leg (measured after: 0.23 s → 0.73 s, with the two `ST` tests running in parallel). Paid because it is the boundary this story is *about* — the same trade `CoordinateChokepointTests` declined for the interpolation cap, and declined there precisely because that cap "is a chosen round number rather than a semantic edge like ±121". A field width is the semantic edge. Committed header-only: the record loop is orthogonal to field widths and costs a further 0.3 s.
2. **Introduce `DSTHeader.Field`** rather than putting a `String` in the error. It collapses three stringly-typed arguments into one, makes the widths a single table, removes the possibility of a tag/width mismatch at a call site, and gives US-308 a `CaseIterable` compile-time-exhaustive switch for its localised field nouns. Accepted cost: it touches all twelve emission lines in the file the goldens depend on, and `Field`/`Field.width`/`Field.limit` are public API from here.

## How the red was proven

Two-step, and stated rather than left looking like an oversight. The **trap** half is a genuine runtime red: three exit tests asserting `.success`, failing with `.success → .signal(SIGTRAP → 5)` (commit 1, `[red]`, CI red on all of them). The **typed-error** half cannot be a runtime red at all — `DSTSerializationError` does not exist before the fix, so those tests' red is a build failure, and there is no third option, because today's code traps and a trap kills the runner. Landing the signatures first so they would compile still crashes on the precondition, so it buys nothing. Their non-vacuity was proven separately, by mutation: changing one expected payload to `.extentPlusY` / `limit: 98` fails with `expected error ".fieldOverflow(field: …extentPlusY, value: "100", limit: 98)" … but ".fieldOverflow(field: …colorBlocks, value: "100", limit: 99)" was thrown instead`, so the `Equatable` comparison discriminates both field and limit.

## Deliberately not decided here

Whether `DSTFile.init` should also refuse a zero-stitch stream. `DSTFileTests.emptyStream` pins that a header-only file is legal today, US-308's export gate wants `assembledStream().count > 1`, and Catty ships exactly the 515-byte header-plus-EOF file US-308 calls an anti-goal. That is the export story's decision; ADR-025 says explicitly that it is not taking it. Also left: narrowing `DSTFileTests.writeToMissingDirectory`'s `#expect(throws: (any Error).self)`, which since this story can no longer distinguish a write failure from a header error — the `DSTFile(...)` call stays *outside* the expectation block, which is what keeps the test honest.
