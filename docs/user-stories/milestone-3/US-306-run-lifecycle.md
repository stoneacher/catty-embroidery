# US-306 — Run lifecycle: driver, `AsyncStream`, batching, play/stop, needle

**Epic**: E4 Stage & preview | **Estimate**: ~5 h | **Depends on**: US-302, US-305

**Status**: In review — implemented 2026-08-17, ADR-027 pinned. **577 engine tests** (up from 546) and 47 app tests; five screenshots. In-loop `swift-code-reviewer` round 1 closed: one Critical (a discarded run corrupting the next), two Important, four suggestions, all accepted. Awaiting the cross-vendor `/codex-review` loop before hand-over.

**Story**: As a user, I want to press play and watch the needle lay stitches, and press stop and still have my design, so the preview is a live run rather than a static picture.

`Interpreter` is a `Sendable` struct with `mutating func step()`, so the driver owns it by value off `@MainActor` and batches its events across. Two reference lessons shape this story: Catroid's adaptive sub-stepping is an *anti*-throttle that must not be ported, and Catty's stop path tears down the object graph its own share code reads — so "export still works after stop" is an acceptance criterion here, not a hope.

## Acceptance criteria
- [x] `InterpreterDriver` owns the `Interpreter` value in a non-`@MainActor` context, loops **`step()`** — not `run(maxTicks:)`, which cannot break on a *stitch* budget — and yields one `RunBatch` per frame's worth of work into an `AsyncStream`.
- [x] `AsyncStream` uses **unbounded buffering**, never `.bufferingNewest`: dropping a batch would lose stitches permanently from an append-only list. Back-pressure is adequate because the producer self-paces and `apply(batch)` is O(batch).
  (**Correction, 2026-08-17, US-306 implementation**: the conclusion holds but the *reason* as written is only half true. "The producer self-paces" is true under `DisplayRunPacing` and **false under `ImmediateRunPacing`**, which every test uses — there the producer races ahead of the consumer and the only bound on the buffer is `maxStitchesPerRun`. That is affordable, roughly 5 MB of `PreviewStitch` at the 200 000 cap, but it is a different argument and worth stating in the form that is actually true.)
- [x] `ticksPerFrame` defaults to **1**, with a `maxStitchesPerFrame` budget for when it is raised. The budget is not theoretical: one tick emits 51 stitches in sample 1 and **132** in a triple-stitch design.
  (**Correction, 2026-08-17, US-306 implementation**: this criterion said **106** for the triple-stitch design. The figure is **132**, pinned as a literal in `SampleBudgetTests.perTickStitchMaximum` — `(SampleID.squareCoil, 132)` — by a test whose own doc comment says it is pinned *because* "US-306 sizes its per-frame budget against it". Re-measured at 132 during implementation. The same stale 106 appeared in the milestone README's design summary and is corrected there too. It changes no decision — the budget default is 2 000, which clears either figure by an order of magnitude — but a story citing a number no test defends is exactly what that test was written to prevent.)
- [x] **The budget governs how many ticks run per frame, not how large a batch may be** — `step()` returns one atomic `[InterpreterEvent]`, so the driver cannot split it and a single tick can exceed any per-frame cap by any margin. **There is no fixed global bound at all**: `step()` loops every runnable thread and accumulates all of their events into one array (`Interpreter.swift:79`), so the worst case scales with the number of concurrent scripts. Per thread per tick the bound is **3 000 002** events — one `.needleMoved` emitted before the stitches (`Interpreter+Step.swift`), plus the first anchor, plus 3 × ADR-014's 1 000 000 *segment* cap, since `TripleStitchPattern` emits three points per segment ("so at most 3× that many stitches", its own source comment). An oversize batch is applied in a single observable mutation — correct, just a known worst-case frame.
  (Provenance: the first draft said "up to ADR-014's 1 000 000 cap" and implied the cap was enforceable at this seam. Codex round 1 corrected it to 3 000 001 and flagged the atomicity; round 2 found that still wrong on two counts — the missing `.needleMoved`, and the absence of any global bound once more than one thread runs.)
  (**Implementation note, 2026-08-17**: measured rather than argued. One thread, `tripleStitch(1)` + `moveNSteps(2000)`: **6 001 stitches in one tick**. Eight concurrent scripts each moving 1 000 steps: **24 008 in one tick**, all in the same tick because ADR-018 round-robins one action brick per thread and every thread spends tick 0 activating its pattern. Both are applied whole. Also learned: at the default `ticksPerFrame = 1` the per-frame stitch budget is **unreachable by construction**, so the tests that exercise it must raise `ticksPerFrame` *and* give the program work after the oversize tick — as written, both halves of test item 5 would have been vacuous.)
- [x] The view model performs **exactly one** observable mutation per batch. A test proves the mutation count equals the *batch* count, not the stitch count — this is the roadmap's "batched before mutating observable state", made checkable.
  (**Implementation note, 2026-08-17**: the obvious test for this is green against the very implementation the criterion forbids. `withObservationTracking`'s `onChange` is **one-shot**, so a view model that appended stitch by stitch fires it on the first stitch and the remaining thousands go unobserved — reporting 1, exactly as a correct implementation does. What makes the claim checkable is `PreviewRunState.revision`, a counter bumped once per `apply(_:)`, asserted against the *update* count: 139 against 3 194 stitches for `octagonRosette`. The property is additionally structural — `RunViewModel` has exactly one observed stored property and one method that mutates it, so a per-stitch fold is not reachable without adding a second statement.)
- [x] `RunState` is `idle | running | finished(.programFinished | .stoppedByUser | .stitchLimitReached)`. **There is no `failed` case** — ADR-018 guarantees the interpreter never halts (every bad-formula path continues with a per-brick fallback; `FormulaError.notANumber` is caught, not propagated), so nothing in the run path can fail. `failed` belongs to `ExportState` in US-308. This deliberately corrects ROADMAP.md's four-case enum rather than shipping a case with no producer.
- [x] `forever` never terminates on its own, so the app owns the stop: no hard tick cap, a generous stitch cap that resolves to `.stitchLimitReached`.
- [x] The run `Task`**s are** cancellable; the driver checks `Task.isCancelled` each frame; the producer finishes the continuation on every exit path and `onTermination` cancels the producer.
  (**Correction, 2026-08-17, US-306 implementation — this criterion was wrong in two ways, and one of them would have failed silently.**
  *First, "the run `Task`" is singular and there are necessarily two*: a producer stepping the interpreter off the main actor, and a consumer applying batches on it. Only the producer can *decide* to stop — it observes `Task.isCancelled` and emits the terminal update carrying `assembledStream()` — so a `stop()` that cancelled the consumer (the natural reading of this criterion, and what cancelling a `for await` task or a `.task {}` does) would leave the interpreter running to its natural end or the stitch cap, produce no `.stoppedByUser` terminal at all, and lose anything yielded after the buffer drained. Export-after-stop would fail the way Catty's does while every producer-side test still passed. `RunSession.stop()` therefore cancels the **producer only**, and the consumer drains until the stream finishes — usually **one** element later and occasionally two. (Codex round 3 corrected the example this sentence first gave: a stop landing *inside* a frame costs only one element, because round 1's fix re-checks cancellation after the frame and the frame's stitches ride out on the terminal itself. Two happens only for a stop landing between the completion check and the ordinary yield.)
  *Second, "`onTermination` finishes the continuation" is backwards*: `onTermination` fires *because* the continuation was finished or dropped, so calling `finish()` inside it is a no-op. The wiring the criterion is reaching for is the reverse — the producer finishes the continuation from a `defer` on every exit path, and `onTermination` cancels the producer, so a consumer that walks away stops the interpreter instead of leaving it running to the stitch cap.)
- [x] **The terminal batch always carries `assembledStream()`** — on natural finish, on the stitch cap, *and* on cancellation. Catty's `Stage.stopProject()` calls `removeAllChildren()` and `project?.removeReferences()`, destroying the graph `shareDST` reads; making the export model part of the terminal batch closes that hazard by construction. At 0.64 ms per 50k call (measured), once per run is free.
- [x] The stage keeps rendering in `.finished` (Catroid precedent: `StageListener.render()` still calls `stage.draw()` whenever `!finished`, regardless of pause).
- [x] `reset()` is one assignment, because the interpreter is a value type — contrast Catroid's three separate resets (`embroideryPatternManager.clear()` twice, `resetDrawingState()`, `resetEmbroideryThreadColor()`) and Catty's reload-from-disk.
- [x] Pacing sits behind an injected `RunPacing` interface (ADR-006 pattern 2): a display implementation sleeps ~1/60 s, an immediate implementation returns instantly so a test drains a whole run deterministically without sleeping.
  (**Implementation note, 2026-08-17**: "returns instantly" must not mean an empty body. An `async` function that never suspends does not yield the cooperative thread, so a `forever` program under immediate pacing would monopolise it and starve the consumer until the stitch cap — a hang that reads like a deadlock and is nothing of the kind. `ImmediateRunPacing.waitForNextFrame()` awaits `Task.yield()`. A third implementation was also needed and was not anticipated here: a **gated** pacing double, because under immediate pacing a mid-run `stop()` races a natural finish and the completion reason comes back `.programFinished` — green for the wrong reason, flaky for the right one.)
- [x] Needle indicator: greenfield on both platforms (Catroid's needle is an ordinary sprite with a PNG; Catty has zero occurrences of "needle" in `src/`). Judged on ADR-009 cost and accessibility, not parity. It must **not** be announced continuously by VoiceOver.
- [x] **Story-specific definition of done**: play/stop ≥ 44 pt with localised labels and accessibility labels that change with state; **Reduce Motion does not disable the stitch animation** — that is the feature's content, not decoration — it disables transform springs and the fit-to-screen re-animation.
- [x] Close-out records the batching numbers discovered by watching real samples animate: `ticksPerFrame`, `maxStitchesPerFrame`, the stitch cap, and the `tickDelta = 1/60` coupling.

## The numbers this story settled

| Quantity | Value | How it was chosen |
|---|---|---|
| `RunBudget.ticksPerFrame` | **1** | ADR-018's coupling: one logical tick per displayed frame, so `wait(1)` reads as one second. |
| `RunBudget.maxStitchesPerFrame` | **2 000** | Clears the measured per-tick maxima (51 and 132) by an order of magnitude. **Unreachable at `ticksPerFrame = 1`** — it exists for when the tick count is raised. |
| `RunBudget.maxStitchesPerRun` | **200 000** | Bracketed on both sides: 4× US-309's 50 000-stitch exit criterion, and well under the DST `ST` field's 999 999 ceiling that US-211 turns from a trap into a thrown error. Counts stitch *events*, not export records. |
| `AppRunClock.frameSeconds` | **1/60** | The single number both `InterpreterClock.tickDelta` and `DisplayRunPacing.frameDuration` are derived from — two literals could drift, and the symptom would be `wait(1)` no longer reading as a second. |
| `PreviewRunState.settleChunk` | **1 000** | A starting value US-309 tunes, like `bakingThreshold = 2000`. Measured: `octagonRosette` settles at 3 000 of 3 194 (three advances), `squareCoil` at 2 000 of 2 976 (two) — both cross the baking threshold, so M3's real samples now exercise the raster path US-305 could only ship unreachable. |
| Frames per sample run | **139** (`octagonRosette`), **137** (`squareCoil`) | ≈ 2.3 s at 60 Hz. |
| Observable mutations per run | **equal to the frame count**, not the stitch count | 139 against 3 194. |
| Worst measured single tick | **24 008 stitches** (8 concurrent scripts), **6 001** (1 thread, triple stitch + 2 000 steps) | 3.1 ms and 1.0 ms in release. Applied whole. |

**ADR-024's open question is answered.** It asked, addressed to this story by name, at what scale `Image(size:renderer:)` rasterises — because if it were 1× rather than the display scale, the settled layer would be visibly softer than the live tail and a seam would show at the watermark. With `settleChunk = 1000` the watermark now advances at runtime for the first time, so the question became answerable: magnifying a definitely-settled region (inner blue, well before index 2 000) against a definitely-live one (the final orange tail) in the post-run screenshot shows **identical edge quality — no seam**. `Image(size:renderer:)` rasterises at the display scale.

## Test-first plan
1. [x] With immediate pacing, a full sample run drains to `.finished(.programFinished)` and the display list count equals that sample's stitch-event count. **Not "from US-301"** — `SampleRun`/`SampleRunHarness` live in `SamplesTests`, and SwiftPM forbids a test target depending on another test target (the same constraint that forced US-301 ahead of US-302). The count is re-derived from the interpreter and the literals 3 194 / 2 976 are pinned separately, so a drift names itself instead of moving both sides of the equation at once.
2. [x] Observable-mutation count equals batch count, not stitch count. **Not by spying on the apply path**, which only measures how many times `apply` was called — trivially once per update, and blind to the defect. See criterion 5's note: the naive `withObservationTracking` counter is green against the implementation the criterion forbids.
3. [x] Cancelling mid-run leaves `.finished(.stoppedByUser)`, a non-empty display list, **and** a non-nil export model. Needed a **gated** pacing double: under immediate pacing the stop races a natural finish. Asserted at both layers — the driver's terminal batch is empty here, so the assertion is on the display list, not the batch.
4. [x] A `forever` program stops at the stitch cap with `.stitchLimitReached` and does not hang. `.timeLimit(.minutes(1))` so "does not hang" fails instead of hanging the suite; a small injected cap rather than draining the 200 000 default, which is pinned separately.
5. [x] **Oversize single tick**, two cases. Both were **vacuous as written** and had to be rewritten: at the default `ticksPerFrame = 1` the per-frame stitch budget is unreachable, so the tests would have proved only that a batch is not truncated. They run at `ticksPerFrame: 4, maxStitchesPerFrame: 100`, against a program with work *after* the oversize move — otherwise the run finishes inside the same frame and "the frame ended at the budget" has nothing to observe. Measured, and discriminating: one thread gives `[6001, 30]` with the budget against `[6031]` without; eight concurrent scripts give `[24008, 240]` against `[24248]`. The story's stated worst case of 3 000 002 events per thread per tick is an **argument, not a fixture** — reaching ADR-014's 1 000 000-segment cap also engages ADR-020's interpolation refusal and would take minutes.

6. [x] `reset()` returns `.idle`, empties the display list and clears the export model; a second `play()` reproduces the identical display list. **Asserted on `.stitches`, never on the whole `StitchDisplayList`**: its synthesized `==` includes `resetCount`, which differs 1 against 2 across two runs by design, so comparing the values would fail for a reason unrelated to determinism and send the next reader hunting a nondeterminism that was never there.
7. [x] `wait(1)` under `tickDelta = 1/60` occupies **exactly 60** batches. **No drift appeared and there was nothing to pin**: sixty accumulations of `1.0/60.0` sum to `1.0000000000000013`, which is `>= 1.0`, so the wait completes on the sixtieth tick. The 60 is design-dependent and the design is now stated in the test: the driver detects completion with `Interpreter.isFinished` after the tick, so the frame that finishes the wait is also the terminal frame. A driver spending an extra `step()` to discover `.finished` would produce 61. A bracketed case (`runningStitch`, `wait(1)`, `moveNSteps` → **62**) stops an off-by-one hiding in the first or terminal frame.
8. [x] Screenshots mid-run and post-run, plus the now-reachable "Ready to Stitch" state, dark mode and AX5. Dark mode proves ADR-024's canvas-invariance claim visually — the pane, title and back button adapt while the mat, hoop and both thread colours are pixel-identical. AX5 wraps the hoop caption to two lines and keeps "Play Again" on one, nothing truncated, with the canvas yielding space first.

## In-loop review, round 1 (`swift-code-reviewer`, 2026-08-17)

One **Critical**, two **Important**, four suggestions. All accepted; nothing rejected.

- **Critical — a discarded run's buffered frames landed in the run that replaced it.** And it was reachable: pick a new sample while a run is in flight. Measured at 5 001 stitches and `.finished(.stitchLimitReached)` arriving *after* a `reset()`, with a buffered terminal publishing the discarded design's export model — US-308's input.
  **The finding matters more than the defect, because my own reasoning is what hid it.** The correction above argues from "`AsyncStream.Iterator.next()` returns `nil` when the consuming task is cancelled", which I wrote into this story, into ADR-027 and into three code comments. It is **false while elements are buffered**, and I only checked it after the reviewer contradicted it: a consumer cancelled before it ever ran still received all five buffered elements, and `next()` in a cancelled task with one buffered element returned the element. Cancellation marks the stream terminal; it does not discard `pending`. The premise is what made buffered stale frames look impossible, so nothing guarded against them. Fixed twice over — `Task.isCancelled` in the consumer, and `PreviewRunState.apply` refusing updates unless the run is `.running` — and both guards were proven load-bearing by reverting each and watching the new tests fail.
- **Important — `ticksPerFrame: 0` produced a run that could never end**, yielding empty frames forever with **zero** terminals: the only path found that breaks the terminal guarantee. Every `RunBudget` axis is now clamped to at least 1 and the axes are `let`, since a clamp in `init` is defeated by assigning to a `var`.
- **Important — the "no needle once finished" test could not fail.** It recomputed the rule in its own body and asserted the result, so it stayed green if `RootView` dropped the condition. The rule moved into `PreviewRunState.visibleNeedle` and is pinned in the package; the app test now asserts only the wiring it can actually observe, and its comment says so.
- Suggestions taken: `deinit` cancels the consumer; the `settleChunk` modulo is guarded against a future zero (which would **trap**, not degrade); the limit notice gained plural variations, being the catalog's first numeric string; the stitch-cap test asserts `terminalCount == 1` like the other two terminal paths.
- Three doc claims corrected rather than edited away: the `AsyncStream` premise above, `onTermination`-assigned-after-`finish` not running immediately (measured), and "one element after `stop()`" being one *or two*. Also narrowed: `apply`'s "O(batch), never O(display)" holds only within the value — in the app the list is handed into the view tree, so copy-on-write makes the frame O(display) regardless.
- Confirmed sound: the terminal guarantee on all three real paths, `runFrame`'s arithmetic for positive budgets, the watermark and cache-key safety, and — recomputed from sRGB — every needle contrast figure to the stated precision.
