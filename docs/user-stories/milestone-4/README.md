# Milestone 4 — Block editor

**Status**: Planned — 2026-09-19. Fourteen stories, **~58 h**: eleven new (US-401…US-411) plus three carried in from the backlog (US-312, US-314, US-315). Planned with `swift-architect`, a read-only reference sweep of Catroid and Catty, and a package/app inventory, in the session that closed M3.

Goal: **create and edit programs in the app.** M3 proved the thread from a bundled sample to a `.dst` file; M4 makes the program on the near end of that thread the user's own. A brick palette adds bricks, a flat list reorders and deletes them, type-specific editors change their parameters, every mutation is undoable, and the working program survives a relaunch. See [ROADMAP.md](../../ROADMAP.md).

Every story is developed test-first: the tests listed in its "Test-first plan" are written and red before implementation starts.

The first four stories (US-401…US-404) are **package-only** and run entirely on the existing fast `swift test` gate — deliberately the same shape M3 used with US-301/US-302, and for the same reason: the editor's hard parts are pure value transformations, and they should be proved before any pixel exists. US-314 follows them and is *not* package-only, despite sitting next to them in the order.

Placement decided by Sebastian at this planning session (2026-09-19).

- **US-314** is here because M4 *increases* its exposure: [ADR-038](../../DECISIONS.md) makes every applied edit **void** the run — leaving it idle, to be replayed — so "the design grows while the user is manipulating the stage" stops being an edge case and becomes the ordinary rhythm of editing. *(Codex round 1 corrected two things here: an applied edit voids rather than "restarts", and this story is **not** package-only — `StageManipulation`'s begin methods receive no fit, while the cancellation path in `StageManipulationCoordinator.swift:231` touches only `manipulation.cancelled()`, so the baseline needs app wiring and an integration test. - **US-312** is taken **against its own backlog note**, which said the sidecar option is "better decided once M5's file handling exists". That note is still right about the *sidecar*, and this story is therefore scoped to the option that does not need M5: **say so in the app**. The sidecar *decision* is left to M5; the **research** that informs it is this story's close-out obligation, so M5 inherits an answer rather than the question. Recorded this way because the entry's advice was overridden deliberately, not overlooked.
- **US-316 was considered and not taken.** It stays in the backlog. The cost is stated rather than glossed: M3's 60 fps exit criterion remains unmet with no scheduled work against it, and the A15-class capture — open since 2026-09-02 and already re-deferred once at M3 close on the grounds that US-316 must precede it — stays blocked for a second milestone. The backlog preamble's own precedent (the ±121 trap, deferred once and then mis-scoped twice) is the risk being accepted. It is accepted knowingly: M4's value is the editor, and US-316 is an open-ended measurement story whose first half is building a fixture that may refute ADR-009's bet rather than tune it.

## Milestone exit criteria

1. **A program can be built from nothing and embroidered.** Starting from a blank program, a user adds bricks from the palette, edits their parameters, reorders them, runs the result on the M3 stage, and exports a `.dst` — with no bundled sample involved at any point.
2. **Every editor mutation is undoable**, proved by a test that enumerates `EditAction`'s cases and asserts each one round-trips through undo to a `Program` equal to the one before it. Enumeration, not a hand-written list — a new action case must fail the test rather than silently escape it.
3. **The working program survives a relaunch**, including across a force-quit, and a program the app cannot understand is refused with a message rather than clobbered.
4. **The pair invariant is unbreakable through the UI**: no sequence of palette adds, reorders and deletes can produce a script that fails `Script.validate()`. Asserted as a property over generated action sequences, not only as worked examples.

Criteria 2 and 4 are deliberately written as properties rather than scenarios, because both are claims about *everything the user can do*, and M3's most expensive lesson (US-309's `drawn=0` capture scoring `PASS`) is that a criterion satisfied by a worked example can be satisfied by a test that cannot fail.

**Not an exit criterion, and named so it is not quietly inherited**: M3's 60 fps criterion. It left M3 unmet on the mid-gesture tail and no M4 story addresses it (see US-316 above).

## Design summary

Decided at the M4 planning session (2026-09-19) with `swift-architect`, grounded in the Catroid canonical implementation, Catty prior art, and the shipped M2/M3 package API. Four ADRs are pinned at planning time because US-401's and US-402's tests are written against them; five more are reserved for the stories that discover them.

- **`EditorCore` is a sixth target depending on `ProgramModel` only** among package targets (ADR-033), the same shape ADR-022 gave `Samples`. Foundation is permitted — US-404 puts `Data` and `JSONEncoder` there — exactly as `StagePreview` is "Foundation-only". It is **not** put inside `ProgramModel`, because `ProgramModel`'s public API *is* the serialized format — `SampleJSONResourceTests` asserts `decode(resource) == builder()` — and an undo stack and a palette catalogue are not part of the file. `Script.movingPair(at:to:)` stays where ADR-008 put it and `EditorCore` **wraps** it; nothing is moved or duplicated.
- **No human Xcode session is needed, and this was measured rather than assumed.** A SwiftPM library product may vend several targets, so `.library(name: "ProgramModel", targets: ["ProgramModel", "EditorCore"])` makes `import EditorCore` resolve in an app that already links the `ProgramModel` product. Executed at planning time: the package built, the app's `build-for-testing` succeeded with a probe file importing the new target, and `git status --porcelain -- '*.pbxproj'` was **empty**. The probe was reverted. The cost is a sentence in ADR-033, because product ≠ target 1:1 for the first time and ADR-022's "five products, five targets" bookkeeping stops holding.
- **`apply(_:to:)` is pure, total and non-throwing**, returning an `Equatable` `EditResult` (ADR-033). A deliberate divergence from `movingPair`'s and ADR-025's throwing precedent, for a reason specific to this caller: **every call site branches on rejection**, because a rejected edit must push no undo entry, trigger no autosave, and void no run. With `throws` the ergonomic call is `try?`, which discards the reason — exactly what ADR-025 argues against. `ScriptMoveError` is *wrapped*, never redefined.
- **Brick identity stays out of the model** (ADR-034). Addressing is index-based, mirroring `movingPair`. The cost of the alternative is measured: `bricks:` appears **84 times across 18 files** in the package, including every M2 golden and both sample builders — and worse, a UUID field would break whole-`Program` equality (ADR-006 pattern 3) and `decode(resource) == builder()`, since two structurally identical programs would compare unequal. SwiftUI identity is index-derived, which is **bought** by pushing parameter editing off-row (ADR-039): a row that holds no focus or gesture state can be index-identified honestly.
- **Pair semantics for the four verbs are pinned before any test is written** (ADR-035). Inserting a loop opener inserts **two** bricks so the script is balanced by construction; `.loopEnd` is never in the palette; deleting at an opener removes `[opener…loopEnd]` **inclusive of the body** (Catroid parity — `RepeatBrick.getAllParts()` + `BrickController.delete` on a nested model); deleting at a `loopEnd` redirects to its opener; moving a `loopEnd` is rejected.
- **The `.onMove` destination convention does not match the model's, and the conversion is a named deliverable.** SwiftUI's `toOffset` is an index into the array *before* removal; `Script.movingPair(at:to:)` documents its destination as an insertion index into the list with the block *already removed* (`0 ... remaining.count`, verified in the source). They differ for every downward move. US-408 owns the adapter and a test that exercises a downward move over a multi-brick pair, or reorder lands one position off in half of all cases.
- **The package undo stack is the truth; `UndoManager` is only a trigger surface** (ADR-036). Verified in the iOS 27 SDK: `EnvironmentValues.undoManager` is **get-only**, so `.environment(\.undoManager, …)` does not compile and the environment's manager comes from the responder chain. It may also be `nil`. So undo/redo buttons drive the package stack directly and the feature works with no `UndoManager` at all; what the bridge buys is shake-to-undo, three-finger gestures and the edit menu — accessibility affordances, not logic. **Because the manager keeps its own history and does not observe the stack, it must be re-synchronised after *every* history transition** — a toolbar undo otherwise leaves it holding a registration the stack no longer has *(Codex round 1; the first draft thought a `loadProgram` funnel sufficed)*. Coalescing is an explicit **session** opened and closed by the parameter editor's presentation, never a timer, so it stays a pure testable value with no clock.
- **Autosave has to answer for more than one window** (ADR-037). `UIApplicationSupportsMultipleScenes` is `true` and `WindowRootView` owns an `AppModel` **per scene** — a deliberate, documented decision. So "one working program at a fixed path" loses data: two windows on program P, edit A to Q, background unchanged B, and B's lifecycle save writes P over Q. US-406 chooses a policy before implementing. The recommendation is a **monotonic revision carried by each save**, with an older-revision write dropped — **not** a per-window "has applied an edit" flag, which was the first remedy and does not work: A saves Q, B saves newer R, A then backgrounds and its stale save still qualifies *(Codex rounds 1–3)*. *(Found by Codex round 1 — the first draft promised a single file with no multi-window answer.)*
- **Autosave also owns the non-finite `Double` policy, and that is a milestone correction** (ADR-037). `Variable.swift` and `Formula.swift` both say in prose that "the M5 persistence layer pins the policy" — but the ROADMAP puts autosave in M4, so M4 builds the first save path and therefore owns it. It is reachable from an ordinary number pad rather than adversarially: `Double("1e400")` is `+∞`, a 310-digit entry is `+∞`, and `JSONEncoder` then throws `EncodingError.invalidValue` (all three executed at planning). The policy is **reject at input** with a readable reason (ADR-025's shape one layer up), keep the default coder so there is only one encoding of the format, and surface an escaping encode failure loudly rather than silently.
- **An applied edit voids the run** (ADR-038), reusing ADR-027's existing discard path — consumer cancellation, generation bump, `onRunDiscarded → exporter.discard()`. The in-flight interpreter is unaffected because `Interpreter(program:clock:)` takes the program **by value** and builds compiled threads and independent runtime stores from it rather than reading through a retained copy — the lucky part of M3's design: mutating the editor's program cannot reach a running interpreter. What genuinely goes stale is the **prepared export file** — ADR-026 writes it eagerly because `ShareLink` needs its item at construction — so without this rule a user could edit a program and share a `.dst` describing the one they no longer have. ADR-027 closed "export after stop must still work"; this opens "export after *edit* must not silently work".
- **Parameter editing is off-row** (ADR-039) — tap a row, get a sheet on compact and a popover on regular from one call site via `.presentationCompactAdaptation(.sheet)`. It is the single decision that answers three problems at once: identity (no per-row focus state, so index identity is honest), accessibility (the row can be one combined VoiceOver element with values in its label, as the ROADMAP requires, with no trapped inner controls), and coalescing (the presentation's lifetime *is* the undo session).
- **A brick whose parameter is not a literal is editable where M4 has a control for it, and read-only where it does not.** `.number` gets the number pad and `.variable` gets the variable menu; **`.binary` and `.unaryMinus`** are rendered as text and cannot be edited until M6's formula editor exists, and the read-only path preserves the tree rather than flattening it to a literal. This is not hypothetical and not adversarial: `OctagonRosette`, a **shipping sample**, contains `.repeatLoop(times: .variable("Outer Loop"))` and `.turnRight(.binary(.divide, .number(360), .variable("Inner Loop")))` — **8 non-literal `Formula` nodes across 6 brick parameters** (Rosette 6 in 4, Coil 2 in 2). The alternative (seed the pad and overwrite) silently destroys a working sample the first time a curious user taps it. *(This count took three attempts and is now measured by parsing the checked-in JSON rather than reading source: 14 was a grep that swept in `PROVENANCE.md`; 7 was a source-occurrence count that missed `coilLoop` being a helper called twice. Codex round 1 said 8, I "corrected" it to 7 in round 1, and round 2 showed 8 was right all along.)*

## Documented deviations from the references

Both references were swept read-only for this plan. The headline is that **the editor owes them less than M3's renderer did**, because on four of the five questions there is no precedent to port.

| Deviation | Why |
|---|---|
| A curated, embroidery-focused palette | **The `embroideryDesigner` flavor restricts nothing.** It is four lines of Gradle (`catroid/build.gradle:280-283`) that flip the default of a checkbox preference; the embroidery user sees every stock category *plus* an extra one. What we port is the Embroidery **category** (`CategoryBricksFactory.kt:1039-1056` — 8 embroidery bricks + 11 peripheral motion bricks), not the flavor. The curation is ours to design. |
| Tap-to-add appends at a defined insertion point; no forced drag | Catroid's palette is tap-only, but the tap injects the brick at the **midpoint of the visible list** and immediately enters drag mode, so the user *must* place it (`ScriptFragment.java:613-634`); Catty does the same (`ScriptCollectionViewController.m:626-631`). SwiftUI has no programmatic drag initiation, so the reference flow is not portable. We insert at a defined point and scroll to it. |
| Full multi-level undo **and** redo, covering every mutation | Better than both references, with nothing to port. Catroid has **one** level, stored as a whole-project `undo_code.xml`, with **no redo**, and drag-reorder, brick-add and copy are **not undoable at all** (`ScriptFragment.java:882-943`; snapshot triggers at `:856`, `FormulaBrick.java:219`, `BrickSpinner.java:179`). Catty's script editor has **no undo whatsoever** — `NSUndoManager` appears only in PocketPaint. |
| Type-specific parameter editors instead of a formula keyboard | Neither reference has a simple numeric path: **every** number in Catroid routes through the full formula editor (`FormulaBrick.java:152-164`), and `content/strategy/` contains exactly three non-formula editors (colour, note, visual placement). Catty is the same. M4's number pad is a deliberate divergence, and it is what forces the read-only `.binary` rule above. |
| A curated thread palette rather than a system colour picker | Nothing to port: Catroid delegates to **Paintroid's `ColorPickerDialog` from a binary AAR** (`catroid/src/main/libs/colorpicker-signedRelease.aar`), and Catty has no brick colour picker at all — its thread colour is a plain text field (`StitchThreadColorCell.swift:22-51`). A fixed palette also keeps colour a **discrete** edit (nothing to coalesce) and avoids a `Color`→display-P3→hex round-trip feeding ADR-015's parser values it has never seen. It is also the honest UI for an attribute DST cannot carry (US-312). |
| Deleting a loop deletes its body, with undo as the safety net | Catroid parity, and its mechanism is worth citing so a later reader does not "fix" it: `getAllParts()` returns head + end only, but the body lives *inside* the composite object, so `BrickController.delete` takes it along (`BrickController.java:65-81`, `ForeverBrick.java:41`). Catroid offers no confirmation and no unwrap path. We match the semantics and **do not** add a confirmation dialog, because unlike Catroid we have full undo — the affordance that makes a confirmation unnecessary. An "unwrap, keep the body" action is a different verb and is out of M4 scope. |
| Autosave on every committed edit | The references sit at opposite extremes and neither is right: Catroid saves only on `onPause`, back-press and the undo snapshot, so a crash mid-edit loses work; Catty saves after nearly every mutation (`ScriptCollectionViewController.m` — eleven call sites). At ~4 KB per program there is no reason to debounce, and a debounce means a clock, which means injection and a test double for a problem that does not exist. |
| Index addressing rather than Catroid's nested `CompositeBrick` tree | ADR-008 already chose the flat model, and Catty independently arrived at the same flat representation with paired begin/end bricks (`CatrobatSetup+Bricks.swift:39-48`). Catroid's tree is the outlier, and porting its move/delete/resize semantics would mean porting the tree. |

## Human prerequisites

**None for the code.** Measured at planning time, not assumed — see the Design summary. No new package product, no new Info.plist key, no entitlement (`UndoManager` needs none), and app Swift files are picked up by the synchronized folder group.

One **dated, human-owned item**, scheduled as its own line rather than as a bullet inside the story it blocks — the rule the workflow journal wrote after US-303's Xcode session cost a session boundary:

## Definition of done

Every UI story inherits [ROADMAP.md](../../ROADMAP.md)'s M3+ definition of done in full (String Catalog with translator comments, leading/trailing layout, loading/empty/error states shipped with the feature, Reduce Motion, VoiceOver, ≥ 44 pt targets, Dynamic Type to AX1) plus a simulator screenshot via XcodeBuildMCP. Each story restates only what is *specific* to it.

Three clarifications specific to this milestone:

- **The reorder affordance must work without dragging.** A VoiceOver user cannot drag, so the custom accessibility actions are the *primary* path for them, not a courtesy. They must be **pair-aware**: "move up" on a loop opener jumps the whole preceding sibling block, or the model stays balanced while the screen shows a loop swapping with its neighbour's `loopEnd`. That computation is a pure function and belongs in `EditorCore` beside `range(ofPairAt:)`.
- **Custom actions live behind the rotor.** US-313b's finding applies directly and was a defect *in the test procedure*, not the app: write the procedure as "rotate to Actions, then swipe", or the pass will be recorded as a failure.
- **The manual accessibility pass is bundled once, at the end**, as it was in M3 — VoiceOver, Dynamic Type and Reduce Motion across the whole editor after US-411, not per story. What was not run gets recorded.
